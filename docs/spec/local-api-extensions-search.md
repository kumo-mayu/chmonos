# 拡張データの検索とメモリ [採用]

> **要点**：ほかのソフトの欄は、宣言で `search: true` を付けた物だけをメモリに持ち、検索の条件にする。条件は「＋ 条件を追加」に欄ごとに並べ、今の部品（範囲・日付・候補から積む・三項）を型から当てはめる。
> 段階：[採用]（2026-11-27・ユーザ判断「OKです。それらのできないことは仕様とします」）。まだ作っていない。拡張データの全体は [local-api-extensions.md](local-api-extensions.md)、今の検索の条件は [search-filters.md](search-filters.md)。

## なぜ

ユーザの言葉（2026-11-27）：「メモリ削減案。検索条件に不要なものを宣言時に指定してもらい、検索に必要なもののみをメモリに置く仕組み。検索条件モジュールへの発展を議論しよう。」

検索と件数は、打つたびに全部の商品で数え直す（`SearchFilterPass`）ので、照らす値はメモリに要る。照らさない値まで持つと、件数とソフトの数に比例してメモリが増える。

## メモリに持つ欄 [決定]

- 欄の宣言に `search: true` を付けた欄だけを、API の写し（`QuerySnapshot`）と画面の検索に持つ。検索の条件・件数に使えるのはこの欄だけ。
- **既定は持たない**（付けない）。既定を持つ側にすると、検索を考えていないソフトの値が全部メモリに乗り、メモリを守るかが作り手の気遣いに任される。付け忘れても軽い側に倒れる。
  ユーザの案（要らない物に印を付ける）から向きだけ変えた。
- 付けない欄はファイルに置いたまま。読むのは商品ページを開いた時・1件の GET・`batch` の時だけ。メモ欄はいつも持たない。
- 一覧・検索の答えの `include=extensions` には、メモリにある欄だけを入れる（200件の答えのために200個のファイルを読まない）。全部の欄は1件の GET か `batch` で。
- `search` の付け外しは宣言の変更として受ける（値の意味は変わらない）。付けたら全件を読み込み、外したらメモリから捨てる。
- 上限は `search` を付けた欄と付けない欄で分ける（メモリに乗る前の方を小さく）。数は [local-api-extensions.md](local-api-extensions.md)「上限」の計測で一緒に決める。

## 検索の条件 [決定]

- 「＋ 条件を追加」に見出し「ほかのソフトの情報」を足し、その下にソフトごとのまとまりで欄を並べる（例「試着チェッカー：ポリゴン数」）。
  前に決めた「ソフト → 欄 と選ぶ」から、今の条件と同じ1段で選ぶ形に変えた。
- 型から部品を当てはめる：

  | 欄の型 | 条件の部品 | 今の似た条件 |
  |---|---|---|
  | 数 | 範囲（スライダ2本と分布の帯） | 価格・スキ数 |
  | 日付 | 日付（始まり・終わり） | 公開日 |
  | 真偽 | 三項（はい・いいえ・両方） | お気に入り |
  | 選択肢 | 候補から積む（件数つき・AND／OR） | カテゴリ |
  | 文字の一覧 | 候補から積む | BOOTH タグ |
  | `avatarList` | 候補から積む（アバターの名前） | 対応アバター |
  | 文字・URL | 「含む」の欄（新しい小さな部品） | — |
  | 表 | 後回し（「どれかの行が合う」の形を使い道が出たら決める） | — |

- 複数置く・除く・件数・保存した検索・履歴は、今の決まりにそのまま乗る。API の条件の種類 `extension` も同じ判定（Core の `SearchModuleConditions`）を使う。
- 宣言に足す物：
  - **選択肢の型**：値と表示名の並びを宣言する（決まっていれば件数を数えて候補から積める）
  - 数の型に `unit`・`min`・`max`（単位と範囲の目安。スライダの端と表示に使う）
  - 数の型の**目盛り**（ユーザ指示 2026-11-27「スライダーモジュールの目盛りに対数など、想定される用途がある形式を追加」）。どれも今の検索のスライダが持つ配り方で、新しい配り方は作らない（[search-filters.md](search-filters.md)「見た目」）：

    | 宣言 | 配り方 | 想定する用途 | 今の同じ条件 |
    |---|---|---|---|
    | `scale: "linear"`（既定） | 直線 | 0〜100 の評価・割合・狭い範囲の数 | 属性 |
    | `scale: "log"` | 0 からの対数 | ポリゴン数・マテリアル数・ファイルの大きさなど桁が広い物。小さい数にも意味がある物 | スキ数 |
    | `scale: "log"` ＋ `foldBelow: n` | n までを左端の1目盛（10%）に直線で畳み、その上を対数 | 下の帯に値が詰まらない物（値段のように、n 未満がほぼ無い） | 価格（100円） |
    | `ignoreOutliers: true` | 「外れ値を無視」を出す（既定で入。95%の位置の5倍以上を外れ値） | 1件だけ桁違いに大きい値がある物 | 価格 |
    | `step: n` | 刻み（既定は整数なら1。小数を持つ欄は 0.1 など） | 小数を持つ欄 | — |

    `log` は負の値を持つ欄には使えない（宣言で断る 400 `invalidScale`）。分布の帯は目盛りと同じ配り方で数える（今と同じ）。
- 保存した検索・画面の状態には名前空間と欄の名前を持たせる。条件の種類は文字列（`SearchModuleState.Kind`）なので形式の版は上げない見込み。古い版がこの条件をどう扱うかは作る時に確かめる [要確認]。
- 欄やソフトが無くなった条件は当たらないとし、「この条件の欄はありません」と出す（[local-api-extensions-api.md](local-api-extensions-api.md)「付け先の変化・守り・ほかの口」）。

## 欄をまとめる（`group`）[決定]

ユーザの言葉（2026-11-27）：「このプラグインに想定するものの一つに、VN3利用規約の情報付与というものがあるとします。表で付与した場合、検索に利用可能でしょうか？…モジュールにはどう閉じ込められる？」→「Aのgroup案を採用。このまま進めましょう。」
項目の数が決まっている情報（利用規約の項目ごとの可否など）を、条件を項目の数だけ並べずに1つで絞れるようにする。

- 表では付けない：表の検索は後回しで、作っても「同じ行で項目が◯◯かつ可否が◯◯」と行の中を組み合わせて当てる仕組みが要る。表は行の数が商品ごとに変わる物（アバターごとの試着の結果）に使い、項目の決まった物は1項目1欄にする。
- 宣言の欄に `group`（表示名。例 `"group": "利用規約"`）を付けると、同じ group の欄を**条件の部品1つ**にまとめる。「＋ 条件を追加」には group が1つだけ並ぶ。
- まとめられるのは選択肢と真偽の欄だけ（行の形を揃えるため）。それ以外の型に `group` を付けた宣言は 400 `invalidGroup` で断る。group に入れる欄も `search: true` が要る。
- 部品の中は1欄1行で、選択肢の欄は「指定なし・各選択肢」、真偽の欄は「指定なし・はい・いいえ」を選ぶ。行どうしは AND。行ごとに、ほかの条件のもとでの件数を出す（「可 120・不可 30」）。
  「指定なし」の行は絞らない。値が無い商品を探すのは条件「編集状況」（下の節）。
- 部品の作りは Chmonos が決める（ソフトが部品を持ち込まない決まりのまま。group は並べ方を言うだけ）。
- 商品ページ・編集画面でも、group ごとに見出しを付けてまとめて出す。`editable` の欄も同じまとまりで出す（人が規約を読んで入れる形も取れる）。
- よく使う組み合わせ（例「配信で使える」）は、保存した検索にして条件「保存した検索」で使える（[search-saved.md](search-saved.md)）。
- 保存した検索・画面の状態には、名前空間・group と、行ごとの欄の名前と選んだ値を持つ。欄が無くなった行は「この欄はありません」と出して絞らない。

## 条件「編集状況」に、人が直せる欄を足す [決定]

ユーザの言葉（2026-11-27）：「関連項目として、検索モジュールの未編集にプラグインによるeditable項目を追加する機能を提案する」→ 案に「A、おすすめでOK」。
人に入れてほしい欄（`editable`。[local-api-extensions.md](local-api-extensions.md)「画面」）の入れ忘れを、ほかの項目と同じく探せるようにする。

- 条件「編集状況」（[search-filters.md](search-filters.md)「編集状況」）の見る項目のトグルに、`editable` の欄だけを並べる（例「試着チェッカー：よく合う」）。ソフトが入れる欄は人の入れ忘れではないので並べない。既定では入れない。
- **メモリ**：`editable` の欄は、`search` が無くても「値がある商品」の集まり（商品 ID）だけを持つ。未入力かを見るのに値そのものは要らない（1欄につき集まり1つで、値を持つより十分小さい）。
- 未入力：値が無い・空の一覧（ユーザータグが0件と同じ）。真偽の「いいえ」と数の 0 は入力済み（人が選んだ値）。宣言から外して隠した値は無い物と数える。
- 項目の横の未入力の数は、今の項目と同じく出す。カードの札「未編集」・ナビの「未編集」・編集画面の順番は今のまま（ユーザータグだけ）。
- 欄やソフトが無くなった項目は薄くし「この欄はありません」と出して数えない（残りの項目だけで判定）。全部の項目が無くなったら当たらない条件にする。
- 持ち方：今の `fields` に `ext:<名前空間>/<欄>` の形で足す。古い版（v1.2.0）が知らない項目の名前をどう読むかは作る時に確かめ [要確認]、条件ごと消えるなら別の欄に分ける。
- 作る時期：拡張データの検索の条件の段で一緒に作る。

## 仕様として出来ない事 [決定]

ユーザ判断 2026-11-27「それらのできないことは仕様とします」。

- **ソフトがその場で当たり外れを返す条件**（例：「今の Unity プロジェクトに合う物」をソフトに聞く）。件数は打つたびに全部の商品で数え直すので、毎回聞くと遅く、ソフトが止まると検索が止まる。Chmonos から外へつながない決まり（[plugins.md](plugins.md)）とも合わない。
  代わりに、ソフトが前もって計算して欄に書けば条件にできる（例：真偽の欄「今のプロジェクトに合う」）。
- **ソフトが条件の部品（見た目・照らし方）を持ち込む**：部品は Chmonos が型から決める。
- `search` を付けていない欄での検索・件数。
- 表の欄での検索（後回し）。
