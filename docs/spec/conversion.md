## 言葉（画面）

- **変換**：衣装の変換ツールで、別のアバター向けの衣装を合わせること。画面の語は「変換」（ユーザ判断 2026-11-06）。「変換経由」「変換で使える物も含める」。`ui-terms.md` に足す
- **プロファイル**：変換に要る、アバター（または共通素体）ごとのデータ。画面でも「プロファイル」と書く（ユーザ 2026-11-06「一般的にはプロファイルとされている」）
- **順方向・逆方向**：ツールの語のまま。順方向＝ほかのアバターの衣装を、そのアバターに合わせる。逆方向＝そのアバターの衣装を、ほかのアバターに合わせる
- **変換扱い**：その商品をプロファイルとして扱うか。「アバター扱い」（アバターかどうか）と**独立に**決める（ユーザ 2026-11-06）

## 使える、と見なす決まり

衣装の対応 S＝直接対応＋素体経由（今の相性の 1＋2。`avatar-bases.md`）。アバター B が**変換経由**で使えるのは、

- S のどれか A について「A か A の素体に**逆方向**のプロファイル」があり、かつ
- 「B か B の素体に**順方向**のプロファイル」があるとき（作者の使い方ガイド「衣装元のプロファイルは逆方向、変換先のプロファイルは順方向」）

［決定］素体経由は元の側に1回まで（ユーザ判断「基本は b」）。変換は1回まで。
［決定］**広げる範囲は、プロファイルのつなぎ先で決まる**（外からの点検で、2行が食い違って読めると言われて書き直した・ユーザ判断 2026-11-06）：つなぎ先を**共通素体**にしたプロファイルは、その素体を使うアバター全員に効く（ユーザ「素体が同じであれば動くことがほとんど」。別のショップのアバターでも）。つなぎ先を**アバター**にしたプロファイルは、そのアバターにだけ効き、そのアバターの素体の仲間には広げない。+Head のように同じプロファイルを FBX の場所だけ変えてアバターごとに配っている物は、変換扱いで素体として決めてもらう。
［却下］共通素体のプロファイルを、仲間のアバター用に Chmonos が書き換えて作ること（2026-11-06 に案として出た）。ユーザ判断「ユーザが簡単に行えるものであることと、chmonosが干渉すべき範囲ではないと感じるので見送り」。Chmonos はプロファイルを読むだけで、作らない
素体用の逆方向で、その素体に対応する衣装を変換の元にできる [公式：配布者] 缶詰茶房「この逆変換プロファイルを用いることで「CUUNEbodyに対応の衣装」を、「順変換プロファイルの存在するほかのモデルさん向け」に変換することが出来ます。」（https://booth.pm/ja/items/7691574 ）・MDoll「【◆◆逆変換対応済アバター】の対応衣装を、別のアバター用に変換できます」（https://booth.pm/ja/items/7690877 。逆変換の対象に共通素体 [M] とそのアバター）。
［決定］相性は保存しない（今と同じく、その場で計算する）。

## データの形

- ［決定］**商品ごとの変換扱い**（`items/{id}.json` の `local.conversion`。人が決めた値）：
  - `mode`：`auto`（既定・書き出さない）／`profile`（プロファイルとして扱う）／`notProfile`（扱わない）
  - `targets[]`：つなぎ先1つ＝ `avatarItemId` か `baseName` のどちらか・`forward`・`reverse`・`slug`（中のプロファイルの名前。分かれば）・`confirmed`（人が決めたか）
  - 自動で推した値は `confirmed: false` で持ち、変換経由の計算には**確認したものだけ**を使う（推定を勝手に入れない）。確認待ちも含める設定を置き、既定はオフ（ユーザ判断 2026-11-06「基本不要」）
- **unitypackage の控えに足す**（`unitypackages/{zipのハッシュ}.json`。中身から決まるので古くならない）：
  プロファイルの `avatar_data_{slug}.json` から読んだ `slug`・`name`・`defaultFBXPath`。読むのは取り込みのときで、zip が手元にある物だけ
  （今の `UnityPackageInspector` は 2MB までの `.json` を手掛かりに読んでいるが、残していない）

## 判定（自動で推す所）

［決定］**対象は、プロファイルのファイルを持っている物だけ**（ユーザ判断 2026-11-06：「手元にプロファイルが無いと意味を成さない」。持っていない物は「このプロファイルを買えばよいのでは」程度のことしか言えず、それはコミュニティの一覧の方が確か）。
「持っている」は unitypackage の控えがあること（zip を後で動かした・消した物も、控えがあれば数える。今の `UnityPackageReads.StoredIfGone` と同じ）。BOOTH のタグ・商品名だけでの判定はしない。

**1. プロファイルか**
- unitypackage の控えに `Assets/OutfitRetargetingSystem/Editor/` の下の `config_template2{slug}.json` か `config_{slug}2template.json` がある（18 商品とも当たった）
- **1つの商品が複数のプロファイルを含む**ことがある（663 系は slug 18 個・ツールの本体は4体分）。つなぎ先と向きは slug ごとに持つ
- ツールの本体もプロファイルの商品として扱う（ユーザ判断 2026-11-06）

**2. 向き**（slug ごと）
- `config_template2{slug}.json` → 順、`config_{slug}2template.json` → 逆、両方 → 両方向（`posediff_*` は使わない。逆方向のみの物にも入っていた）

**3. つなぎ先**：［決定］**下の手掛かりを全部集め、食い違わなければ自動で推し、食い違えば聞く**（ユーザ指摘 2026-11-06：「当たったところで完全に止めるのは危険」。アバター本体の商品が、ほかのアバターや素体のプロファイルを同梱することもあり得る）
- 判定のパス・ファイル名の決まり（`OutfitRetargetingSystem/Editor/`・`config_*2*`）は1か所にまとめ、プロファイルらしい物の件数が前より急に減ったら知らせる（道具の更新で名前が変わると黙って0件になるため。外からの点検）
- (a) 商品のカテゴリが「3Dキャラクター」→ その商品自身
- (b) `defaultFBXPath` が、持っているアバターの unitypackage のパスと一致 → そのアバター
- (c) 商品から検出された対応の共通素体 → その素体
- (d) 商品から検出された対応アバター：1体ならそのアバター（ただし (d) だけで決まった物は確認待ちにし、当たり方を別に数える。プロファイルの商品ページの「対応」欄は配る人が自由に書くので、変換の元にできる衣装のアバターを並べている物もあり得る。ユーザ 2026-11-06「コミュニティで自由に出せるものなので保証はできない」）。2体以上なら slug と名前を照らして絞る（かなをローマ字にした形・英字の名前・呼び方。大文字小文字と空白は無視）。購入の記録のバリエーション（`purchases[].variationId`。人が入れた物）があれば、そのバリエーションの名前でも絞る（ユーザ判断 2026-11-06）。
  **今は、対応アバターとバリエーションの結び付きを持っていない**：バリエーション名から検出した対応は `AvatarLink.Source = Variation` と印が付くだけで、どのバリエーションかは残していない。購入の記録で絞るなら、検出のときにバリエーションの ID を `AvatarLink` に足す（BOOTH の内容から決まる値で、検出し直せば入る）
- (e) slug・`name` が共通素体の名前か別名と一致 → その素体。一覧に無ければ「共通素体「〇〇」を足してつなぎますか」と聞く
- **素体用か**：`defaultFBXPath` は代表のアバターの FBX でしかない（ユーザ 2026-11-06「それは baseAvatar のパスのせい」）。まめふれんずは「Base Avatar FBX にお手持ちのまめふれんず素体 fbx を設定」（商品の説明）、+Head は同じ slug `plushead` のプロファイルを、FBX の場所だけ違えてアバター3体分に分けて配っている。
  なので (b) で当たったアバターが共通素体に入っていて、(c)(e) が同じ素体を指すか、slug がアバター名でなく素体の名前なら、素体用として推す。同じ slug が FBX だけ違えて複数あるのも素体用の印
- どれも当たらない → 人が選ぶ

18 商品での見込み：自動で正しく当たる 11・聞く 1・広げすぎる 2（4. でバリエーションごとに対象を分ける商品）・人が選ぶ 4。

## バリエーションとアバターの結び付き（ユーザ案 2026-11-06）

ユーザ：「バリエーション登録のタイミングでどのアバターに対応したバリエーションかどうかを書き込める仕組みを用意した場合にはこの問題は全て解決可能ですよね？…そのバリエーションに一致する可能性が高いアバターと共通素体をサジェストする形でしょう。」

- ［決定］**書く所**：編集の画面の「購入したバリエーション」（今と同じ所）と、変換扱いの画面の2か所（ユーザ判断 2026-11-06）。**付けられるのは BOOTH のバリエーション全部の行**（向き先は商品の事実で、買ったかとは別。買っていない分の向き先が無いと「持っていない分」を見分けられない）。ただし買っていない行では効き目が無いので目立たせない（ユーザ判断 2026-11-07）。**買っていない行の欄は既定で隠す**（場所は残し、買った印を付けても下の行が縦にずれない。設定「買っていないバリエーションにも対応の欄を表示する」で見せる・ユーザ指示 2026-11-07）。
  ［決定］隠した行は欄の部品を組まず、場所も取らない（大量に並ぶ欄なので、畳みを開いたときのスクロール量を増やさない。印を付けて欄が出るときに下の行がずれるのは受け入れる・ユーザ判断 2026-11-07）。
  出す行も、開いたときは上の8行だけ組み、残りは手が空いたときに4行ずつ上から組む（全部まとめて組むと、バリエーション52行の商品で編集画面を開くのが約0.35秒延びた。実測 2026-11-07）
- ［決定］**形**：人が決めた値は `local.variationTargets`、検出した値は `local.detectedVariationTargets`（検出が書き、再検出で作り直す）。1行は `variationId`・`avatars`（アバターの商品 ID）・`bases`（共通素体の名前）・`all`（その商品の対応アバター全部向け。セット売りの行など）。`variationId` が null の行は「バリエーションを選ばない購入」の分で、人が決めた行だけが持つ（ユーザ指摘 2026-11-07）。人が外した、名前から見つけた向き先は `rejectedAvatars`・`rejectedBases`（無ければ書かない）。外しただけの行も人が決めた行で、検出の行に勝つ（ユーザ指摘 2026-11-07：外した候補がまた出ていた）。共通素体ごとにも、全部にも付けられる（ユーザ判断 2026-11-07）。`AvatarLink` にバリエーションを足す形はやめた（検出の `Add` は同じアバターを最初の出どころで止めるので、対応アバター節にも出るアバターのバリエーションが落ちる）
- ［決定］**検出**：バリエーションが2つ以上ある商品で、バリエーションの名前ごとに今の照らし（アバター名・共通素体の名前）を当てる。アバター名も素体の名前も無く、「フルセット」「Fullset」「Full pack」「フルパック」「全セット」「全部入り」「全部まとめ」「全アバター」、英字の単語の「all」を含む行は、対応アバター全部向け（`all`）にする（ユーザ指示 2026-11-07。友人の写しの名前 1,944 個で測り、「セット」だけは衣装の組み合わせの意味が多いので入れない。当たるのは 135 行・122 件）。**1つの名前に複数のアバター**（「〇〇・△△対応」「A / B」）も全部拾う（2人目の友人の写し 1,414 行で 59 行。前は区切りの「・」で落ちて 48 行だった）。拾えないのは、英字のつづりが登録簿の呼び方に無いアバターだけで、アバターの画面で呼び方を足せば拾える。購入の記録にしか名前が残っていない（BOOTH から消えた）バリエーションも、記録の名前で当てる
- ［決定］**人が決めた方を優先**（ユーザ判断 2026-11-06）：同じバリエーションに両方あれば人が決めた方を使い、検出の方は編集の画面で候補として出すだけ。**見分けに検出の値も使う**。設定で「人が入れた物だけ」にもできる（ユーザ判断 2026-11-07）
- ［決定］**持っているバリエーション**：購入の記録のバリエーション（「贈った」は除く）と、手元のファイルに付けたバリエーション（外したファイルは除く）。バリエーションを選ばない購入は、人が向き先を付けたときだけ数える
- ［決定］**持っていない分の見分け**：対応アバターのうち、どれかのバリエーションの向き先に入っていて、持っているバリエーションの向き先のどれにも入っていない物。向き先は素体経由と同じに広げる（アバターはその素体の仲間へ、共通素体はその仲間全員へ）。
  持っているバリエーションが分からないとき、または**持っているバリエーションのどれかに向き先が無いとき**（「本体」のように名前にアバターの無い行）は、何も見分けない（何を持っているか言えないので、薄くしすぎない側に倒す）
- **候補**（押したときだけ入れる）：(1) バリエーション名で引いたアバター・共通素体（今の検出の照らしを、バリエーションごとに返す。友人の写しで、当たるバリエーションの 87〜93% が1体に決まり、読んだ 20 のうち 18 が正しかった。`docs/research/mochifitter.md`）、(2) 中のプロファイルの slug・FBX と同じ決め方（上の「つなぎ先」）
- **持っているバリエーションの候補**（BOOTH の `downloadable` は、ふつうの取り直しで入るのを待つ。一斉には取り直さない・ユーザ判断 2026-11-07）：無料の商品は、BOOTH の JSON の `variations[].downloadable` のファイル ID と、ダウンロード元の記録のファイル ID が一致すれば、そのバリエーション（一意に決まる）。有料はファイル名とバリエーション名の照らし
- **使い道**：変換扱いのつなぎ先を、持っているバリエーションの分だけに絞る（広げすぎる2件の直し）。**衣装にも使う（v1.3.0 に入れる・ユーザ判断 2026-11-06）**：バリエーションでアバターごとに分けて売っている衣装で、持っているバリエーションが分かれば、対応アバターのうち持っている分を見分ける（検索の対応アバターの条件・商品ページの札）。見せ方は作るときに決める
- **今の使われ方**：友人の2つの写し（989 件）で、購入の記録にバリエーションが入っているのは1件だけ [実測]。人が自分から入れることは少ないので、変換扱いの画面の流れの中でも「どのバリエーションを持っていますか」を候補付きで聞く

## 画面

**商品ページ**（「アバター扱い」の欄の隣か下）
- 「変換扱い」：今の扱いを文で（「プロファイル（自動の判定）：まめふれんず（共通素体）・順方向」）。繋がったボタン「自動の判定に任せる」「プロファイルとして扱う」「プロファイルとして扱わない」（「アバターかどうか」と同じ形）
- つなぎ先の行：アバターか素体・向き（順・逆・両方を選べる）・中のプロファイルの名前・確認待ちの印と ✓。足す欄（アバターか共通素体の候補）と × で外す
- **衣装の商品ページの「変換経由」段**（段の名前は「変換経由」・ユーザ判断 2026-11-06。「使える」は約束しすぎ）（ユーザ案 2026-11-06：共通素体の札の段と同じように別の段を作り、持っているプロファイルから広がるアバターを並べる）：対応アバターの欄の、共通素体の段の下に置く。
  並べるのは、変換経由で使えて、**直接対応・素体経由で既に並んでいないアバター**（計算で除く。保存した値に頼らない）。吹き出しは「「A」の逆方向と、このアバターの順方向のプロファイルで、変換できる見込みです」の形（言い方は作るときに直す）。元になれる A が何体もあるときは1体を出し「ほか n 通り」

**変換扱いの画面**（ユーザ案「未確定のような形で「変換扱い」をリストで積んで順々に設定する」）
- 置き場：アバターの管理の左の切り替え（アバター／共通素体）に「変換」を足す（ユーザ判断 2026-11-06）
- 左：プロファイルらしい商品の一覧（決めていない物が上・件数）。右：分かっていること（カテゴリ・中のプロファイルと向き・FBX の場所）・推したつなぎ先と理由（「商品の対応素体から」など）・ボタン「これで決める」「プロファイルではない」「後で」

- **「推した通りにまとめて決める（n 件）」**（外からの点検「確認したものだけを使うので、最初は何も出ない」・ユーザ判断 2026-11-06）：手掛かりが全部一致した物だけが対象。押す前に対象の一覧を見せ、外したい物は外せる。押すのは人なので、推定を勝手に入れない決まりは守る

**検索**：対応アバターの条件に「変換で使える物も含める」（「素体経由の対応も含める」の隣）。**既定は切**（ユーザ判断 2026-11-06。入にすると更新しただけで今の絞り込みの結果が増える）。表示の設定とは別に決める
**設定**：「変換経由の対応アバターも表示する」（既定は入）と「確認していない変換も含める」（既定は切。ユーザ判断 2026-11-06）。素体経由と同じ作り
