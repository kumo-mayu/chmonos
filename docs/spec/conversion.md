## 言葉（画面）

- **変換**：衣装の変換ツールで、別のアバター向けの衣装を合わせること。画面の語は「変換」（ユーザ判断 2026-11-06）。「変換経由」「変換で使える物も含める」。`ui-terms.md` に足す
- **プロファイル**：変換に要る、アバター（または共通素体）ごとのデータ。画面でも「プロファイル」と書く（ユーザ 2026-11-06「一般的にはプロファイルとされている」）
- **順方向・逆方向**：ツールの語のまま。順方向＝ほかのアバターの衣装を、そのアバターに合わせる。逆方向＝そのアバターの衣装を、ほかのアバターに合わせる
- **変換扱い**：その商品をプロファイルとして扱うか。「アバター扱い」（アバターかどうか）と**独立に**決める（ユーザ 2026-11-06）

## 使える、と見なす決まり

衣装の対応 S＝直接対応＋素体経由（今の相性の 1＋2。`avatar-bases.md`）。アバター B が**変換経由**で使えるのは、

- S のどれか A について「A か A の素体に**逆方向**のプロファイル」があり、かつ
- 「B か B の素体に**順方向**のプロファイル」があるとき（作者の使い方ガイド「衣装元のプロファイルは逆方向、変換先のプロファイルは順方向」）

［決定］素体経由は元の側に1回まで（ユーザ判断「基本は b」）。変換は1回まで。
［決定］**広げる範囲は、プロファイルのつなぎ先で決まる**（外からの点検で、2行が食い違って読めると言われて書き直した・ユーザ判断 2026-11-06）：つなぎ先を**共通素体**にしたプロファイルは、その素体を使うアバター全員に効く（ユーザ「素体が同じであれば動くことがほとんど」。別のショップのアバターでも）。つなぎ先を**アバター**にしたプロファイルは、そのアバターにだけ効き、そのアバターの素体の仲間には広げない。+Head のように同じプロファイルを FBX の場所だけ変えてアバターごとに配っている物は、変換扱いで素体として決めてもらう。
［却下］共通素体のプロファイルを、仲間のアバター用に Chmonos が書き換えて作ること（2026-11-06 に案として出た）。ユーザ判断「ユーザが簡単に行えるものであることと、chmonosが干渉すべき範囲ではないと感じるので見送り」。Chmonos はプロファイルを読むだけで、作らない
素体用の逆方向で、その素体に対応する衣装を変換の元にできる [公式：配布者] 缶詰茶房「この逆変換プロファイルを用いることで「CUUNEbodyに対応の衣装」を、「順変換プロファイルの存在するほかのモデルさん向け」に変換することが出来ます。」（https://booth.pm/ja/items/7691574 ）・MDoll「【◆◆逆変換対応済アバター】の対応衣装を、別のアバター用に変換できます」（https://booth.pm/ja/items/7690877 。逆変換の対象に共通素体 [M] とそのアバター）。
［決定］相性は保存しない（今と同じく、その場で計算する）。

## データの形

- ［決定］**商品ごとの変換扱い**（`items/{id}.json` の `local.conversion`。人が決めた値）：
  - `mode`：`auto`（既定・書き出さない）／`profile`（プロファイルとして扱う）／`notProfile`（扱わない）
  - `targets[]`：つなぎ先1つ＝ `avatarItemId` か `baseName` のどちらか・`forward`・`reverse`・`slug`（中のプロファイルの名前。分かれば）・`confirmed`（人が決めたか）・`rejected`（［決定］人が外した。行は残し、見回りは同じつなぎ先を推さない。変換経由に使わない。無ければ書かない・ユーザ判断 2026-11-09「ユーザが外したんですから次からも外れているべき」）
  - ［決定］**統合で重なった行**（素体の統合・商品 ID のまとめで、つなぎ先と `slug` が同じ行が2つ以上になったとき。Codex の点検 2026-11-13 件1）：選んだ行（確認済みで外していない）＞外した行＞推した行（確認待ち）の順で1行を残す。同じ順位なら統合先（まとめでは移した先）の行。向きが食い違っても足し合わせず、残した行の向きのまま。置く位置は重なった行の一番前（`ConversionTarget.Fold`）。前は配列の先頭を残し、「A を外す→B を選ぶ→A を B へ統合」で選んだ B が消えて外した印が残った
  - 自動で推した値は `confirmed: false` で持ち、変換経由の計算には**確認したものだけ**を使う（推定を勝手に入れない）。確認待ちも含める設定を置き、既定はオフ（ユーザ判断 2026-11-06「基本不要」）
- **unitypackage の控えに足す**（`unitypackages/{zipのハッシュ}.json`。中身から決まるので古くならない）：
  プロファイルの `avatar_data_{slug}.json` から読んだ `slug`・`name`・`defaultFBXPath`。読むのは取り込みのときで、zip が手元にある物だけ
  （今の `UnityPackageInspector` は 2MB までの `.json` を手掛かりに読んでいるが、残していない）
  ［実装 2026-11-09］控えの `profiles` 欄（slug → `name`・`defaultFbxPath`）。見回り（`ConversionScan`）が、プロファイルを含む zip で欄がまだ無い物だけ、zip を開いて `avatar_data_*.json` を読む（`ProfileDataReader`。控えで GUID が分かるので tar を1周するだけ）。取り込みの終わりと起動時の見回りで読むので、前の版で取り込んだ物にも1回だけ入る。読んで何も無ければ空を控えてもう読まない。中身の一覧を書き直しても欄は残す

## 人が足す組（ユーザ判断 2026-11-20・avatar2avatar）

プロファイルの商品が無い・プロファイルを使わないツールでも変換できる組を、人が自分で書く。
- ［実装・段1 2026-11-20］**`conversion-pairs.json`**（保存先の直下・`{ "formatVersion", "pairs": [...] }`）。1件＝ `from`・`to`（どちらも `avatarItemId` か `baseName` のどちらか）・`tool`（使うツールの名前・任意）・`memo`（任意・画面で書く。無い前の形のファイルも読める。未配布なので形式の版は上げない）。並びは足した順（画面の並び「追加が新しい順・古い順」はこの位置を使う）。欠けた配列・端（`null`）は空として読み、端が空の組は計算に使わない。同じ `from`・`to` の組は重ねない（ツールとメモが違っても）。元と先が同じ組は持たない
- ［決定］**向きは元→先の1方向**（`from` に対応する衣装を `to` に着せられる）。**「逆も」の口は作らない**（逆はもう1つの組として足す・ユーザ判断 2026-11-20）
- ［決定］人が書いた物なので**確認は要らない**（確認待ちの設定に関係なく使う）
- 計算（`ConversionIndex`）：プロファイルの道筋 ∪ 組の道筋。組の道筋は、S（直接対応＋素体経由）のどれか A が `from` に当たる（アバターならそのアバター、素体なら S の中でその素体のアバター）とき、`to`（アバターならそのアバター、素体なら仲間全員）を並べる。S に既に居るアバターは除く。素体経由は元の側に1回まで、**変換は1回まで**（組から組・組からプロファイルへはつながない）。組はプロファイルの「逆方向のどれか×順方向のどれか」の集合に混ぜない（混ぜると A→B の組が A→順方向の全員に化ける）。プロファイルが1つも無くても組だけで出る
- 道筋（`ConversionRoute.Pair`）は、組から来たならその組を持つ（商品ページの「変換経由」の吹き出しで、組からかプロファイルからかを言うため）。**両方から届くアバターはプロファイルの道筋を言う**（組を足す前からの言い方を変えない）
- 書くのは `UiCommand.ChangeConversionPairs`（`ConversionPairs.Add`／`Remove`／`SetMemo` を錠の中で今の値に当てる）。**読み替え**：商品 ID の変更・まとめ（`ItemIdChanger`）と素体の改名・統合・削除（`AvatarService`）で端を追う。削除した素体を指す組・読み替えで元と先が同じになった組・重なった組は落とす。API の写しは `StorePart.ConversionPairs` で読み直す
- 引越し・書き出しと「すべてを戻す」・形式を上げる前の控えには、保存先の直下の `*.json` として入る（試験 `ConversionPairTests`）
- ［実装・段3 2026-11-20］**編集は「変換」の側**（ユーザ判断 2026-11-20。段2 ではアバターの詳細にあり、元がいつもそのアバターで共通素体を元にできなかった）。アバターの管理の「変換」の一覧の上に畳める節「追加した組（n）」（`ConversionPairEditor`）。［実装・段9 2026-11-20］探す欄より下は1つの流れ：節はプロファイルの商品の一覧（`ConversionList`）の先頭の1行（群）で、節も組の一覧も自分では流さない（前は組の一覧が高さ260で中で流れ、ホイールが中で止まった）。商品の行は見える分だけ作り、画素で流す。［実装・段11 2026-11-20・ユーザ判断「組は大きくなる箇所なので b で」］節の中身は見出し・組を追加する欄・並び・当てはまる組が無い時の1行だけで、**組のまとまりの見出しと組の行は節の後ろに、同じ一覧の行として平らに並べる**（節を開いている時だけ。組の欄の出し入れを差分で写す）。組の行も見える分だけ作る（組400個で開く 1〜2.4秒 → 0.12秒）。商品が1件も見えない時の空表示は、組の行の後ろの1行（`ConversionListEnd`）。左の一覧の選びは組の行か商品の行のどちらか1つ（`SelectedConversionEntry`。一覧が書き戻す null は受けない）。
  ［実装 2026-11-20・ユーザ判断「普通のプロファイルと同じような行にして、右側ビューで見れるように」］行は**プロファイルの商品と同じ形**（選ぶ一覧・同じ字と間）で「元 → 先」と、メモがあれば1行目。↑↓ で選び、Tab で右の欄へ移る。選ぶと右に組の中身：「元」「先」（押すとそのアバターをアバターの見方で・共通素体を共通素体の見方で選ぶ。移る前の「変換」を履歴に積み、戻ると同じ組を選ぶ。登録簿に無いアバター・一覧に無い素体は押せない。［実装 2026-11-20・ユーザ判断「共通素体から共通素体のページに飛べた方が良い」］左の組の行の右クリック「元を開く」「先を開く」と、元のまとまりの見出しの右クリック「開く」も同じ移り方。行を押すと組を選び、見出しを押すと畳むので、移る口は右クリック。見出しの「開く」は選びを替えないので、戻る先は選んでいた組か商品）・ツールの名前（ある時だけ）・メモ（押さずに残る。0.8 秒の待ちで書き、行は作り直さない。**選び直す・足す・外す・読み直す・「変換」を離れる前に待ちを書き切る**。待ちは1つしか持てない）・「この組を外す」（外したら同じ位置の次の組、最後なら前の組を選ぶ。組が尽きたら決めていない商品へ）。
  右はプロファイルの商品と組の**どちらか1つ**：組を選ぶと商品の選びを外し、商品を選ぶと組の選びを外す。組を選んでいる間は、一覧の作り直し（登録簿の読み直し・戻る）で決めていない商品へ選びを移さない。
  ［実装 2026-11-20・ユーザ判断①〜④］**行の形**：「組を追加」の欄は組の一覧の**上**（下だと組が増えるたびに押し下げられた）。行は元と先の頭の絵（アバターは「アバター」の見方の行と同じ読み方・同じ控え。共通素体は素体の行と同じ。絵が無ければ素体の一覧の行と同じ頭の字の升。場所は見えた行で初めて探す。乗せると大きな絵を出し、大きな絵は乗せた時に読む・ユーザ判断①）と「元 → 先」・メモの1行目。
  組は**いつも元でまとめ**、元の絵・名前・組の数の見出しで畳める（`ConversionPairGroup`）。見出しは**畳むだけで選ぶ行にしない**（右に出す物は商品か組の1つで、まとまりには中身が無い）。キーは ↑↓・Home・End・PageUp・PageDown で組の見出し・組の行・プロファイルの商品の行を1つの並びとして渡り（行なら選ぶ・端で止まる。段11 から組と商品の間も渡る。商品の行の間は一覧の既定のまま）、見出しで Enter・Space は開閉、← で畳み → で開く（`AvatarsView.ConversionList_PreviewKeyDown`・`AvatarsViewModel.ConversionEntryTarget`）。
  並びは「元の名前順」（既定）・「元の名前の逆順」・「追加が新しい順」・「追加が古い順」。名前の順は、まとまりの中が先の名前順（逆順でも中は先の名前順のまま）。追加した順は**配列の位置**を使い（足すと末尾・外す・メモ・読み替えでは順を保つ。時刻は持たない）、まとまりは中のいちばん新しい組の順、中も同じ向き（古い順は新しい順のちょうど逆）。
  並びと畳んだまとまりは `ui-state.json` の `conversionPairSort`・`conversionPairCollapsed`（元の端。アバターは ID・素体は名前で、同じ名前のアバターと素体を分ける。素体の改名・ID の変更では追わず、そのまとまりは開いた姿に戻る）。**選んだ組のまとまりは開いて覚える**（足した・既にある組へ移った・外した後の次の組・戻るで選び直した組）。選んだ組のまとまりを畳んでも組の選びは残る（一覧の出し入れの間の ListBox の書き戻しは受けない）。外した後の次の組は今の並びの順で引く。
  「組を追加」の行で、元と先の両方を候補付きの欄（アバターと共通素体。変換扱いのつなぎ先の欄と同じ群・絵。候補の絵に乗せると大きな絵・ユーザ判断①）で選び、**「追加」（欄の Enter も同じ）を押した時だけ足す**（2026-11-20。前は先の候補を決めた瞬間に足していた。候補が出ている間の Enter は候補を決めるだけ）。足したら足した組を選んで右に出し（同じ画面の共通素体の「追加」と同じ）、先だけ空にする（同じ元から続けて足せる）。既にある組は、断ってその組を選ぶ。
  足さない時は欄の下で言う：候補に無い→「候補からアバターか共通素体を選んでください。」、同じ物同士→「元と先に同じ物は選べません。」、同じ組→「「元 → 先」は既にあります。」（Core も錠の中で同じ物を黙って足さない）。足した・外したら検索を絞り直す。「変換」に入る時と登録簿を読み直した時に組を読み直す（素体の改名・削除と ID の変更でも書き換わる）
  ［実装 2026-11-20・ユーザ「元と先、両方を指定できる形の文字列(他のアバター検索UIと同じ形)検索」］**組を探す欄**は「変換」の見方のいちばん上（切り替えの下）。欄の形・案内「名前・ID・呼び方で探す」は「アバター」の見方の探す欄と同じで、アバターの端は同じ照らし（`AvatarSearch`：名前・商品ID・BOOTHでの正式名・呼び方）、共通素体の端は素体の名前（添える「（共通素体）」では当てない）。下のつながったボタン「両方」「元」「先」で当てる端を選ぶ（既定は両方・覚えない）。［実装 2026-11-20・ユーザ判断②］語と探す所は、下のプロファイルの商品の一覧にも当てる（`ConversionItemSearch`）。商品のつなぎ先は向きで振り分ける：逆方向は元・順方向は先（検索の条件「プロファイル」の変換元・変換先と同じ）、両方向と向きの分からない物は両方。外したつなぎ先は当てない。商品名・商品IDは元でも先でもないので「両方」の時だけ当てる。絞っている間の群の見出しは「決めていない（1/3）」（当たった数/全部。当たらない群は出さない）、0件は「打ち込んだ言葉に当てはまる商品がありません。」と「絞り込みを消す」。選んだ商品は絞りで隠れても選んだまま（右に出し続ける）。「後で」・次へは見えている行の中で回る。
  絞っている間：見出し「追加した組（当たった数/全部）」とまとまりの数は当たった数。当たる組の無いまとまりは見出しごと出さない。当たったまとまりは**畳んでいても開いて見せるが、畳んだ事の記録（`conversionPairCollapsed`）は書き換えない**（絞りの間に替えた開閉も覚えず、語を消すと覚えた姿に戻る。語を替えるたびに開いた姿から）。節を畳んでいれば節は開く（節の開閉は覚えない値）。当たる組が無ければ「打ち込んだ言葉に当てはまる組がありません。」と「絞り込みを消す」。
  選びは絞りで外さない（当たらない組を選んだままなら、右に出したまま一覧には出さない。右を商品へ移さない）。**足した組・既にある組・戻るで選び直した組が当たらない時は、絞りを外して見せる**（「アバター」の見方で絞りで外れたアバターへ移る時と同じ）。外した後の次の組は、見えている組の中で引く。絞りの間に選んだ組が、覚えた姿で畳んだまとまりにあれば、語を消した時に開いて覚える（選んだ組のまとまりは開いて覚える決まり）。
  右の組の欄の「元」「先」の名前の前に、左の行と同じ絵（同じ `ConversionEndIcon`・同じ升。絵は押す所に入れない）
- アバターの詳細は**読むだけ**：「変換の組」に、そのアバターが元か先にある組を「元 → 先」の札で並べ（メモは吹き出し）、「変換で編集」で「変換」へ移る（`ConversionPairSummary`）。そのアバターの共通素体が端の組は出さない。商品ページの「変換経由」の札の吹き出しは、組から来た物を「「A」用を、追加した組で変換できる見込みです。」と言う。**商品ページに常に置く変換扱いの入口は作らない**（ユーザ判断 2026-11-20）。ツールの名前を画面で書く口はまだ無い

## 判定（自動で推す所）

［決定］**対象は、プロファイルのファイルを持っている物だけ**（ユーザ判断 2026-11-06：「手元にプロファイルが無いと意味を成さない」。持っていない物は「このプロファイルを買えばよいのでは」程度のことしか言えず、それはコミュニティの一覧の方が確か）。
「持っている」は unitypackage の控えがあること（zip を後で動かした・消した物も、控えがあれば数える。今の `UnityPackageReads.StoredIfGone` と同じ）。BOOTH のタグ・商品名だけでの判定はしない。

**1. プロファイルか**
- unitypackage の控えに `Assets/OutfitRetargetingSystem/Editor/` の下の `config_template2{slug}.json` か `config_{slug}2template.json` がある（18 商品とも当たった）
- **1つの商品が複数のプロファイルを含む**ことがある（663 系は slug 18 個・ツールの本体は4体分）。つなぎ先と向きは slug ごとに持つ
- ツールの本体もプロファイルの商品として扱う（ユーザ判断 2026-11-06）

**2. 向き**（slug ごと）
- `config_template2{slug}.json` → 順、`config_{slug}2template.json` → 逆、両方 → 両方向（`posediff_*` は使わない。逆方向のみの物にも入っていた）

**3. つなぎ先**：［決定］**下の手掛かりを全部集め、食い違わなければ自動で推し、食い違えば聞く**（ユーザ指摘 2026-11-06：「当たったところで完全に止めるのは危険」。アバター本体の商品が、ほかのアバターや素体のプロファイルを同梱することもあり得る）
- 判定のパス・ファイル名の決まり（`OutfitRetargetingSystem/Editor/`・`config_*2*`）は1か所にまとめ、プロファイルらしい物の件数が前より急に減ったら知らせる（道具の更新で名前が変わると黙って0件になるため。外からの点検）
- (a) 商品のカテゴリが「3Dキャラクター」→ その商品自身
- (b) `defaultFBXPath` が、持っているアバターの unitypackage のパスと一致 → そのアバター［実装 2026-11-09］`ConversionScan.FbxIndex`（持っているアバターの中身の控えの .fbx）と `FbxAvatarsOf`。手掛かりの種類は `FbxAvatar`、見つけた理由は「FBX の場所が「A」と同じ」。控えから抜いた .fbx の場所は zip のハッシュごとに覚え、控えのファイルの更新時刻と大きさが変わるまで読み直さない（登録簿と商品のファイルは毎回歩き直す）。アバターの管理の「変換」は一覧を作る裏で先に読む（2026-11-13 の Codex の点検の件3：選ぶたびに画面のスレッドで全部のアバターの控えを読み、100体で100ms を超えていた）
- (c) 商品から検出された対応の共通素体 → その素体
- (d) 商品から検出された対応アバター：1体ならそのアバター（ただし (d) だけで決まった物は確認待ちにし、当たり方を別に数える。プロファイルの商品ページの「対応」欄は配る人が自由に書くので、変換の元にできる衣装のアバターを並べている物もあり得る。ユーザ 2026-11-06「コミュニティで自由に出せるものなので保証はできない」）。2体以上なら slug と名前を照らして絞る（かなをローマ字にした形・英字の名前・呼び方。大文字小文字と空白は無視）。購入の記録のバリエーション（`purchases[].variationId`。人が入れた物）があれば、そのバリエーションの名前でも絞る（ユーザ判断 2026-11-06）。
  **今は、対応アバターとバリエーションの結び付きを持っていない**：バリエーション名から検出した対応は `AvatarLink.Source = Variation` と印が付くだけで、どのバリエーションかは残していない。購入の記録で絞るなら、検出のときにバリエーションの ID を `AvatarLink` に足す（BOOTH の内容から決まる値で、検出し直せば入る）
- (e) slug・`name` が共通素体の名前か別名と一致 → その素体。一覧に無ければ「共通素体「〇〇」を足してつなぎますか」と聞く
- **素体用か**：`defaultFBXPath` は代表のアバターの FBX でしかない（ユーザ 2026-11-06「それは baseAvatar のパスのせい」）。まめふれんずは「Base Avatar FBX にお手持ちのまめふれんず素体 fbx を設定」（商品の説明）、+Head は同じ slug `plushead` のプロファイルを、FBX の場所だけ違えてアバター3体分に分けて配っている。
  なので (b) で当たったアバターが共通素体に入っていて、(c)(e) が同じ素体を指すか、slug がアバター名でなく素体の名前なら、素体用として推す。同じ slug が FBX だけ違えて複数あるのも素体用の印
- どれも当たらない → 人が選ぶ

18 商品での見込み：自動で正しく当たる 11・聞く 1・広げすぎる 2（4. でバリエーションごとに対象を分ける商品）・人が選ぶ 4。

## バリエーションとアバターの結び付き（ユーザ案 2026-11-06）

ユーザ：「バリエーション登録のタイミングでどのアバターに対応したバリエーションかどうかを書き込める仕組みを用意した場合にはこの問題は全て解決可能ですよね？…そのバリエーションに一致する可能性が高いアバターと共通素体をサジェストする形でしょう。」

- ［決定］**書く所**：編集の画面の「購入したバリエーション」（今と同じ所）と、変換扱いの画面の2か所（ユーザ判断 2026-11-06）。**付けられるのは BOOTH のバリエーション全部の行**（向き先は商品の事実で、買ったかとは別。買っていない分の向き先が無いと「持っていない分」を見分けられない）。ただし買っていない行では効き目が無いので目立たせない（ユーザ判断 2026-11-07）。**買っていない行の欄は既定で隠す**（場所は残し、買った印を付けても下の行が縦にずれない。設定「買っていないバリエーションにも対応の欄を表示する」で見せる・ユーザ指示 2026-11-07）。
  - 「対応」を足す欄の候補は、商品の対応アバターの「＋ 追加」と同じ作り（頭の絵・呼び方の添え書き・群の見出し。ユーザ指示 2026-11-18）。先頭に見出しの無い「対応アバターすべて」、続けて所持アバター・共通素体・未所持アバター。付けた札は商品の欄の札と同じく文字だけ。欄の幅は 210（共通素体の名前が「…」で切れないように 170 から広げた）。
  ［決定］隠した行は欄の部品を組まず、場所も取らない（大量に並ぶ欄なので、畳みを開いたときのスクロール量を増やさない。印を付けて欄が出るときに下の行がずれるのは受け入れる・ユーザ判断 2026-11-07）。
  出す行も、開いたときは上の8行だけ組み、残りは手が空いたときに4行ずつ上から組む（全部まとめて組むと、バリエーション52行の商品で編集画面を開くのが約0.35秒延びた。実測 2026-11-07）
- ［決定］**形**：人が決めた値は `local.variationTargets`、検出した値は `local.detectedVariationTargets`（検出が書き、再検出で作り直す）。1行は `variationId`・`avatars`（アバターの商品 ID）・`bases`（共通素体の名前）・`all`（その商品の対応アバター全部向け。セット売りの行など）。`variationId` が null の行は「バリエーションを選ばない購入」の分で、人が決めた行だけが持つ（ユーザ指摘 2026-11-07）。人が外した、名前から見つけた向き先は `rejectedAvatars`・`rejectedBases`（無ければ書かない）。外しただけの行も人が決めた行で、検出の行に勝つ（ユーザ指摘 2026-11-07：外した候補がまた出ていた）。共通素体ごとにも、全部にも付けられる（ユーザ判断 2026-11-07）。`AvatarLink` にバリエーションを足す形はやめた（検出の `Add` は同じアバターを最初の出どころで止めるので、対応アバター節にも出るアバターのバリエーションが落ちる）
- ［決定］**検出**：バリエーションが2つ以上ある商品で、バリエーションの名前ごとに今の照らし（アバター名・共通素体の名前）を当てる。アバター名も素体の名前も無く、「フルセット」「Fullset」「Full pack」「フルパック」「全セット」「全部入り」「全部まとめ」「全アバター」、英字の単語の「all」を含む行は、対応アバター全部向け（`all`）にする（ユーザ指示 2026-11-07。友人の写しの名前 1,944 個で測り、「セット」だけは衣装の組み合わせの意味が多いので入れない。当たるのは 135 行・122 件）。**1つの名前に複数のアバター**（「〇〇・△△対応」「A / B」）も全部拾う（2人目の友人の写し 1,414 行で 59 行。前は区切りの「・」で落ちて 48 行だった）。拾えないのは、英字のつづりが登録簿の呼び方に無いアバターだけで、アバターの画面で呼び方を足せば拾える。購入の記録にしか名前が残っていない（BOOTH から消えた）バリエーションも、記録の名前で当てる
- ［決定］**人が決めた方を優先**（ユーザ判断 2026-11-06）：同じバリエーションに両方あれば人が決めた方を使い、検出の方は編集の画面で候補として出すだけ。**見分けに検出の値も使う**。設定で「人が入れた物だけ」にもできる（ユーザ判断 2026-11-07）
- ［決定］**持っているバリエーション**：購入の記録のバリエーション（「贈った」は除く）と、手元のファイルに付けたバリエーション（外したファイルは除く）。バリエーションを選ばない購入は、人が向き先を付けたときだけ数える
- ［決定］**持っていない分の見分け**：対応アバターのうち、どれかのバリエーションの向き先に入っていて、持っているバリエーションの向き先のどれにも入っていない物。向き先は素体経由と同じに広げる（アバターはその素体の仲間へ、共通素体はその仲間全員へ）。
  持っているバリエーションが分からないとき、または**持っているバリエーションのどれかに向き先が無いとき**（「本体」のように名前にアバターの無い行）は、何も見分けない（何を持っているか言えないので、薄くしすぎない側に倒す）
- **候補**（押したときだけ入れる）：(1) バリエーション名で引いたアバター・共通素体（今の検出の照らしを、バリエーションごとに返す。友人の写しで、当たるバリエーションの 87〜93% が1体に決まり、読んだ 20 のうち 18 が正しかった。`docs/research/mochifitter.md`）、(2) 中のプロファイルの slug・FBX と同じ決め方（上の「つなぎ先」）
- **持っているバリエーションの候補**（BOOTH の `downloadable` は、ふつうの取り直しで入るのを待つ。一斉には取り直さない・ユーザ判断 2026-11-07）：無料の商品は、BOOTH の JSON の `variations[].downloadable` のファイル ID と、ダウンロード元の記録のファイル ID が一致すれば、そのバリエーション（一意に決まる）。有料はファイル名とバリエーション名の照らし
- **使い道**：変換扱いのつなぎ先を、持っているバリエーションの分だけに絞る（広げすぎる2件の直し）。**衣装にも使う（v1.3.0 に入れる・ユーザ判断 2026-11-06）**：バリエーションでアバターごとに分けて売っている衣装で、持っているバリエーションが分かれば、対応アバターのうち持っている分を見分ける（検索の対応アバターの条件・商品ページの札・統計の「アバター別の所持数」「所有アバターに着られるもの」。統計は切り替えを置かず常に外し、名前から見つけた向き先を使うかは同じ設定に従う・2026-11-19 open.md 106）。見せ方は作るときに決める
- **今の使われ方**：友人の2つの写し（989 件）で、購入の記録にバリエーションが入っているのは1件だけ [実測]。人が自分から入れることは少ないので、変換扱いの画面の流れの中でも「どのバリエーションを持っていますか」を候補付きで聞く
