# 取り込みと BOOTH への問い合わせ（今の決め事）

> **要点**：BOOTH への問い合わせは1本ずつ、1.5秒以上空ける（**絶対に破らない**）。順番は1本の梯子
> 「人が押した通信 ＞ 指名された画像 ＞ ①JSON ②HTML ＞ ③検出 ＞ ④1枚目 ＞ ⑤残りの画像 ＞ ⑥ショップのアイコン ＞ ⑦期限の来た商品」。
> 取り込み中もアプリは使え、取り込みは積め、取り消しは即座。1商品ずつ保存するのでどこで止めても壊れない。
>
> **コード**：`Core/Scanning/ImportPipeline.cs`（周回と画像の列）・`ImportWorkSet`・`FolderScanner`・`ScanCacheIndex`・`UnresolvedMerge`、
> `Core/Booth/BoothClient.cs`（ゲート）・`BoothPriority`、`Core/Services/ImageBacklog`（⑤の再開）・`DueRefresh`（⑦）・`BoothChanges`・`UnityPackageCatalog`・`VolumeTable`
>
> **経緯**：`docs/history/import-order.md`（梯子を決めた理由）、`docs/history/import-concurrency.md`（取り込み中に使える・⑦・印）、
> `docs/history/tech-debt-2026-09-14.md` 1-2・1-3（未確定の一覧）、`docs/research/id-resolution.md`（商品IDの決め方）

## 梯子と優先度

- 全部の問い合わせは `BoothClient` の1つのゲートを通る。**並列化しない・間隔を縮めない**（相手への負担を避ける決め事で、性能の妥協ではない）。
- 優先度は引数ではなく `BoothClient.Prioritize(…)` の範囲（`AsyncLocal`）で決まる。何も張らなければ ①② と同じ段。
- 画面から押した操作は `CommandHandler` の入口で「人が押した」になる。開いただけで取る物（ショップのアイコン＝⑥・バナー＝指名された画像）はハンドラーの中で段を下げる。
- 起動時の裏の作業（⑤・持っていないアバターの画像・⑦）は人の操作ではないので `UiCommand` を通さない。
- 「この商品の画像取得を優先」はその商品の残りを全部取り切ってから戻る。割り込みはリクエストの切れ目で起きる。

## 対象と履歴（ユーザ判断 2026-09-21・G1〜G4）

- **対象は「今積んだ物」だけ。**起動時は空で、落とした物・選んだ物・履歴から積んだ物・監視の新着が入る。落としたとき・フォルダビューから始めたときは取り込み画面へ移らない（下の帯で進み具合と入口を出す。`MainViewModel.ImportNotice`）。
  前は履歴を全部「対象」に積んでいたので、1本落としたつもりでも過去に指したフォルダ全部が走っていた。
- **履歴（`ImportFolders`）は「何を読んだか」の記録**で、対象ではない。取り込み画面に別の一覧として出し、1件ずつ「対象に追加」。
  ファイルも残す（何を読んだかは確かめたい）が、**監視の対象にはしない**（監視は人が「はい」と答えたフォルダだけ）。
- **履歴と監視は1件ずつ足し引きする**（`FolderListChange` を `ChangeSettings` に渡す）。画面の一覧の写しで丸ごと書かない。
  取り込み画面は起動時に1回読んだ写しで、設定画面は保存のたびに自分の一覧で書いていて、片方で足した物をもう片方が消していた
  （2026-09-23・技術的負債 1-1 の再発）。取り込み画面の一覧は開くたびと変えた後に今の設定から並べ直す。
- **起動時の自動取り込みの対象は、監視フォルダの新着と、前回途中で止まった取り込みの続きだけ**（続きはユーザ判断 2026-09-29。`Core/Scanning/LaunchImportTargets`・試験あり）。
  続きは下の帯の「続きから進む」が積む物と同じ（前回の対象と、BOOTH の不調で取れなかった商品のファイル）。帯が出ていない（伝えることが無い）回は積まない。
  前は新着だけを見ていて、①の途中で閉じた回はファイルが走査の控えに載っているので新着に数えられず、続きが残っていても起動時に何も始まらなかった。
  監視フォルダが無くても続きは見る。今そこに無い物（外付けを外している）は積まない。履歴は積まない。続きの対象に監視していないフォルダがあっても「監視しますか」とは聞かない。
- **自動で始めたときは窓で尋ねない。**展開先のファイルを指していたらそのまま取り込み、**要確認に出して**後から差し替えられるようにする
  （押してもいないのに応答待ちの窓が黙って出ていた）。
- **見つからないファイルは監視フォルダの中から中身で探して結び直せる**（`MissingFileFinder`）。結び直したら検索の写しを読み直す（前は検索の `path:` が起動し直すまで古い場所で絞っていた・点検 2026-09-30 の C）。
  探す処理は丸ごと画面のスレッドの外で走る（2026-09-30。`architecture.md`「スレッドとディスク」）。取り込み中に押してもよい：控えは錠の中で今の控えに足し、商品は錠の中で今の値の場所だけを差し替える。
  同一性はハッシュなので、移した・名前を変えただけなら戻る。大きさが合う物だけ中身を確かめる（全部をハッシュすると数百GBを読む）。

## 周回

1. 対象（`ImportWorkSet`）から走査 → 商品IDを決める → ①JSON ②HTML（全商品まとめて）→ ③対応アバターの検出。
   **①②を全商品まとめてやるのは、部分的な知識で作業を始めさせないため**（候補に種類の名前などが揃ってから）。
   **取り込み全体と検出は画面のスレッドの外で回す**（2026-09-24。Core は続きを元の文脈へ戻すので、全件の読み込み・③の走査が画面のスレッドで走っていた）。
   ③は商品ごとの走査の結果を控え、booth・説明・登録簿の索引・見出しの設定が変わっていない商品は走査し直さない（2000件で2回目の検出が 2.1秒 → 0.16秒。結果は同じ）。
   走査と ID の特定の進み具合は1ファイルごとではなく、1秒に10回ほどに間引いて最新だけ知らせる。
2. ④1枚目・⑤残り・⑥アイコンは周回の外の**画像の列**で1件ずつ取る。1件ごとに積まれたフォルダを見て、あれば次の周回へ移る。
   新しい周回の1枚目は列の先頭に入れる。
   届かない失敗（応答が無い・5xx）が3件続いたら、この回の画像の残りは取りに行かない（①②とは別に数える。印を置かないので起動時の⑤で取れる。`background-and-network.md`）。
   **④の並びは検索の既定・編集の待ち行列と同じ規則**（`ItemOrder.ByAcquired`＝入手日の新しい順、同じなら商品名順。ユーザ判断 2026-09-21）。
   走査した順のままだと、絵が埋まっていく順と人が上から片付けていく順が無関係になり、待ち行列の先頭の絵だけが来なかった。
   入手日は人が手で入れたときしか入らないので、取り込んだばかりの商品は同着になる——**同着の決め手を3か所でそろえることが要点**。
3. **1枚目が取れた時点で、その商品を画面に出す**（白いカードを並べない）。取れなかったら「画像なし」として出す（消さない）。
4. 検索・要確認・未確定の一覧は勝手に並べ替えず、「取り込み中に n 件増えました。押すと一覧に反映します。」を出す。画面を離れたら黙って最新にする。
5. 取り込み中は「保存先を変える」を押せない。
6. **途中で止まったままなら、どの画面からでも分かるようにする**（ユーザ指摘 2026-09-22）。下の帯に
   「前回は n / N 件まで進んで中断しました」＋［続きから進む］［続きを捨てる］を出す。**帯は常設ではない**
   ——続きが残っている間と通信している間だけで、走り出したら通信の帯に替わる（2本並べない）。
   解消するまで出し続けるのは、②が済んでいない商品は説明文が無く、③が走っていないので編集にも出てこないため
   （未確定・要確認・形式の変化と同じ扱い）。続ける気の無い人のために「続きを捨てる」で記録だけ消せる（取れた分は消さない）。
   - 「続きを捨てる」は**戻せない**ので、ツールチップと確認の窓（既定はキャンセル）で言う。やり直すには履歴の「対象に追加」から始め直せばよいことも書く
     （2026-09-23：「やめる」では何が無くなるか読めず、確認も無かった）。記録を消すのは `UiCommand.DiscardInterruptedImport`、帯は書き終わってから下ろす。
   - 「続きから進む」は**対象を積むところまでやる**。取り込み対象は次の起動で空に戻るので、
     前は「もう一度押すと続きから進みます」が**押せないボタンを指していた**。
     積むのは前回の対象だけ（`ImportState.Targets`）——履歴を全部積むと対象外のフォルダまで走査してしまう。

## 積む・取り消す・中断

- 実行中でも「今の取り込みに追加」。同じフォルダは集合なので1つになる。まだ走査していない物は一覧から外せば取り下がる。
- 取り消しは**全体を即座に**（段の切れ目まで待たない）。
- **次の起動で①②は自動では続けない**（フォルダの走査は人が指示した読み取りだけ）。中断した事実は `import-state.json` から「前回は 34 / 100 件まで進んで中断しました」と出す。①が全部済んだ後に閉じたなら出さない。
  **周回が走査に入る前に、対象と「走査の途中」（`scanning`）を書き、①に入るところで外す**（2026-09-30）。前は①で1件取れるまで何も書かず、走査・ID の特定の途中で閉じる・中止すると対象が空のまま残り、帯も起動時の続きも出なかった。走査の途中は①の件数が無いので「前回の取り込みは途中で中断しました」と出す。走査の控えは10秒ごとなので、続きではその間の分だけハッシュを取り直す。
- ⑤（画像）は手元の JSON だけで対象が決まるので、起動時に再開してよい（設定「起動したとき、裏で取得を始める」で切れる）。
- 取得済みでも説明のファイルが無い商品は②の対象に戻す（説明が無い商品には空のファイルを置く）。
- **「追加した」の足跡（`recent.json`）は溜めて書く**（`RecentStampBuffer`。2026-09-29）。50件ごとと①を抜けるとき（終わり・中止・例外）に1回。
  1件ずつ書くと育つファイルを毎回読み書きし、2,000件で約18秒・2,000回になっていた（→ 0.35秒・40回。`docs/research/memory-budget.md`）。
  錠の中で今のファイルに当てるので、その間の閲覧の足跡は消えない。取り込み中の「最近追加した」は50件ずつ増える。落ちたら最後の50件ぶんまでの「追加した」が「不明」になる（商品は無事）。

## 走査と手元のファイル

- ハッシュは「パス・大きさ・更新日時」が `scan-cache.json` と同じなら計算しない。**持っているハッシュの zip は開かない**：中身の一覧は商品の `contents`、ID の手掛かりは控えの `clueItemIds` を使う（2026-09-24。取り込み直すたびに全部の zip を開き直していた）。
- 控えは途中で10秒ごとと周回の終わりに、錠の中で今の控えに重ねて書く（見つからないファイルを探す所も足すため）。**取り込みの終わりに、取り込み元の下で無くなったパスを落とす**（つながっていないボリュームの上は落とさない）。
- 走査は**木を1回だけたどる**（幅優先・フォルダごとに1回並べ、そこから展開先・取り込むファイル・展開先の中の数を決める。大きさと日時は列挙で取れた物を使う）。見つかる物は前の作りと同じ（試験で突き合わせている）。
- 登録したフォルダを測り直すのは取り込み1回につき最初の周回だけ。
- 走査で飛ばす再解析点は**ジャンクションとシンボリックリンクだけ**（ループの元）。OneDrive の中はフォルダもファイルも再解析点なので、前は丸ごと飛んでいた（2026-09-23）。
  **中身が手元に無いクラウドのファイル（オンラインのみ）は読まない**——ハッシュを取るとダウンロードが始まる。**勝手にダウンロードはしない。**
  数は取り込みの結果に「N 件は OneDrive の『オンラインのみ』なので読めませんでした」と次の手（フォルダを「常にこのデバイスに保持する」にする）を添えて出し（0件なら出さない）、どのフォルダで何件かはログに残す（ユーザ判断 2026-09-23）。
- **ハッシュを計算できなかったファイル**（書き込み中のダウンロード・ほかのアプリが開いている物）は、走査で読めなかった物と同じ「読めなかったファイル」の数に入れて結果に出し、パスをログに残す（前は黙って飛ばしていた）。控えには書かないので次の取り込みで読み直す。
- **中を読めないフォルダ**（権限が無い・ネットワーク越しで切れた）も黙って飛ばさず、結果に「読めなかったファイルが n 件、フォルダが m 件あります」と数え、パスをログに残す（2026-09-30。前は空のフォルダとして飛ばしていた）。中に何件あったかは読めないので、ファイルの数には足さない。フォルダだけのときは次の手を「エクスプローラで開けるか確かめる」にする。走査の途中で消えたフォルダは数えない。
- **zip として開けなかった zip は、記録に印 `archiveBroken` を付ける**（大容量の確かめ 問題4・ユーザ判断 2026-09-30）。未確定の記録にも、商品のファイルの記録（`LocalFiles`）にも付く。前は中身の一覧が空の物として置くだけで、途中で切れたダウンロードに気付けなかった。
  - 印が立つのは形式が合わないとき（目録が無い・崩れている・zip ではない物に .zip の名前）だけ。ほかのアプリが開いていた・権限が無いは立てない（次は開けるかもしれない）。
  - **開いてみないと分からない事実なので記録に書く**（未確定の画面で開き直すと zip の数だけ読む）。開けた物には書かない。開けなかった zip は控えに手掛かりを書かないので、取り込むたびに開き直して決め直す。落とし直せば中身が変わり、印の無い別の記録になる。
  - **商品に結び付いた物にも付ける**（ユーザ判断 2026-09-30）。ダウンロード元の記録から商品が1つに決まると未確定を通らないので、前は印がどこにも出なかった。
    付くのは、新しい商品を作るとき・既にある商品に足すとき・前から商品が持っている物を見たとき（手で結んだ壊れた zip は場所が変わらないので、印が今の答えと違えば場所を足す道で書く）。
    未確定から商品へ登録するとき・商品から外して未確定へ戻すとき・BOOTH に無くて未確定へ戻すときは、記録ごと引き継ぐ。印の無い古い記録は、取り込み直すと付く。
  - **同じ場所に落とし直すと、壊れた方の記録は消える**：壊れた zip の記録が指す場所に別の中身が在れば、その場所を記録から外し、場所が残らなければ記録ごと落とす（下の「同じ場所の中身が変わったら」の道。記録ごと落とすのは壊れた zip だけ）。
    手掛かりの無い物（手で結んだ物）を落とし直すと、商品からは消え、新しい方は未確定に出て、結んでいた商品が候補に残る。
    別の名前で落とし直して壊れた方も残っているなら、印は残る（まだ在る）。壊れた方を消しただけなら、記録は「見つかりません」として残る（壊れていない記録と同じ決まり）。
  - 結果には、未確定の分と商品の分を行を分けて出す（案内する先が違う。0件なら出さない）。「読めなかったファイル」と同じ枠：あちらは取り込めていない物で次の手が「閉じて取り込み直す」、こちらは入っていて次の手が「ダウンロードし直す」。
    - 未確定：「未確定に、壊れていて開けないzipが n 件あります。下の「未確定を開く」で確かめて、ダウンロードし直してください。」
    - 商品：「m 件の商品に、壊れていて開けないzipが n 件あります。下の「壊れたzipがある商品を検索で開く」で確かめて、ダウンロードし直してください。」。商品が1つのときだけ、頭を「「商品名」に、」にする（30字で切る。押さなくても分かる）。
      ボタン「壊れたzipがある商品を検索で開く」は、検索の条件「壊れたzip」だけで絞って開く（ユーザ判断 2026-09-30・`docs/spec/search.md`。未確定の側の「未確定を開く」と同じ作法。取り込み中は出さない）。
      前は「「商品名」など m 件の商品に」と名前を1つ言うだけで、残りは商品ページを1つずつ開かないと分からなかった。検索に出るのは記録に印のある商品すべてなので、この取り込みで見ていない分も並ぶ（m より多いことがある）。
    - 数は中身（ハッシュ）で数える。商品の分は、この取り込みで開いてみた物だけ（走査していない取り込み元の物は数えない）。BOOTH に無くて未確定へ戻した物は未確定の分に入る。
  - **見つからない物**：目録が無事で中のデータだけが化けた zip（全部を解かないと分からない。一時展開で分かる）、rar（中を開かない）。
- 新しい商品を①で書くとき・未確定の「このIDで登録」・フォルダの登録は、**書く直前に読み直し、在れば booth だけを重ねて手元のファイルは足す**（L13。取る数秒の間に別の道が同じ商品を作ることがある）。
- ②は節を**今の booth に足す**（`ItemRepository.ChangeBoothAsync`）。①と②の間に人が「商品情報を取り直す」を押して今の方が新しく取れていれば（`Booth.FetchedAt` で比べる）触らない。前は①の写しで丸ごと書き、取り直した新しい booth を古い物に戻していた。
- **手掛かりから商品が決まらなくても、同じ中身（ハッシュ）を持つ商品があれば、記録に無い場所をその商品に足す**（2026-09-30・大容量の確かめ A）。
  未確定で手で結んだ物を別の取り込み元へ移したとき、前は「もう持っている」として黙って飛ばし、記録が古い場所のままになっていた。
  外した印の行は持ち主に数えない（錠の中でも見直す）。管理から外した中身はその前で止まる。同じ中身を2つの商品が持つなら両方へ足す。
  手掛かりで決まる物は、もともと「手元にある商品」の道（①の前）で足している。
- **手掛かりで商品が決まったときも、同じ中身を持つほかの商品へ新しい場所を足す**（ユーザ判断 2026-09-30）。
  同じ zip を、手掛かりで決まる商品と手で結んだ商品の両方が持つとき、前は決まった商品にだけ足し、手で結んだ方は古い場所のまま「見つかりません」になっていた
  （手掛かりの有無で結果が分かれていた）。外した印の行と管理から外した中身に足さないのは上と同じ。古い場所は `LocalFileMerger` が落とす。
- 商品のファイルを足すとき、実在しなくなったパスは落とす（移した・消した）が、**つながっていないボリュームの上のパスは残す**（`LocalFileMerger`。外付けを外している間に同じ商品へファイルを足すと、外付けの上の記録が消えていた・2026-09-23）。
- **同じ場所の中身が変わったら、古い中身の記録からその場所を外す**（ユーザ判断 2026-09-30「3A」。`ImportPipeline.DropReplacedPathsAsync`）。
  `LocalFileMerger` は場所に何かが在るかしか見ないので、更新版を同じ名前で上書きすると、古い中身の記録も「その場所に在る」として残り、商品ページに同じ名前の行が2つ並んでいた。
  - **場所が1つも残らない記録も残す**（商品ページで「見つかりません」の行になる。種類の結び付きや、手で結んだ事実を失わない）。記録ごと落とすのは壊れた zip の記録だけ（上）。
  - **判じるのは、今回の走査でその場所のハッシュを取った（か、走査の控えから分かった）ときだけ。**走査していない場所・読めなかったファイル・つながっていないドライブの上の場所は触らない。
  - 同じ場所を2つの商品が持っていれば、どちらの記録からも外す。外した印の行からも外す（そこに在るのは別の中身）。錠の中で今の値に当てる。
  - 新しい中身の行き先は今までどおり：手掛かりで商品が決まればその商品へ、同じ中身を持つ商品があればそこへ、どちらでもなければ未確定へ。
  - **未確定へ出るときは、同じ場所にあった商品を候補として記録に残す**（ユーザ判断 2026-09-30「2A」。`unresolved.json` の `samePathItemIds`）。
    手で結んだ物を上書きすると、前はどの商品の物だったかが画面から分からなくなっていた。**自動では結ばない**（同じ名前の別の商品を置いただけかもしれない）。
    壊れた zip の落とし直しも、壊れていない物の上書きも同じ道。外した印の行の商品と、新しい中身を「この商品のものではない」と外してある商品は載せない。
    上書きを見つけた回にしか分からない（次の回には古い記録はその場所を指していない）ので、未確定の一覧を作り直すときに、前に書いた同じ中身の記録から引き継ぐ。
    画面での見せ方は `docs/spec/id-resolution.md`「未確定の画面」。
  - 見ていない所：外したパスに、外した中身が控えどおり在るとき（走査で計算なしに弾くので、ここまで来ない）。
- **管理から外したのは、その中身。場所ではない**（ユーザ判断 2026-09-23）。同じ名前で落とし直した更新版まで外し続けないため。
  - 計算なしで外すのは、外したパスで、走査の控え（`scan-cache.json`）が今の大きさ・更新日時と合い、控えのハッシュが外した物のときだけ（`ExclusionFilter.IsExcludedWithoutHashing`）。
  - 合わない（控えが無い・大きさか日時が違う）ならハッシュを取り直し、外した中身なら外し、違えば新しい物として取り込む。監視も同じ判定で新しいと数える。
  - 移動・改名した物はハッシュで外す（今のまま）。除外の記録（`excluded.json`）に欄は足さない——大きさと日時は控えが持っている。
- 既に商品に紐付けたフォルダの中は見に行かない。zip を展開したフォルダは元の zip と見分ける。
- 取り込むフォルダのドライブ文字と通し番号の組をその周回で控える（`volumes.json`）。

## 未確定の一覧（`unresolved.json`）

- 取り込みは周回で見つけた物で一覧を作り直すが、**丸ごと上書きしない**：前に書いた一覧と今の一覧を比べ、その間に人が外した物は戻さず、足した物は消さない（`UnresolvedMerge`）。
- **ボリュームがつながっていない取り込み元の下の未確定は引き継ぐ**（外付けを外したまま取り込んでも消えない）。フォルダが消えただけなら片付いたとして落とす。
- **今回見つからなかった未確定を落とすのは、そのパスが今回走査した取り込み元の中にあるときだけ**（2026-09-30・大容量の確かめ E）。
  対象は「今積んだ物」だけなので、走査していない取り込み元の物は見ていないだけで、残す。
  前は外付けだけを見ていて、フォルダ乙（や監視の新着1本）を取り込むとフォルダ甲の未確定が消え、甲の物は走査の控えに載るので監視も新しいと数えず、どこにも出なくなっていた（G1 の 2026-09-21 から）。
- **走査の控えに載っているだけの物（商品にも未確定にも除外にも無い）は、その取り込み元を取り込み直すと未確定に戻る**（ユーザ判断 2026-09-30・試験あり）。
  控えが決めるのは「ハッシュを取り直すか」だけで、行き先（商品・未確定・除外）は取り込みのたびに決め直す。戻すために読み直すファイルは無い。
  上の件で消えた物を戻す手は、取り込み画面の「取り込み元の履歴」の「対象に追加」から取り込み直すこと。**監視の新着には数えない**（控えに載っている物は新しくないと見る。今のまま）。
- BOOTH に無かった（404）ファイルも未確定へ回す（手元から消さない）。
- 未確定の画面の操作（割り当て・外す・戻す）は錠の中で1件ずつ足し引きする。読み書きは画面のスレッドの外で走る（`docs/spec/architecture.md`「書き込み」）。
- **展開した中身の見分け（`ArchiveContentDetector`）は、行を1回組む間だけフォルダの列挙を覚える**（`Pass`。2026-09-30）。親を6段たどるので、
  覚えないとフォルダの数だけ同じ親を列挙し直す。組むたびに新しく作り、またいで持たない（フォルダの中身が変わったのに古い見分けを返さないため）。

## 取れなかった物

- 404だけが「非公開」の数えに入る（3回連続で確定）。タイムアウト・5xx・接続失敗は数えず、同じ実行の中で2回まで間隔を空けて（2秒→8秒）試し、だめならその回は飛ばす。429 を受けたら間隔を倍にして30秒で頭打ち。Retry-After は60秒まで付き合う。
- **①で BOOTH の不調（タイムアウト・5xx・接続失敗・200 でも読めない応答）で取れなかった商品は「続きから」に残す**（ユーザ判断 2026-09-23・#10）。
  前は飛ばすだけで、そのファイルは商品にも未確定にも入らず、ハッシュが走査の控えに載るので監視も新しいと数えず、黙って消えたように見えた。
  - `import-state.json` の `unfetched`（商品IDとファイル）に書く。**最後まで走っても空でなければ記録を消さず**、下の帯に「前回の取り込みで N 件は BOOTH の不調で取れませんでした。少し待ってから「続きから進む」で取り直せます」を出す。別の取り込みを始めても引き継ぎ、取れた・商品が既にあった・404 で未確定へ回したら外す。
  - 「続きから進む」は前回の対象と、取れなかったファイルを積む（最後まで走った回はファイルだけ）。取り直しは同じ梯子の①を通る（1本ずつ・1.5秒・優先度は変わらない）。
  - 取り込みの結果にも件数と次の手を出す。監視は取り直すまでそのファイルを「新しい」と数える（`FolderWatch`）。「続きを捨てる」はこれも消す。
- **応答の無い失敗（接続できない・タイムアウト）か 5xx が3件続いたら、その回の問い合わせを打ち切る**（ユーザ判断 2026-09-29・点検 2026-09-28 の 9）。
  ネットにつながっていないと1件ごとに再試行で長く待ち（つながらないとき約13秒・応答が無いとき最長約100秒）、全件を回るので止まって見えた。
  BOOTH が落ちている間に全件を再試行で回ると、復旧に時間の掛かる相手へ問い合わせを重ね続ける。
  - 数えるのは①②の1件ごとの結果（再試行の後）。応答が無いのと 5xx は混ざっても続けて数える。**BOOTH が意味のある物を返したら数え直す**（取れた・404・読めない応答）。429（混雑）はこちらの出し過ぎなので、今の扱いのまま数えない（数え直す）。
    見分けは `BoothFetchResult.IsUnreachable`・`IsServerError`（`BoothClient` が立てる）、数えるのは `BoothOutageWatch`（画像の段と同じ部品。理由は最後に数えた失敗の種類）。
  - ①で打ち切ったら、残りは問い合わせずに `unfetched` へ入れる（一時失敗と同じく「続きから」で取り直す）。②で打ち切ったら残りの説明文は取らない。
    どちらもこの回の画像は取りに行かない（起動時の⑤か「足りない情報を取得」で取れる）。③は走らせる（手元の材料で済む分がある）。
  - `import-state.json` に打ち切った理由 `stopped`（`offline`／`serverDown`。打ち切っていない回は書かない）と対象（`targets`）を残す。
    ②で止めた商品は①が済んでいて `unfetched` に載らないので、「続きから進む」で対象を走査し直し、説明の無い商品として②へ戻す。
  - 結果と下の帯は理由で言い分ける。応答が無いときは、途中で止めたこと・ネットにつながっていないようだということ・つながってから「続きから進む」を押すこと。
    5xx のときは、途中で止めたこと・BOOTHが不調のようだということ・時間をおいて「続きから進む」を押すこと（つなぎ直しても直らない）。
    人が押した「商品情報を取り直す」も、つながらないときと BOOTH の不調とで文を言い分ける（`RefreshOutcome.Unreachable`。5xx は `ServerError`、429 などは `TemporaryFailure` で、文はどちらも「不調」）。
- 404で取れなかった画像には `{ハッシュ}.missing` を置く。**日数では外さず、その商品の JSON を取り直したときに外す**。印の付いた画像は「決着済み」として数え、優先ボタンの代わりに「n 枚は取得できませんでした」を出す。

## ⑦ 期限の来た商品の取り直し

- `NextFetchDueAt <= 今` を古い順に、暇になってから（梯子の最下位）。間隔は7日±3日（設定画面には出さない）。連続404が3回以上なら30日（**季節ものは1ヶ月ほどしか公開されない。延ばすと原理的に取り逃す**）。
- 取り直しは画像を落とさない。増えた画像は④⑤の列に積む（人が押した取り直しも同じ経路で先頭に来る）。
- 変わっていたら要確認（`ItemUpdated`）：販売終了・価格・種類の増減・画像の増減・商品名。**スキ数は知らせない**（必ず動く）。説明文は見出しごとに比べ、変わった・足した・消えた見出しを知らせ、変わった行だけを持たせる（`LineDiff`。2026-10-02。空白と空行の違いは数えない）。何が変わったかを1件に列挙する。
- 同じ商品の未読（未解消）の `ItemUpdated` があれば、新しい差をそこへ**重ねる**（`ChangeStack`。ユーザ判断 2026-10-02「重ねましょう」。前は差し替えていて1回目の差が消えた）。1件にまとめ、`createdAt` は最初の変化のまま `updatedAt` に重ねた日時を書く（要確認の並びと「何分前」は `updatedAt` で見る）。既読にした後の変化は新しい知らせ。
  - 短い値（商品名・価格・件数・販売）は「最初の前 → 最後の後」。説明文の見出しの頭の抜き出しも同じ。
  - 変わった行は行の差どうしを重ねる（前の本文は残っていないので）：後で消えた行が前に足した行にあれば足した側から取り除き、後で足した行が前に消した行にあれば消した側から取り除き、どちらでもなければ後ろに続ける。同じ文の行は1本ずつ打ち消す。上限（種類ごとに30行）は重ねた後に当て直し、超えた数は `moreAdded`・`moreRemoved` に足す。数だけ残した行は文が無いので打ち消せない。
  - 前と後が同じで行も残らない欄（価格が上がって戻った、など）は外す。全部外れたら知らせごと消す。
- 対応アバターの節が読めなくなったら `PageStructureChanged`。

## 取り込みの裏で読む物

- **unitypackage の中身**：zip の中の unitypackage を①と同時に裏で読み（小さい zip から・画面を止めない優先度）、入る先の要約を①の後で商品に写す（`UnityPackageCatalog`）。手でファイルを付けた後も同じ。
- 失敗は `logs/app.log` に残す（取り込みは止めない）。
