# 使っている商品の更新の促し（v1.3.0・作っている途中）

> **要点**：改変に使った商品・Unity のプロジェクトに入っている商品に、新しい版が出たら促す。対応アバターを足しただけの更新では促さない。
>
> **コード**：`Core/Services/UsedUpdateKind.cs`（促す更新か）
>
> **経緯**：`docs/plan.md` の 7（ユーザ指示 2026-11-06・判断 2026-11-06／11-09）

**まだの所**（2026-11-09）：v1.3.0 に上げたときの、今ある通知からの移行だけまだ（`docs/plan.md` の 7 の「作る順」）。

## 画面

- ［実装］**商品ページの上の帯**（`ItemViewModel.UsedUpdate`・撮る場面 `item-page-used-update`）：商品として促し（`HasPendingContentUpdate`）、かつ使っているときだけ。文は「改変 n 件・Unityプロジェクト n 件で使っています。新しい版が出ています。」（使っていない方は書かない・ユーザ判断 2026-11-06「一旦この形」）。ボタンは「更新履歴を見る」（説明文の更新履歴の見出しまで流す。見出しが無い商品では出さない）と「確認した」（`UiCommand.CheckContentUpdate`）。通知の「BOOTHで変わったところ」の帯の上に、同じ1行の高さで置く。既読とは別。編集画面の中では出さない。使っているかは見張りの答えが変わるたびに出し直す。
- ［実装］**改変の行の札**「新しい版あり」と、行の「確認した」（`UiCommand.CheckModificationUpdate`。その改変のその商品の行に `updateCheckedAt` を書く）。商品の帯は消さない。
- ［実装］**検索**：条件「更新通知あり」の種類に「使っている商品の中身の更新」（キー `used`・中身の更新の隣）を足す。知らせを読んでいても、商品として促し、かつ使っていれば当たる。**アプリだけ**（使っているかは Unity のプロジェクトを見るアプリの見張りが答えるので、API の種類は今の5つのまま・ユーザ判断 2026-11-09）。前に保存した条件は5つのまま読む（新しい種類は入らない）。見張りの答えが変わると絞り直す。
- 改変を書くと（画面・Unity からの受け取り・API のどれでも）、見張りが改変の数だけ数え直す（`ModificationRepository.Written`。プロジェクトは調べ直さない）。

## 使っているか（`UsedItems`・`App/Services/UsedItemsWatch`）

- ［決定］使っている所は、その商品を使った**改変**（外した行だけの改変は数えない）と、その商品が入っている **Unity のプロジェクト**（unitypackage が入っている・同じ絵の画像が見つかった。名前が同じだけの画像は数えない）。数は記録に書かず、見せる所で組む。
- ［決定］調べるプロジェクトは、改変に紐付けたプロジェクトと今開いている Unity のプロジェクト（ユーザ判断 2026-11-09）。検索の条件「Unityプロジェクト」と同じ調べ方（`ScanUnityProject`）で、結果は同じ控え（`unityscans/`）に書き、先に控えを見せてから調べ直す。BOOTH には問い合わせない。
- いつ調べるか：検索の写しを読み終えたとき（起動の後・取り込みの後）と、窓に戻ったとき。1つ 0.6〜4.7秒（782件）かかるので、このアプリで一度調べたプロジェクトは、Unity で開いている間だけ調べ直す。Unity を閉じたプロジェクトは、改変に紐付いていなければ数えない。フォルダが無い・読めないときは前の結果を残す。

## 控えを書く所（`UsedUpdateRecorder`）

- ⑦と人が押した取り直し（`ItemService.RefreshAsync` の終わり）。更新履歴の見出しが動いた商品だけ、**対応アバターを検出し直してから**見分ける（ユーザ判断 2026-11-06。検出は取り込み・ボタン・90日ごとにしか走らず、足されたアバターが商品に入っていなかった。`background-and-network.md`）。見分けに使う名前は、検出し直した後の商品の対応アバター・共通素体の名前と別名。
- 通知とは別に書く：商品ごとの「更新を知らせる」を切っていても書く（ユーザ判断 2026-11-09）。
- 控えを書けなくても取り直しは成功として返す（ログに残す）。アプリを閉じて検出の途中で止まった分は控えに入らない（次に更新履歴が動いたときにまた見る）。

## データの形と、促しが消える条件

- ［決定］商品の `local.contentUpdate`（`ContentUpdate`。最後の1件。見つけていなければ書かない）：`foundAt`（見つけた日時）・`filesBefore`（その時に持っていたファイルのハッシュ。外した物・古い版は入れない）・`checkedAt`（商品ページの「確認した」。押していなければ書かない）。手元のファイルに「いつ取り込んだか」の記録が無いので、その時に何を持っていたかを控える。
  また促す更新が来たら作り直す（前の「確認した」は捨てる）。持ち主は `LocalOwners.ContentUpdate`。
- ［決定］**商品として促す**（`LocalBlock.HasPendingContentUpdate`・書き出さない）：控えがあり、「確認した」を押しておらず、その後に新しいファイル（控えに無いハッシュの持っているファイル）か、見つけた後に登録したフォルダが無い。使っているか（改変・Unity のプロジェクト）は記録に書かず、見せる所で組む（アプリの外で変わるので）。
- ［決定］**改変の行**（`UsedUpdates.IsMemberBehind`・ユーザ判断 2026-11-09）：行の使ったファイルが控えに入っていれば出す（新しいファイルで送り直すと消える）。この改変で「確認した」（構成物の `updateCheckedAt`）を控えより後に押していれば出さない。使ったファイルが分からない行は商品の印に従う。外した行には出さない。

## 促す更新か（`UsedUpdateKind`）

- ［決定］手掛かりは強い通知と同じ「更新履歴の見出しの変化」（`BoothChanges.HasStrongChange`）。そのうち、**足した行が全部「対応アバターの追加」なら促さない**（別のアバター用の Prefab・変換プロファイルの公開は、今使っている人のファイルを変えない）。
- ［決定］**迷えば促す**（ユーザ判断 2026-11-06）。行が1つでも追加と言い切れなければ促す。足した行が上限（30行）で切れた知らせ・行の差を持たない古い形の知らせも促す。消した行は見ない。
- ［決定］アバターの新しい版への対応（「〇〇 Ver1.3.0 に対応」）は更新に数える（ユーザ判断 2026-11-06：アバターを上げた人には要る）。版の後に「対応」が来る形で見分け、それ以外の版の数字（足した物そのものの版）は外して読む。
- 行の見分け：
  - どちらとも言わない行：空・日付だけ・版だけ（行の頭の記号・日付・版は外して読む）。これしか無い知らせは促す
  - 更新の行：修正・調整・機能・削除などの語（日・英・韓）、道具への対応（Modular Avatar・lilToon・シェーダーなど）
  - 追加の行：「〇〇用 Prefab を追加」「〇〇用プロファイルを公開」「〇〇に対応」「〇〇対応」「対応アバターを追加」「support for 〇〇」「〇〇 대응」、または今の対応アバターの名前を並べただけの行（名前を除くと、つなぎの記号と語しか残らない）。名前が入っているだけでは追加にしない（「〇〇用の新しいテクスチャ」を見落とす）。「추가」（追加）は色や機能の追加と見分けられないので型に入れない
- 名前は全角・半角をそろえ、ラテン文字の付け記号（「é」など）を外し、大文字小文字を無視して照らす。濁点・半濁点は外さない。1字の名前は使わない。
- 確かめ［実測］（2026-11-09）：友人の写し2つの強い通知 29 件に当てると、追加だけは3件（別のアバター用の Prefab・プロファイルの公開・韓国語の対応完了）で、11-06 に手で読んだ分け方と合った。「〇〇対応」と修正が混ざる物は促す側に入った。
