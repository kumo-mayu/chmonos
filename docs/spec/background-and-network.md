# 裏の作業・通信・失敗の書き残し（今の決め事）

> **要点**：BOOTH への問い合わせは全部 `BoothClient` の1つのゲート（1本ずつ・1.5秒以上）を通り、優先度は1本の梯子で決まる。
> ゲートは PC で1つ（同じ PC で動くアプリ・評価台・道具を合わせて1本ずつ・1.5秒以上）。
> 起動時に自動で始めてよいのは手元の JSON だけで対象が決まる作業（⑤画像・持っていないアバターの1枚目・⑦期限）だけで、フォルダの走査（①②）は人が押して始める。
> 失敗は黙って飛ばさず `logs/app.log` に残す。
>
> **コード**：`Core/Booth/BoothClient.cs`・`BoothPriority`・`PriorityGate`・`BoothMachineGate`、`Core/Services/ImageBacklog`・`DueRefresh`・`BoothChanges`・`NotificationService`・`FolderWatch`、
> `Core/Diagnostics/AppLog.cs`（`LogFile`）、`App/FireAndForget.cs`（`Forget()`）、`App/ViewModels/MainViewModel*.cs`（`RunBackgroundStageAsync`）
>
> **経緯**：`docs/history/import-concurrency.md`（梯子・印・⑦）、`docs/history/booth-machine-gate-2026-09-30.md`（PC で1つの門）、`docs/history/tech-debt-2026-09-14.md` 2-1〜2-3、`docs/research/antivirus.md`（名乗り・配布物）

## 通信の決め事

- **1本ずつ、1.5秒以上空ける**（設定画面の下限も 1500ms）。並列化しない・間隔を縮めない。`BoothClient` を通らない通信を書かない。
- 429 を受けたら以降の間隔を倍にしていく（上限30秒）。Retry-After は60秒まで付き合い、超えたらその1本は次回に回す。
- **Retry-After で待てと言われたら、他の問い合わせも待つ**（ユーザ判断 C15）。待ちはゲートの中で行うので誰も追い越さない（中断は効く）。
  60秒を超える指示でも、次の問い合わせは60秒は待つ。503 などに Retry-After が付いたときも 429 と同じく間隔を広げる。
- 最後の問い合わせの時刻は**送った後はどう抜けても**（中断・想定外の例外でも）更新する。更新が漏れると次の1本が間隔を空けずに出る。
- **間は、起動してからの刻みで測る**（壁の時計ではなく `TimeProvider.GetTimestamp`。2026-09-30）。時計を合わせ直しても、戻った分だけ待つ・進んだ分だけ詰めることが無い。
  待ち終えた後に刻みで測り直し、タイマーが早く鳴った分（OS の刻み約 16 ms の粗さ）は待ち足す。
- **門は PC で1つ**（ユーザ判断 2026-09-30。`BoothMachineGate`）。同じ Windows のユーザで動くプロセス全部を合わせて、1本ずつ・前の問い合わせが終わってから1.5秒以上。
  前は門がアプリ1本ごとで、保存先の違うアプリを2本開くと（普段使いと確かめ用の写し・アプリと評価台・並べて走らせた道具）それぞれが1.5秒ごとに問い合わせ、合わせると破っていた。
  - 仕組みは**ファイル1つと、その上の範囲の錠**（`%LOCALAPPDATA%\Chmonos.Shared\booth-gate.txt`。保存先の外。既定の保存先とも別のフォルダ）。
    握るのは中身を読み書きする一瞬と、問い合わせを送ってから終わるまで。**間隔を待っている間は放す**（握ったまま待つと、裏の作業を続けるアプリが握り続ける）。
    中身は最後の問い合わせの刻み・そのときの間隔・待てと言われた刻み・最後に出した人と待っている人の印（読める文字の数行）。
  - **落ちても止まらない**：錠は OS が外す。送ったまま落ちたら「送っている最中」の印が残り、次の人は落ちた1本が相手の側で終わるまでの分（2 秒）を見てから、間隔を空けて出る
    （「今終わった」とみなして間隔だけ空けると、相手から見た間が応答にかかった分だけ短くなる。測ると 1424 ms だった）。
    Windows を起動し直した後の古い刻み・壊れた中身・大きすぎる値でも、待つのは自分の設定の上限（間隔 30 秒・指示の待ち 60 秒）まで。
  - **間隔の設定が違えば長い方に合わせる**（最後に出した側・待っている側・自分のいちばん長い物。429 で広げた分も含む）。待てと言われた刻み（Retry-After）も全部のアプリが守る。
  - **1本の中の優先順位はそのまま**（下の梯子）。プロセスをまたぐ優先順位は無い。代わりに、最後に出したアプリは、ほかのアプリが順番を待っていれば 0.25 秒譲る
    ——2本が動いている間は1本ずつ交互になり、もう1本の人が押した問い合わせは、こちらの1本の後に出られる。待っている相手が居なければ譲らない。
  - **門を避ける作り方は無い**：門を選ぶ引数は外に出していない。入らないのは、待ちを差し替えた組み立て（相手が作り物の試験）だけ。
    通信の出口が本物のまま待ちだけを差し替える組み立ては、`AppServiceContainer` が断る。
  - 門のファイルが開けない（書けない場所・壊れた権限）ときは、門なしで進み、ログに1回残す（止めると BOOTH から何も取れない。アプリ1本の中の決め事は守る）。
  - 実測（2026-09-30・`experiments/BoothGateProbe`。相手は手元の作り物のサーバ）：1本のときの上乗せは1回の問い合わせあたり 70〜80 マイクロ秒（間隔の 0.005%）。
    2つのプロセスで続けて出すと、前の応答が終わってから次が届くまで最小 1500 ms・重なって届いた物は無し・交互。数字と経緯は `docs/history/booth-machine-gate-2026-09-30.md`。
- **転送（3xx）も門を通す**（2026-10-06・外部の点検）。出口の自動の転送は切る（`BoothClient.CreateHttpClient`。アプリ・Cli・experiments はこれで組む）。自動の転送は通信の層の中で先へ出るので、門も間隔も通らなかった。
  - 301・302・303・307・308 を受けたら `Location` を読み（相対なら今の先から）、**https で、booth.pm・その下（ショップ）・booth.pximg.net（画像）**だけ、門を通して取り直す（間隔を空けて・優先度は元のまま）。
  - たどるのは5回まで（BOOTH の転送は1〜2段）。許さない先・回数の超え・先の読めない転送は、失敗（`IsRejected`）で返し、再試行しない（取り直しても同じ）。
  - 出口が勝手に転送していた応答（頼んだ先と応答の先が違う）は受け取らずに捨て、ログに残す（組み立ての付け忘れの見張り）。
- **期限は1本30秒、送ってから本文を読み終えるまで**（2026-10-06）。前は HttpClient の期限で、見出しを先に受ける読み方では本文に効かず、本文が止まると PC の門を握ったまま戻らなかった。
  期限は送る直前から数える（門の順番待ち・間隔の待ちは入れない）。切れたら「タイムアウトしました」（`IsUnreachable`）で、門は必ず放す。
  - **受ける量の上限**：文字（JSON・ページ・検索）は8MB、画像は20MB（バナーの実測の最大4MBの5倍）。長さを名乗っていれば読む前に、名乗らなければ上限を超えた所で受けるのをやめて捨てる（`IsRejected`）。
- **ブラウザを名乗らない**：`Chmonos/0.1 (personal library manager)`（ブラウザの顔をした自動の通信はスクレイパーと見られ得る。2026-09-14 にアプリの名前と一緒に `BoothAssetManager/0.1` から改名）。
- 保存する説明から script・埋め込み・フォーム・イベントの属性・http 以外の URL を削る（セキュリティソフトの検査で怪しまれないように）。
- 配布物の exe は本体の1つだけ（用途の分からない exe・メモリを書き出す道具は怪しまれやすい）。
- ログイン（cookie）を使う通信はしない。
- **BOOTH 以外への通信は YouTube だけ**（ユーザ指示 2026-09-14：商品ページの動画の欄に絵とタイトルを出す）。
  - **欄を開いたときだけ**（人の操作）。裏では取りに行かない。
  - タイトルは鍵の要らない oEmbed（`youtube.com/oembed`）。1本ずつ、BOOTH と同じアプリの名前で名乗る（`YouTubeInfo`）。
    通信の失敗（429・5xx を含む）は覚えない。
  - **取れたタイトルは `video-titles.json` に控え、30日以内なら聞き直さない**（ユーザ判断 2026-09-14：何の動画か分からないので控える）。
    30日を過ぎたら欄を開いたときに聞き直し、非公開・削除（400・401・403・404）なら控えを消す。
    30日を過ぎた控えは、書くときと起動したときにも消す（`VideoTitleBook`・`UiCommand.RememberVideoTitle`・`PruneVideoTitles`）。
    YouTube の開発者ポリシーの「API で取ったデータは30日まで」に合わせた（`docs/research/youtube-terms.md`）。
  - 絵は動画の ID から決まる `i.ytimg.com/vi/{ID}/mqdefault.jpg` を画面が直に読む。**保存しない**
    （利用規約は、許された場合を除いてダウンロードを禁じている。同じ調べ）。

## 優先度の梯子

```
人が押した通信 ＞ 指名された画像 ＞ ①② ＞ ③ ＞ ④ ＞ ⑤ ＞ ⑥ ＞ ⑦
```

- 優先度は `BoothClient.Prioritize(…)` の範囲（`AsyncLocal`）。`CommandHandler` が入口で「人が押した」を張るので、**画面から押した操作は全部が最上位**。開いただけで取る物はハンドラーの中で下げる（ショップのアイコン＝⑥、バナー＝指名された画像）。
- **未確定の「このIDで登録」の残りの画像は⑤の段**（メモ60 案B・ユーザ判断 2026-10-06）：登録は商品JSON・商品ページ・1枚目・アイコンまでを人が押した段で取り、残りの画像は登録の直後にその商品だけを⑤（`Gallery`）で裏に頼む。起動時の裏の作業と同じく人の操作ではないので「人が押した」優先度を掛けない（命令の中から頼むが、段を⑤へ下げる）。届かない失敗が3件続いたら残りは問い合わせず、取らなかった絵は次の起動の⑤が拾う。`docs/spec/id-resolution.md`
- 割り込みはリクエストの切れ目で起きる。再取得は JSON と HTML が揃ってから1回だけ保存するので、途中で譲っても中途半端な状態は残らない。
- 取り込みの段の中身は `docs/spec/import.md`。

## 起動時の裏の作業

1. 対応アバターの検出し直し（③。登録簿の `detectedAt` から設定「対応アバターを検出し直す間隔」（既定90日）を過ぎたときだけ。検出は取り込み・ボタン・手で紐付けた後にしか走らず、⑦が取り直した説明文や手で直した別名が取り込まない間は効かないため。2026-09-16 ユーザ判断。書き換えた商品があれば一覧を組み直す）
2. ⑤ 前の取り込みで取り切れなかった画像（`ImageBacklog`：`Booth.Images` の件数とディスクの差で対象が決まる。フラグを持たない）
3. 持っていないアバターの1枚目（`images/_avatars/{ID}/`。登録簿の `ImageUrl` が無ければ商品 JSON を取り直す。持っているアバターは商品の1枚目を使い、控えは消す）
4. ⑦ 期限の来た商品の取り直し（`DueRefresh`）

- **段ごとに受け止め、落ちたらログに残して次の段へ**（1段の失敗で残りを飛ばさない）。止まるのは閉じたときだけ。
- 設定「起動したとき、裏で取得を始める」1つで全部切れる（読むのは起動時だけ。途中で切っても始まった分は続く）（従量制の回線・静かにしたい場面。勝手に動いて見える物には止める手段が要る）。
  **止まるのは BOOTH へ行く段だけ**：通知の上限・ページの作りの確認・手で直した JSON の確認は通信しないので、切っていても走る（2026-10-05。前は丸ごと止まっていた。`MainViewModel.RunLocalChecksAsync`）。
- 画像を保存しない設定なら①〜③だけ。関門は梯子・`ImageBacklog`・`ImagePipeline` の各入口の3層（入口を足したときに漏れないように）。
- 人の操作ではないので `UiCommand` を通さない。
- 監視対象フォルダ：起動時に新しいファイル（`scan-cache.json` のパス・サイズ・更新日時で判定。ハッシュは計算しない）を**見つけるところまで**。取り込みを始めるかは設定（既定は切。始めても画面は切り替えない）。設定を入れると、前回途中で止まった取り込みの続きも一緒に始める（`import.md`）。
  外付けを外している間は「増えていない」とみなす。監視対象は人が「はい」と答えたフォルダだけ（取り込み元の履歴 `ImportFolders` とは別に持つ）。
  **「知らせなくてよい」を押したら、その顔ぶれの間は黙る**（ユーザ判断 2026-09-21・G16）。覚えるのは新着の一覧の指紋**1つだけ**
  （ファイルを1件ずつ覚えると、監視フォルダの大きさに比例して記録が膨らむ）。何か増えれば顔ぶれが変わるのでまた出る。
- **「起動したとき、裏で取得を始める」で止まらないもの**（ユーザ判断 2026-09-21・G10/G14）：押して始める取得、取り込みの続きの取得（アバターの画像）、
  画面を開いたときに取るもの（ショップのアイコンとバナー）。**人が開いた・押したものは止めない**という切り分けで、説明にもそう書く。
- **⑦（期限の取り直し）は1回の起動で 200 件まで**（ユーザ判断 2026-09-21・G15）。1件2リクエスト×1.5秒で約10分。
  一時失敗では予定日を動かさない決まりなので、圏外が続くと毎回全件を叩き直していた。**予定日は動かさない**——
  こちら側の都合（圏外）で本当の更新の取り直しが遅れるため。残りは次の起動へ回る（期限の古い順なので古い物から片付く）。
- **見つからなくなった日時の見回り**（ユーザ判断 2026-10-05。`MissingMarksSweep`・`MainViewModel.StartMissingMarksSweep`）：窓を出した後に裏で一度、記録しているファイルとフォルダの場所を全部見て `missingSince` を付け外しする。
  前は取り込みと使おうとした画面でしか書かず、取り込まずに使っている間は、手で消した zip が印・検索の条件・統計に出なかった。
  決まりと部品は取り込みの見回りと同じ（ドライブごとにまとめて見る・つながっていないドライブの上は書かない・根の答えは3秒で打ち切る・変わった商品だけ商品ごとの錠の中で今の値に当てる・控えた文字に来た別のディスクと権限の無い場所は書かない・場所は外さないが、同じ中身のほかの場所に在ると確かめたら無いと確かめた場所は外す。`import.md`）。在るフォルダの見た日時（`lastSeenAt`）は、取り込みと同じく空のとき・また見つかったときだけ入れる（見るたびには書かない。2026-10-05）。
  BOOTH に問い合わせないので、設定「起動したとき、裏で取得を始める」を切っていても見る。**見回りは1本ずつ**：取り込みの見回り（最初の周回のフォルダの数え直しを含む）と番を合わせ、後から来た方は今の値と同じなら書かない。
  書いた商品は検索の写しへ知らせる（50件までは1件ずつ差し替え、超えたら全件を読み直す。1件ずつは毎回絞り込みをかけ直すため）。
- **前の起動で終わらなかった未確定の登録の列**（`registration-queue.json`。メモ60）は、窓を出した後に同じ順で続ける。人が押した登録なので上の裏の作業とは別の列で、優先度は押したときと同じ（設定「起動したとき、裏で取得を始める」でも止めない）。`docs/spec/id-resolution.md`
- 起動時に10分より古い `.tmp` を消す（保存先の全体を再帰でたどるので、窓を出した後に裏で・書き込みの門の中で。2026-09-24）。一時展開フォルダの消し残りを消す（この保存先の置き場所 `%TEMP%\Chmonos\unpacked-{保存先の印}` だけ。保存先の違う別のアプリの分は消さない。`docs/spec/unity.md`）。

## 取れなかった物・変わった物

- 404だけを「非公開」に数える（3回連続）。一時エラーは数えず、同じ実行で2回まで（2秒→8秒）試す。
- 一時エラーのうち**応答が1つも来なかった物（接続できない・タイムアウト）**は `BoothFetchResult.IsUnreachable`、**5xx** は `IsServerError` で見分ける（2026-09-29）。
- **届かない失敗（応答が無い・5xx）が3件続いたら、その回の残りは問い合わせない**（ユーザ判断 2026-09-29）。数えるのは `BoothOutageWatch` 1つで、どこも同じ決まり：
  混ざっても続けて数え、BOOTH が意味のある物を返したら（取れた・404・読めない応答）数え直す。429 はこちらの出し過ぎなので数えない（数え直す）。
  打ち切りは問い合わせを減らす向きなので、1本ずつ・1.5秒の決め事には触れない。
  - 取り込みの①②：残りを「続きから」に残し、画面は理由で言い分ける（ネット／BOOTHの不調。`docs/spec/import.md`）。
  - 取り込みの画像の段（④⑤⑥）：①②とは別に数える（画像は別の置き場から来るので、片方だけ落ちていることがある）。
  - 対応アバターの検出（取り込みの③・「対応アバターを検出する」・起動時の検出し直し）：問い合わせなかったIDは登録簿に書かず、次の検出でまた試す。
    落ち着くまで繰り返す検出の全体で1つ数える。画面の文は理由で言い分ける（`docs/spec/avatars.md`）。起動時の検出し直しは画面にもログにも出さない。
  - 起動時の裏の作業：⑤（残りの画像）・持っていないアバターの画像・⑦（期限の取り直し）が段ごとに数える。
    ⑦は取り直しの結果で数える（`RefreshOutcome.Unreachable`・`ServerError`。BOOTHに無い商品・手元に無い商品は問い合わせていないので数えない）。
  - ショップ一覧を開いたときに取るアイコン（`ShopService.SyncIconsAsync`）：1回の取得で数える（点検 2026-09-29・8）。
    「確かめた」（`IconCheckedAt`）を書くのは BOOTH が答えた店だけ（取れた・404・読めない絵）。一時的に取れなかった店と打ち切り後の店には書かず、次に開いたときにまた取りに行く
    （書くと、つながった後も確かめ直す日まで休んでしまう）。結果は `ImagePipeline.FetchShopIconAsync` の `ShopIconFetch` で分ける。
  - 画像は、問い合わせなかった物に印（`.retry`・`.missing`）を置かない。「まだ取っていない」扱いのまま、次の起動の⑤か「足りない情報を取得」で取る。
    ⑦は予定日を動かさない（一時失敗と同じ）ので、残りは次の起動で期限の古い順にまた来る。
  - 裏の作業は窓を出さないので、打ち切ったことは `logs/app.log` に残す（どの段か・理由）。
- 200 でも読めない応答（JSON でない・型が変わった）は**一時失敗**として扱い、ログに残す（`BoothItemMapper.TryMap`）。
  ⑦は1件ずつ受け止めて次へ進む（1件が投げると残りが止まり、期限の古い順なので毎回同じ商品で止まっていた）。
  取り直し（⑦・人が押した物）で読めなかったときは、**予定日だけ普段の間隔で進める**（`RefreshOutcome.Unreadable`。2026-09-23）。
  BOOTH は応答しているので圏外の一時失敗とは違い、動かさないと毎回の⑦の先頭で同じ商品に1本を使い続けた。
  booth・取得日時・404 の回数には触れない。人が押したときは「次回に再試行します」ではなく、読めなかったと言う。
- 取れなかった画像の印 `{ハッシュ}.missing` は、その商品の JSON を取り直したときに外す（日数では外さない）。
- ⑦：7日±3日。連続404が3回以上なら30日。変わっていたら `ItemUpdated`（販売終了・価格・バリエーション・画像・商品名・説明文の見出し。スキ数は知らせない。同じ商品の未読があれば重ねる。import.md ⑦）。対応アバターの節が読めなくなったら `PageStructureChanged`。`NotifyOnUpdate`（商品ごと・既定オン）がオフなら知らせない。

  **数えるのは②（商品ページ）を取った商品だけ**（説明のファイルが在るもの。ユーザ指摘 2026-09-22）。
  説明文は商品JSON（①）から入り、見出しはHTMLからしか入らないので、①だけ済んだ商品は必ず「読み取れなかった」ように見える——

## 通信の見せ方

- 常設の1行に「今 BOOTH に何をしているか」だけを出す（取り込みの反映など手元の話は混ぜない）。押すと取り込み画面へ。
- 取り込み画面の進捗：①② は件数のバー、④「6. サムネイルを取得。取得できたものから一覧に表示されます」（編集は③が終われば、サムネイルを待たずにできる）、⑤「ギャラリーを取得しています。」、残り時間の見込みを3つ（この段の残り／編集できるまで／画像を取り終わるまで。残りの問い合わせの数 × 直近20件の実測）。
- **見込みは、分かっている物にだけ数字を付ける**（ユーザ指示 2026-09-21：「「編集できるまで」という文言が嘘なのが良くない」）。
  - 残りの問い合わせは**段ごとに数える**（`ImportWorkSet.RequestsLeft` は ①②④⑤⑥ の5つ）。まとめて1つにすると「この段の残り」が出せず、④の最中に④⑤⑥全部の時間が出ていた。
  - ③で何件問い合わせるかは③に入るまで分からないので、**①②の間は「編集できるまで」を時間で出さず、「あと ○○ で分かります」**（＝①②の残り。これは正確に言える）を出す。
  - 画像の数は**②が終わった時点で数える**。以前は周回の最後（③の後）だったので、①②③の間は0のままで「画像を取り終わるまで」が「編集できるまで」と同じ数字になっていた。①②の間は「商品ページを取り終わると分かります」と書く。
- **1件あたりの実測は①と②でほぼ変わらない**（実測：①1.66秒・②1.80秒。本文は9KBと111KBで12倍違うが、1.5秒の間隔にほぼ吸収される。`experiments/FetchTimingProbe`）。段ごとに平均を分ける必要は無い。
- ①で商品ができた時点で検索・ショップ・件数に出す（絵の無いカードは「画像を取得中」）。**編集は③が済むまで出さない**（編集の件数・列・商品ページのその場で直す操作を塞ぎ、理由と残り時間を添える。見る・送る・星は塞がない）。
  一覧へ入れる読み直しは**10秒に1回まで**。間引きを飛ばすのは③が済んで編集に出せる商品ができたとき（③待ちが減ったとき）だけ（2026-09-24。増えたときも飛ばしていて、①の間は1件ごと＝約1.5秒ごとに全件を読み直していた）。

## 失敗の書き残し

- `logs/app.log`（保存先の中）に書き足す。1MB を超えたら `app.old.log` へ回して2つだけ残す。**ログが書けなくても投げない**。
- 残す物：裏の作業の失敗（起動時の段・監視・取り込みの裏・手で紐付けた後の検出・unitypackage の読み込み・ドライブ文字の組）、画面が例外を受け止めて文に出した所、`UnobservedTaskException`・`AppDomain.UnhandledException`・画面のスレッドの例外。
- 残さない物：コマンドが「できなかった」を返し、画面に理由が出る所（期待した失敗）。初回起動の窓の失敗（ログの置き場がまだ無い）。
- **待たない作業は `〜.Forget()`**（`_ = 〜Async()` は書かない）：落ちたらその場で呼んだファイルとメソッドの名前を添えてログへ。`Task<CommandResult>` が Failed を返したときも残す（画面が受け取らないので）。
