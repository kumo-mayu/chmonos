# 裏の作業・通信・失敗の書き残し（今の決め事）

> **要点**：BOOTH への問い合わせは全部 `BoothClient` の1つのゲート（1本ずつ・1.5秒以上）を通り、優先度は1本の梯子で決まる。
> 起動時に自動で始めてよいのは手元の JSON だけで対象が決まる作業（⑤画像・持っていないアバターの1枚目・⑦期限）だけで、フォルダの走査（①②）は人が押して始める。
> 失敗は黙って飛ばさず `logs/app.log` に残す。
>
> **コード**：`Core/Booth/BoothClient.cs`・`BoothPriority`・`PriorityGate`、`Core/Services/ImageBacklog`・`DueRefresh`・`BoothChanges`・`NotificationService`・`FolderWatch`、
> `Core/Diagnostics/AppLog.cs`（`LogFile`）、`App/FireAndForget.cs`（`Forget()`）、`App/ViewModels/MainViewModel*.cs`（`RunBackgroundStageAsync`）
>
> **経緯**：`docs/history/import-concurrency.md`（梯子・印・⑦）、`docs/history/tech-debt-2026-09-14.md` 2-1〜2-3、`docs/research/antivirus.md`（名乗り・配布物）

## 通信の決め事

- **1本ずつ、1.5秒以上空ける**（設定画面の下限も 1500ms）。並列化しない・間隔を縮めない。`BoothClient` を通らない通信を書かない。
- 429 を受けたら以降の間隔を倍にしていく（上限30秒）。Retry-After は60秒まで付き合い、超えたらその1本は次回に回す。
- **Retry-After で待てと言われたら、他の問い合わせも待つ**（ユーザ判断 C15）。待ちはゲートの中で行うので誰も追い越さない（中断は効く）。
  60秒を超える指示でも、次の問い合わせは60秒は待つ。503 などに Retry-After が付いたときも 429 と同じく間隔を広げる。
- 最後の問い合わせの時刻は**送った後はどう抜けても**（中断・想定外の例外でも）更新する。更新が漏れると次の1本が間隔を空けずに出る。
- **ブラウザを名乗らない**：`Chmonos/0.1 (personal library manager)`（ブラウザの顔をした自動の通信はスクレイパーと見られ得る。2026-09-14 にアプリの名前と一緒に `BoothAssetManager/0.1` から改名）。
- 保存する説明から script・埋め込み・フォーム・イベントの属性・http 以外の URL を削る（セキュリティソフトの検査で怪しまれないように）。
- 配布物の exe は本体の1つだけ（用途の分からない exe・メモリを書き出す道具は怪しまれやすい）。
- ログイン（cookie）を使う通信はしない。
- **BOOTH 以外への通信は YouTube だけ**（ユーザ指示 2026-09-14：商品ページの動画の欄に絵とタイトルを出す）。
  - **欄を開いたときだけ**（人の操作）。裏では取りに行かない。
  - タイトルは鍵の要らない oEmbed（`youtube.com/oembed`）。1本ずつ、BOOTH と同じアプリの名前で名乗る（`YouTubeInfo`）。
    通信の失敗（429・5xx を含む）は覚えない。
  - **取れたタイトルは `video-titles.json` に控え、30日以内なら聞き直さない**（ユーザ判断 2026-09-14：何の動画か分からないので控える）。
    30日を過ぎたら欄を開いたときに聞き直し、非公開・削除（400・401・403・404）なら控えを消す。
    30日を過ぎた控えは、書くときと起動したときにも消す（`VideoTitleBook`・`UiCommand.RememberVideoTitle`・`PruneVideoTitles`）。
    YouTube の開発者ポリシーの「API で取ったデータは30日まで」に合わせた（`docs/research/youtube-terms.md`）。
  - 絵は動画の ID から決まる `i.ytimg.com/vi/{ID}/mqdefault.jpg` を画面が直に読む。**保存しない**
    （利用規約は、許された場合を除いてダウンロードを禁じている。同じ調べ）。

## 優先度の梯子

```
人が押した通信 ＞ 指名された画像 ＞ ①② ＞ ③ ＞ ④ ＞ ⑤ ＞ ⑥ ＞ ⑦
```

- 優先度は `BoothClient.Prioritize(…)` の範囲（`AsyncLocal`）。`CommandHandler` が入口で「人が押した」を張るので、**画面から押した操作は全部が最上位**。開いただけで取る物はハンドラーの中で下げる（ショップのアイコン＝⑥、バナー＝指名された画像）。
- 割り込みはリクエストの切れ目で起きる。再取得は JSON と HTML が揃ってから1回だけ保存するので、途中で譲っても中途半端な状態は残らない。
- 取り込みの段の中身は `docs/spec/import.md`。

## 起動時の裏の作業

1. 対応アバターの検出し直し（③。登録簿の `detectedAt` から設定「対応アバターを検出し直す間隔」（既定90日）を過ぎたときだけ。検出は取り込み・ボタン・手で紐付けた後にしか走らず、⑦が取り直した説明文や手で直した別名が取り込まない間は効かないため。2026-09-16 ユーザ判断。書き換えた商品があれば一覧を組み直す）
2. ⑤ 前の取り込みで取り切れなかった画像（`ImageBacklog`：`Booth.Images` の件数とディスクの差で対象が決まる。フラグを持たない）
3. 持っていないアバターの1枚目（`images/_avatars/{ID}/`。登録簿の `ImageUrl` が無ければ商品 JSON を取り直す。持っているアバターは商品の1枚目を使い、控えは消す）
4. ⑦ 期限の来た商品の取り直し（`DueRefresh`）

- **段ごとに受け止め、落ちたらログに残して次の段へ**（1段の失敗で残りを飛ばさない）。止まるのは閉じたときだけ。
- 設定「起動したとき、裏で取得を始める」1つで全部切れる（読むのは起動時だけ。途中で切っても始まった分は続く）（従量制の回線・静かにしたい場面。勝手に動いて見える物には止める手段が要る）。
- 画像を保存しない設定なら①〜③だけ。関門は梯子・`ImageBacklog`・`ImagePipeline` の各入口の3層（入口を足したときに漏れないように）。
- 人の操作ではないので `UiCommand` を通さない。
- 監視対象フォルダ：起動時に新しいファイル（`scan-cache.json` のパス・サイズ・更新日時で判定。ハッシュは計算しない）を**見つけるところまで**。取り込みを始めるかは設定（既定は切。始めても画面は切り替えない）。
  外付けを外している間は「増えていない」とみなす。監視対象は人が「はい」と答えたフォルダだけ（取り込み元の履歴 `ImportFolders` とは別に持つ）。
  **「知らせなくてよい」を押したら、その顔ぶれの間は黙る**（ユーザ判断 2026-09-21・G16）。覚えるのは新着の一覧の指紋**1つだけ**
  （ファイルを1件ずつ覚えると、監視フォルダの大きさに比例して記録が膨らむ）。何か増えれば顔ぶれが変わるのでまた出る。
- **「起動したとき、裏で取得を始める」で止まらないもの**（ユーザ判断 2026-09-21・G10/G14）：押して始める取得、取り込みの続きの取得（アバターの画像）、
  画面を開いたときに取るもの（ショップのアイコンとバナー）。**人が開いた・押したものは止めない**という切り分けで、説明にもそう書く。
- **⑦（期限の取り直し）は1回の起動で 200 件まで**（ユーザ判断 2026-09-21・G15）。1件2リクエスト×1.5秒で約10分。
  一時失敗では予定日を動かさない決まりなので、圏外が続くと毎回全件を叩き直していた。**予定日は動かさない**——
  こちら側の都合（圏外）で本当の更新の取り直しが遅れるため。残りは次の起動へ回る（期限の古い順なので古い物から片付く）。
- 起動時に10分より古い `.tmp` を消す（保存先の全体を再帰でたどるので、窓を出した後に裏で・書き込みの門の中で。2026-09-24）。一時展開フォルダの消し残りを消す。

## 取れなかった物・変わった物

- 404だけを「非公開」に数える（3回連続）。一時エラーは数えず、同じ実行で2回まで（2秒→8秒）試す。
- 200 でも読めない応答（JSON でない・型が変わった）は**一時失敗**として扱い、ログに残す（`BoothItemMapper.TryMap`）。
  ⑦は1件ずつ受け止めて次へ進む（1件が投げると残りが止まり、期限の古い順なので毎回同じ商品で止まっていた）。
  取り直し（⑦・人が押した物）で読めなかったときは、**予定日だけ普段の間隔で進める**（`RefreshOutcome.Unreadable`。2026-09-23）。
  BOOTH は応答しているので圏外の一時失敗とは違い、動かさないと毎回の⑦の先頭で同じ商品に1本を使い続けた。
  booth・取得日時・404 の回数には触れない。人が押したときは「次回に再試行します」ではなく、読めなかったと言う。
- 取れなかった画像の印 `{ハッシュ}.missing` は、その商品の JSON を取り直したときに外す（日数では外さない）。
- ⑦：7日±3日。連続404が3回以上なら30日。変わっていたら `ItemUpdated`（販売終了・価格・バリエーション・画像・商品名。スキ数と説明文は知らせない）。対応アバターの節が読めなくなったら `PageStructureChanged`。`NotifyOnUpdate`（商品ごと・既定オン）がオフなら知らせない。
- 要確認（`notifications.json`）：既読にしても消さない。200件を超えたら古い既読か解消済みから捨てる（未読は捨てない）。上限は起動時にも当てる。R-18 を出さない設定でも要確認には出す。
- ⑦で変わっていたら、説明文は**見出し（セクション）ごとに**比べる。更新履歴の見出しの変化だけを強い通知にする。見出しを持たない商品は説明文そのものを比べる（2026-09-18 に設計へ合わせた）。
- バリエーション（`variation`）の結び付きがBOOTH側から消えた／戻ったら `OrphanVariationLink` / `VariationBackOnBooth`。
- 説明文はあるのに見出しが0件の商品が、最近取り直した中で8割を超えたら `PageStructureChanged`（14日・5件以上のときだけ見る）。読めるようになったら解消済みにする。
  **数えるのは②（商品ページ）を取った商品だけ**（説明のファイルが在るもの。ユーザ指摘 2026-09-22）。
  説明文は商品JSON（①）から入り、見出しはHTMLからしか入らないので、①だけ済んだ商品は必ず「読み取れなかった」ように見える——
  **取り込みを②の前で止めただけで、HTMLを1件も取っていないのに帯が出ていた。**

## 通信の見せ方

- 常設の1行に「今 BOOTH に何をしているか」だけを出す（取り込みの反映など手元の話は混ぜない）。押すと取り込み画面へ。
- 取り込み画面の進捗：①② は件数のバー、④「サムネイルを取得しています。取得できたものから編集できます。」、⑤「ギャラリーを取得しています。」、残り時間の見込みを3つ（この段の残り／編集できるまで／画像を取り終わるまで。残りの問い合わせの数 × 直近20件の実測）。
- **見込みは、分かっている物にだけ数字を付ける**（ユーザ指示 2026-09-21：「「編集できるまで」という文言が嘘なのが良くない」）。
  - 残りの問い合わせは**段ごとに数える**（`ImportWorkSet.RequestsLeft` は ①②④⑤⑥ の5つ）。まとめて1つにすると「この段の残り」が出せず、④の最中に④⑤⑥全部の時間が出ていた。
  - ③で何件問い合わせるかは③に入るまで分からないので、**①②の間は「編集できるまで」を時間で出さず、「あと ○○ で分かります」**（＝①②の残り。これは正確に言える）を出す。
  - 画像の数は**②が終わった時点で数える**。以前は周回の最後（③の後）だったので、①②③の間は0のままで「画像を取り終わるまで」が「編集できるまで」と同じ数字になっていた。①②の間は「商品ページを取り終わると分かります」と書く。
- **1件あたりの実測は①と②でほぼ変わらない**（実測：①1.66秒・②1.80秒。本文は9KBと111KBで12倍違うが、1.5秒の間隔にほぼ吸収される。`experiments/FetchTimingProbe`）。段ごとに平均を分ける必要は無い。
- ①で商品ができた時点で検索・ショップ・件数に出す（絵の無いカードは「画像を取得中」）。**編集は③が済むまで出さない**（編集の件数・列・商品ページのその場で直す操作を塞ぎ、理由と残り時間を添える。見る・送る・星は塞がない）。
  一覧へ入れる読み直しは**10秒に1回まで**。間引きを飛ばすのは③が済んで編集に出せる商品ができたとき（③待ちが減ったとき）だけ（2026-09-24。増えたときも飛ばしていて、①の間は1件ごと＝約1.5秒ごとに全件を読み直していた）。

## 失敗の書き残し

- `logs/app.log`（保存先の中）に書き足す。1MB を超えたら `app.old.log` へ回して2つだけ残す。**ログが書けなくても投げない**。
- 残す物：裏の作業の失敗（起動時の段・監視・取り込みの裏・手で紐付けた後の検出・unitypackage の読み込み・ドライブ文字の組）、画面が例外を受け止めて文に出した所、`UnobservedTaskException`・`AppDomain.UnhandledException`・画面のスレッドの例外。
- 残さない物：コマンドが「できなかった」を返し、画面に理由が出る所（期待した失敗）。初回起動の窓の失敗（ログの置き場がまだ無い）。
- **待たない作業は `〜.Forget()`**（`_ = 〜Async()` は書かない）：落ちたらその場で呼んだファイルとメソッドの名前を添えてログへ。`Task<CommandResult>` が Failed を返したときも残す（画面が受け取らないので）。
