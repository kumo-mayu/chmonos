# 画面の文言の書き方（今の決め事）

> **要点**：1つの文言に載せるのは、その場でいちばん要ることを1つ（多くても2つ）。作り手の判断の理由・根拠の数字・経緯は画面に書かない。
> 吹き出しは1〜2文・40字まで。窓や空表示の本文は一文50字を目安に、80字まで（ユーザ判断 2026-09-24）。語は [ui-terms.md](ui-terms.md)。
>
> **道具**：`node tools/wording.mjs`（印の意味と使い方はスキル `ui-wording`）
>
> **経緯**：`docs/history/ui-wording-2026-09-24.md`（AI らしさの点検と、この決め事を作った理由）、`docs/research/ui-wording.md`（2026-09-09 の総点検）
>
> **手本**：SmartHR のライティングの手引き（エラーは事象・原因・対処）、Ubie の UX ライティングの手引き（日常語・一文80字以内・50字推奨・肯定で書く）、文化庁「公用文作成の考え方」（2022。一文を短く）

## 何を載せるか

これまでの決め事は「書く」方ばかりで、押すと何が起きるか・取り返し・次の手・行き先を、全部1つの文に入れていた。
その結果、1つの吹き出しに3〜4文が入り、読まれなくなった。ここでは**削る**方を決める。

- **1つの文言に載せるのは、次のうち、その場でいちばん要る1つ。多くても2つ。**
  - 何が起きるか（ボタン・メニューの名前と吹き出し）
  - 取り返しがつくか（確認の窓）
  - 次に何をすればよいか（空表示・エラー）
- **作り手の判断の理由・根拠の数字・経緯は画面に書かない。**docs（spec・history）に書く。
  - 書かない例：「〜を避けるため」「前は〜だった」「件数が少ないと数字が暴れるため」「1500ミリ秒より短くはできません（相手のサービスに負担をかけないため）」
  - コードのコメントは「なぜ」を書く（CLAUDE.md「書き方」）。**この決まりは画面の文には当てない。**使う人に要るのは作り手の理由ではなく、何が起きるかと次の手。
  - 書いてよい理由：押せない理由（「BOOTHに無い商品なので開けません」）と、失敗の原因（「ディスクの空きが足りません」）。これは使う人の次の手を決めるので、理由ではなく状態の説明。
- **文の終わりの括弧の補足は使わない。**要ることなら独立した1文にし、要らないなら削る。数・キー・単位だけの括弧（「未確定（{n}）」「（Ctrl+F）」）はよい。
- **見れば分かることは書かない**（[ui-dialogs.md](ui-dialogs.md)「どこに言うか」）。
- **迷ったら削る。**削って困る情報が無いかは、下の「正確さを落とさない」で確かめる。

## 長さ

| 置き場 | 目安 |
|---|---|
| ボタン・メニュー・見出し | 文にせず句で書く（「商品情報を取り直す」「表示順」） |
| 吹き出し（ツールチップ） | 1〜2文・40字まで |
| 窓の本文・空表示・画面の中の説明 | 一文50字を目安、80字まで。3文を超えるなら削るか、画面の置き場所を分ける |
| 1行の知らせ（「〜しました。」） | 1文 |

## 書き方

- **です・ます**で、短く言い切る。「〜かもしれません」「〜ようです」は、本当に分からないときだけ使う。
- **否定に読める言い方をしない。**肯定で書ける所は肯定で書く（「既にライブラリにある商品です」は「登録できない」に読めた）。
- **語は [ui-terms.md](ui-terms.md) に従う。**普通の Windows のソフトで見る語にする。表に無い語を使うときは、先に表に書き足す。
- **内部の言葉を画面に出さない**（item・appTag・BoothID・variation・マスタ）。.NET の例外の文も出さない（[ui-empty-and-errors.md](ui-empty-and-errors.md)）。
- **アプリ自身を主語にしない。**「こちらで決められない」「相手にします」は主語を省くか、対象を名前で書く。
- **Markdown の記号を残さない**（`**`・`` ` ``・行頭の `- `）。強調したいときは画面の太字を使う。
- **数と単位の間に空白を入れる**（「{n} 件」）。英字と日本語の間には入れない（「BOOTHで開く」「Unity側」）。

## 要素ごとの型

良い例・悪い例はスキル `ui-wording` にある。

| 要素 | 型 |
|---|---|
| ボタン・メニュー | 押すと何が起きるかが分かる名前（「商品情報を取り直す」）。行き先がアプリの外なら分かるようにする（「BOOTHで開く」） |
| 見出し | 名詞で短く（「表示順」「監視しているフォルダ」） |
| 吹き出し | ボタンの名前で足りない1点だけ。取り返しのつかない操作なら、そのこと |
| 確認の窓 | 1行目に何が起きるか、2行目に取り返しがつくか。ボタンは動作の名前で、やめる側は「キャンセル」（[ui-dialogs.md](ui-dialogs.md)） |
| エラー | 事象・原因・対処（「保存できませんでした。ディスクの空きが足りません。空きを作ってからもう一度お試しください。」）。削るときは原因から削り、次に対処を削る。何が起きたかは最後まで残す |
| 空表示 | 読み込み中・探して0件・1つも無い、の3通り（[ui-empty-and-errors.md](ui-empty-and-errors.md)）。次に何をすればよいかを1文で |
| メモの欄 | **用途を書かない**（メモ10-② 2026-10-02。自由に書いてもらう）。入力欄の中の薄い案内は「メモ」。説明を置くなら保存の仕方だけ（「打ち終えると保存されます。」） |
| 進み具合 | 「〜しています…」と n/N |
| 済んだ知らせ | 「〜しました。」の1文。件数を添えるなら文の中に入れる（「{n} 件を追加しました。」） |

## 正確さを落とさない

短くするときに、次のものを落とさない。

- **取り返しの情報**：戻せない操作の「元に戻せません」、戻せる操作の戻し方。
- **通信やダウンロードが起きるか**：「BOOTHに問い合わせます」「商品のファイルはダウンロードしません」。
- **押せない理由と、失敗の原因**（上の「書いてよい理由」）。
- **意味**：言い換えた後の文が、同じ操作・同じ結果を指しているか。

## 前からある決まり

- 取り返しのつかない操作には、取り返しがつくかを書く。空表示とエラーには、次にやることを書く。
- ボタンは押すと何が起きるかが分かる名前にする（「今すぐ取り直す」→「商品情報を取り直す」、「はい／いいえ」→「商品を開く」「画像として追加」）。
  確認は問いの形にし、どちらの意図か分からないから聞いているときは既定のボタンを置かない。
- 押しても何も起きないように見える物を作らない（結果は必ず知らせる。効かない選択肢は表示しないか、押せない理由を添える）。
