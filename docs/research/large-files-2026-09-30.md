# 大容量のファイルを扱ったときの安定性と引っかかり（2026-09-30）

> **要約**
> - **目的**：大きな zip・中身の多い zip・重い unitypackage・大量のファイルを扱ったときに、落ちる・固まる・誤った表示・片付かない所が無いかを測る（ユーザ指示「大容量のファイルを扱った時の動作の安定性や引っかかりなども確かめておいてください」）。
> - **結果**：取り込み・フォルダビュー・unitypackage の読み取り・一時展開は、このPCでは固まらず、メモリも目標の範囲だった。
>   **重いのは1か所**：未確定の画面で、中身が数万件の zip の行を選ぶと画面が止まる（7万件で約49秒・メモリが約1GBまで上がる。5千件でも約2秒）。
>   ほかに、取り込みの走査中に閉じると次の起動で何も言わない、一時展開に進み具合と中止が無く2回押すと誤った文が出る、壊れた zip が普通の未確定と見分けられない、読めないフォルダを黙って飛ばす、がある。
> - **2・3（2回押す所）・5 は 2026-09-30 に直した**（各節の「直した」）。ほかは直すかをユーザが決める。
> - **6・7 は測って直した**（2026-09-30。末尾の「問題6・7を測って直した」）：取り込み中の止まりは 1MB の配列をファイル1件ごとに作っていたせい、残るメモリは未確定の数え直しのゴミだった。
> - **注意**：このPCはメモリが 64GB で、作り物のファイルは作った直後なのでキャッシュに載っていた。ハッシュと展開の速さは**ディスクの速さではない**（HDD や USB の外付けではずっと遅い）。

## 見つけた問題（重い順）

### 1. 未確定で中身の多い zip の行を選ぶと、画面が止まってメモリが戻らない（確か）

- 再現：中身7万件の zip を取り込み、未確定を開き、その行を選ぶ（UI Automation を使わずキーの押下だけでも同じ）。
- 起きたこと：約49秒、画面が何も受け付けない。作業セットが 385MB から約1GB に上がり、別の行へ移っても戻らない（移るときにまた約24秒止まった）。中身5千件でも約2秒止まる。
- わけ：「このファイルについて分かっていること」の中身の一覧が、仮想化していない `ItemsControl`（`ScrollViewer` の中）で、全件の `TextBlock` を作る（`Views/ResolveView.xaml` の `SelectedContents`）。
- 案：一覧を仮想化する（`VirtualizingStackPanel` と `ScrollViewer.CanContentScroll`、または `ListBox`）か、先頭の数百件だけ出して「ほか n 件」とする。

### 2. 取り込みの走査中に閉じると、次の起動で何も言わない（確か）

- 再現：大きなフォルダを取り込み、「2. 商品IDを解決」の途中（7秒後）で窓を閉じ、起動し直す。
- 起きたこと：「前回は…中断しました」の帯が出ない。取り込み対象も空に戻る（`import-state.json` は `targets` が空のまま）。走査の控えは10秒ごとに書くので、閉じる前の10秒未満の分はハッシュを取り直す。
- 大きなライブラリを HDD で読むと、この段が一番長い（数十分になり得る）ので、閉じた人は続きがあることに気付けない。
- 案：①に入る前でも、対象を積んだ時点で `import-state.json` に対象を書き、帯を出す。閉じるときに走査の控えを書く。
- **直した（コミット 15aef6f）**：わけは、記録を書くのが①で1件取れたときだけで、走査・ID の特定の間は取り込みの始めに書いた空の記録（取れなかった商品の引き継ぎだけ）のままだったこと。周回が走査に入る前に対象と `scanning` を書き、①に入るところで外すようにした。帯は「前回の取り込みは途中で中断しました」、起動時の続き（`LaunchImportTargets`）も同じ対象を積む。走査の控えは今のまま10秒ごとなので、閉じる直前の10秒未満の分は続きでハッシュを取り直す（直していない）。

### 3. 一時展開に進み具合も中止も無く、2回押すと誤った文が出る（確か）

- 進み具合：押してからエクスプローラが開くまで、画面は何も変わらない（`ItemFileActions.UnpackAndOpenAsync`）。中止の道も無い（命令に取り消しを渡していない）。このPCでは 2.3GB が1秒で終わったが、遅いディスクでは数十秒、無言で待つ。
- 2回押す：展開の途中にもう一度「一時的に展開して開く」を押すと、2本目が1本目の書きかけのフォルダを消して展開し直し、1本目が「展開できませんでした。別のアプリがファイルを開いています。」で失敗する（アプリ自身が掴んでいるので、文が誤り）。最後にできたフォルダは中身がそろっていた。1回再現。
- 案：展開中は下の帯に進み具合（何 MB／何件）と中止を出し、同じ zip の展開を重ねない（走っていればそれを待つ）。
- **2回押す所を直した（コミット d39c58b）**：わけは、展開が錠を持たず、2本目が終わった印の無い書きかけを「途中で止まった展開」と見て消していたこと。展開先ごとの錠で1本ずつにし（2本目は1本目を待ち、終わった印を見てそのまま返す）、画面では同じ zip の2度目を弾く（エクスプローラを2つ開かない）。アプリ自身が掴む重なりが無くなったので「別のアプリ」の文は出なくなる。**進み具合と中止は足していない**（画面の見せ方が変わるのでユーザに聞く）。
- **進み具合と中止を足した（ユーザ判断 2026-09-30）**：展開の間、下の帯に「展開しています… 120.5 MB / 2.3 GB」と zip の名前、［中止］を出す。中止はファイルの途中でも効き、書きかけを錠の中で消す（止めた後に同じ zip を押すと最初から展開し直す）。決まりは `docs/spec/unity.md`。画面ではまだ確かめていない（試験は Core の中止・進み具合・片付けまで）。
- **残りを直した（ユーザ判断 2026-09-30「2B」「4A」）**：Unity へ送る前の取り出し（`ExtractEntry`）も書き出しの途中で中止が効くようにし、取り出しが長いときだけ送る帯に大きさの進み具合を出す。一時展開と取り出しが失敗したときは、書きかけをその場で消す（前は次に押すかアプリを閉じるまで残った）。画面と Unity ではまだ確かめていない（試験は Core の中止・失敗・片付け・やり直しと、文を替えるかの決まりまで）。

### 4. 壊れた zip が、普通の未確定と見分けられない（確か）

- 途中で切った zip と中身がでたらめの zip は、取り込みで何も言われずに未確定へ入る。未確定の画面でも「アーカイブの中身」が出ないだけで、壊れていることは分からない（ダウンロードが途中で切れた物に気付けない）。
- 同じ zip を商品ページで「一時的に展開して開く」と「ファイルが壊れているか、読めない形式です。ダウンロードし直すと直ることがあります。」と正しく出る。
- 案：取り込みで zip として開けなかった物を数えて結果に出し、未確定の行にも「zip として開けません（壊れているかもしれません）」を出す。
- **直した（コミット 2310fa7・ユーザ判断 2026-09-30）**：わけは、取り込みが zip を開けなかったこと（形式が合わない・ほかのアプリが開いている・権限が無い）を1つにまとめて握りつぶし、中身の一覧が空の未確定として置いていたこと。形式が合わなかったときだけ未確定の記録に `archiveBroken` を書き、行の札「壊れたzip」・選んだときの「このzipは壊れていて開けません。ダウンロードし直して、もう一度取り込んでください。」・取り込みの結果の「壊れていて開けないzipが n 件あります…」を出す。試験は途中で切った zip とでたらめな中身の zip を作って確かめた（`BrokenArchiveImportTests`）。**画面では確かめていない。**
  - 直していない：ダウンロード元の記録から商品に紐付いた壊れた zip（商品ページのファイルの欄に印が無い。ログにパスだけ残す）。目録が無事で中のデータだけが化けた zip（全部を解かないと分からない）。rar（中を開かない）。
- **商品に結び付いた分も直した（コミット 0d0da2f・ユーザ判断 2026-09-30「商品に結びついたzipが壊れていたら→A」）**：開けなかった事実を商品のファイルの記録（`LocalFileRecord.ArchiveBroken`）にも書き、商品ページ・編集画面のファイルの行に同じ札「壊れたzip」を出す（在る物にだけ。「見つかりません」「取り外しているドライブ」の行には出さない）。
  未確定から登録するとき・商品から外して戻すとき・BOOTH に無くて戻すときは記録ごと引き継ぐ。取り込みの結果は未確定の分と商品の分を行を分けて出し、商品の分は名前を1つ言う。
  同じ場所に落とし直すと、壊れた方の記録は消える（前の作りのままだと、壊れた方が「その場所に在る」として残り、札が消えない）。試験は `BrokenArchiveOnItemTests`。**画面では確かめていない。**
  - 直していない（ユーザ判断）：目録が無事で中のデータだけが化けた zip は、壊れていない物と同じ扱いのまま。検索のカードと一覧には印を出していない。

### 5. 読めないフォルダを黙って飛ばす（確か）

- 読む権限を外したフォルダは、取り込みの結果の「読めなかったファイル」にも数えられず、ログにも残らない（`FolderScanner.List` が空として返す）。
- 読めないファイル（権限を外した・別のプロセスが掴んだ）は「読めなかったファイルが 2 件あります（取り込めていません）。…閉じてから、もう一度取り込んでください。」と出て、ログにパスが残る。こちらは良い。
- 案：読めなかったフォルダも数えて結果に足し、パスをログに残す。
- **直した（コミット 2a1031b）**：わけは、1段ずつ並べる列挙に `IgnoreInaccessible` を入れていて、権限の無いフォルダが例外にならず空として返っていたこと（`List` の catch にも届いていなかった）。切って投げさせ、読めなかったフォルダのパスを走査の結果に持たせ、取り込みの結果に「フォルダが n 件」と数え、ログに1件ずつ残す。途中で消えたフォルダは数えない。

### 6. 取り込み中は商品ページを開くときの止まりが長くなる（確か・軽い）

- 取り込みが無いとき 222〜582ms、8万件の取り込み中は 777〜1,295ms。検索とフォルダビューへの切り替えは 100ms 以下のまま。
- **取り込み中に長くなる分を直した（`44b68e2`）**：わけはハッシュを取るたびに 1MB の配列を作っていたこと。取り込みが無いときの 200〜600ms は画面を組む時間で、直していない（末尾の「問題6・7を測って直した」）。

### 7. 未確定が数万件あると、取り込みの後にメモリが下がりきらない（確か・軽い）

- 8万件の取り込みの後、30秒たっても 485／385MB（目標 300〜400MB の上）。起動し直すと 323／227MB。未確定の一覧（`unresolved.json` 35MB）と走査の控え（22MB）を抱えている分と見られる（内訳は取っていない）。
- ばらばらの画像ファイルが多いフォルダを取り込み元にすると、1ファイルが1行の未確定になる（6万件のフォルダで6万行）。
- **直した（`4e41503`）**：残っていたのは抱えている物ではなく、ナビの札の未確定の数え直しが出したゴミだった。数え直しの後で返させる（末尾の「問題6・7を測って直した」）。

## 目標から外れた物

- メモリ 300〜400MB：場面3 の7万件の zip の行（約1GB、戻らない）・場面1 の8万件の取り込みの後（485／385）・場面2 の取り込み中に画面を回したとき（最大 628／529）・場面8 の1周目（637／551）と各周の山（約430／335）。
- 固まり 33ms：場面3 の7万件（約49秒）・5千件（約2秒）・取り込み中の商品ページ（最長 1.3秒）・未確定を開く（最長 420ms）・フォルダビューを開く（388ms）。商品ページを開くときの 200〜600ms は取り込みが無くても出る。

## 良かった所

- 4.5GB の Zip64・2.3GB の1ファイル・7万件の Zip64 を、どれも取り込み・一覧・商品ページで正しく扱えた（大きさは「4.5 GB」「2.1 GB」と出る）。
- 取り込みの中断は 2.3GB のハッシュの途中でも 0.14秒で止まる。閉じるのも1秒以内。
- 1GB の unitypackage は取り込みの裏でも商品ページからでも、画面を止めずに読めた。
- 一時展開の置き場は、エクスプローラで開いたままアプリを閉じても消えた。展開に失敗したときの文（壊れている・別のアプリが開いている・権限が無い）は3つとも言い分けられていた。
- 入れ子40段（最長1,326字）の zip も展開できた（エクスプローラで奥まで開けるかは見ていない）。
- 11分・6周の後、周の終わりのメモリは 323→341MB で、はっきりした漏れは見えない（1周に約3MB ずつ増えているが、ぶれと区別できない）。

## 確かめられなかった物

- **ディスクの本当の速さ**：作ったファイルがキャッシュに載ったままで、管理者の権限が無いので捨てられない。HDD・USB の外付けでの時間（ハッシュ・展開）と、その間の進み具合の見え方は未。
- **空き容量が足りないとき**：小さなボリュームを作れない（管理者の権限が要る）。コードでは「ディスクの空きが足りません。空きを作ってからもう一度お試しください。」を出す。書きかけの展開はアプリを閉じるまで一時フォルダに残る（空きを作りたい人の邪魔になる）。
- **`heavycheck`・`unitypkg` の写し**：`heavycheck` の未確定が指す 1GB の zip は前の作業用フォルダと一緒に消えていた。`unitypkg` は `location.json` が別の保存先（`-first`）を指していて、起動すると別の物が開く。代わりに作り物の 1GB の unitypackage を使った。
- **中身が圧縮の効く unitypackage**：作り物は乱数なので展開がほぼ写すだけで速い。実物（テクスチャなど）は伸長に時間がかかる。
- 購入した実物のファイルは使っていない。Unity は動かしていない。

## 測り方の注意

- `ui-check` の既定の起動（Debug）では、同じ2万件の取り込みが **84.5秒**（Release は 12.2秒）。取り込みの速さを画面越しに測るときは Release で測る（`dotnet build BoothAssetManager.App -c Release -o <作業用フォルダ>` して、ui-kit の `$ChmonosExe` をそこへ向けた）。
- UI Automation で画面の文字を全部読む（`Get-ChmonosTexts`）と、見えている要素の分だけアプリ側に部品ができてメモリが増える。7万件の一覧を出した後に読むと数字が変わるので、メモリと固まりを測る間は読まない。
- 固まりを測る `WM_NULL` の待ちは上限を長く取る。30秒で打ち切っていたら、7万件の件は「30秒」としか出なかった。

**抱えている物ではなく、使い終わったゴミだった。**直す前の版で、取り込みが終わって60秒後のダンプ（このときの作り物は未確定 60,300 行）：

### 普通の規模で効くか

- **ハッシュ（`44b68e2`）は、新しく読むファイルの数だけ効く**。zip 300本で 300MB の割り当てと第2世代の GC 99回が無くなる（上の表）。持っているファイルの取り込み直し（控えが当たる）ではハッシュを取らないので変わらない。
- **画面越しでは、普通の規模の差は測れなかった**。zip 300本とばらばらのファイル2千件の取り込みは前後とも1秒未満で終わり、20秒後のメモリは前 276〜288／176〜182、後 275〜277／175〜178（交互に2巡）。
- 数え直しの後の詰め直し（`4e41503`）は、増えた量が 32MB に届かなければ何もしないので、未確定が数百〜数千件では素通りになる。行を並んで組まない方は件数によらず効くが、数千件では数十ms の話。
- 印の読み取り（`ee195fc`）は1ファイルあたり約13マイクロ秒の差。数千件で数十ms。

### 直さなかった物と案

- **商品ページを開く 200ms 前後（取り込みが無くても出る）**。画面を組む時間なので、減らすには作りか見せ方を変える。案：
  ①説明文を最初の1コマの後に組む（約65ms。説明が一瞬遅れて出る）。②商品ページの画面を1つ持ち回す（検索の画面と同じ形。部品を作り直す約30msと1回目の上乗せが減るが、画面に持つ状態を全部洗う必要がある）。
  ③履歴と足跡の書き込みを画面のスレッドの外で行う（このPCで約16ms。HDD ではディスクへの書き出しの分だけ長くなる。未測定）。
- **数え直しそのものの重さ（未確定が数万件のとき）**。記録を2回読む・行を全件組む・組むたびに全ファイルの Zone.Identifier を読み直す（保存した値が旧版の文字化けを含み得るための読み直し。`docs/spec/id-resolution.md`）。
  8万件で、終わった直後に約5秒・裏で1コア分・山が 460／370MB。未確定を1件登録するたびにも走る。保存した値を信じれば読み直しは要らなくなるが、古い形のデータの扱いが変わるので判断が要る。
  → 読み直しは下の「Zone.Identifier の読み直しをやめた」で直した。残りの2つの案もそこに書いた。
- **詰め直しが画面のスレッドを止める時間**。画面を移るたびに 34〜44ms、8万件の取り込みの後は 48〜99ms（1〜2回）。手が止まった所で走るので今のまま。

### 測り方の注意（足した分）

- 商品ページを開く所の数字には、UI Automation の木の更新（1回 約64ms）が乗っている。前の夜の「222〜582ms」も同じ。人がマウスで押すときの値は、その分だけ短い見込み（UI Automation を使わずに開く手段が無く、測れていない）。
- 開く1回目と2回目以降は分けて見る（1回目は初回だけの支度が乗る）。
- 同じ中身のファイルは未確定で1行にまとまる。作り物を種類ごとに同じ乱数の種で作ると、件数が合わなくなる（最初の作り物は 80,300 ファイルで 60,300 行だった）。
- Release でも `dotnet-trace` を付けている間は遅く出る（例外1回の重さが特に増える）。時間は付けずに測り、付けたときは割合だけを見る。

## Zone.Identifier の読み直しをやめた（2026-09-30）

ユーザ判断「Aで進めてくれ」。未確定の画面とナビの札は、元zipを**未確定の記録に保存した値（`zoneReferrerUrl`）だけ**で割り出す（`f41d555`）。
ファイルの Zone.Identifier を読むのは、取り込みの走査で記録を作るときだけ。

- **前の動き**：`UnresolvedOrigin.For` が、保存した値より先に今あるファイルの印を読み直していた。9月前半の版が CP932 の ReferrerUrl を UTF-8 として読み、化けたまま保存していたための救済。
  未確定の画面を開くたび・札が数え直すたびに、未確定の件数ぶんディスクを読む。
- **測った数字**（割り出しだけを Release の Core で直に。作り物のファイル・同じ機械・交互に3巡の2・3巡目）：

  | | 前（読み直す） | 後（保存した値） |
  |---|---|---|
  | 印の無いファイル 6万件 | 760〜771ms・25MB | 2〜7ms・1.8MB |
  | 印のあるファイル 2万件 | 3.2秒・40MB（1巡目は 12.9秒） | 2〜3ms・3.4MB |

  印のあるファイル（zip を展開した中身は全部これ）は1件あたり約160マイクロ秒で、印の無いファイルの約12倍かかっていた。画面越しには測っていない（アプリを起動していない）。
- **取り込み直すと書き直される**：走査は、ハッシュを控えから使う回でも印を読み直し、見つけた記録で前の記録を置き換える（`UnresolvedMerge.ForImport` は見つけた方を先に採る）。
  試験 `UnresolvedReferrerReimportTests`：化けた値（U+FFFD 入り）を保存した記録と、値の無い記録が、取り込み直しで今の読み方の値になる（ハッシュの計算 0・控えから 1）。`ImportPipeline.cs` は直していない。
  書き直されるのは、走査した取り込み元の中で見つかった記録だけ。取り込んでいない取り込み元・外している外付けの記録は前のまま残る。
- **読むときの救済は足していない**。名前の化けた値の記録は、取り込み直すまで元zipではなくフォルダで束ねられる（途中のフォルダだけが化けた値は、前と同じく元zipで束ねる）。
- **古い記録の数**（読むだけ。`%LOCALAPPDATA%` の `BoothAssetManager-*`・`Chmonos*` にある `unresolved.json` 30本）：
  `zoneReferrerUrl` に U+FFFD を含む記録は **0 件**。NUL の入った記録も 0 件。そもそも `zoneReferrerUrl`・`zoneHostUrl` を持つ記録が、どの保存先にも1件も無かった
  （未確定のある保存先は 14・合わせて 1,087 件。411・333・327 件の3つのほかは 1〜4 件）。本番の保存先は未確定 0 件、本番が指している写しは 1 件（値なし）。
  **前の読み直しなら元zipが取れた記録も 0 件**：1,087 件のうち 1,071 件は zip 自身（場所から決まる）、残り 16 件は zip 以外で、この機械にあって印を持つ物が 16 件、その印が元zipの場所を指す物は 0 件。
  この機械の保存先では、前後で束ね方は変わらない。直す物も無い。
- **前と変わる所**：商品から外して未確定へ戻した記録（`ItemService` が作る）は印の値を持たない。前は画面が読み直して元zipの束に入れたが、今は取り込み直すまでフォルダで束ねる（直すかは判断待ち）。
  BOOTH に無かった商品の記録（取り込みが作る）も値を持たないが、手掛かりのあるファイル（zip 自身・ブラウザで落としたファイル）なので束ね方は変わらない。

### 数え直しの重さ：残りの2つ（直していない）

- **記録を2回読む**。札の読み手（`NavCountReader`）は `unresolved.json` の印（大きさ・更新日時・書き込みの数）が前と同じなら読まないが、
  未確定が1件でもあると、その後で `MainViewModel.ReadCounts` が記録を毎回読み直して、材料が同じかを見ている（同じなら行は組まない）。変わった回は読み手と合わせて2回読む。
  案：読み手が印を返し、単位の数の覚え（`UnitCountMemo`）の鍵を「印＋商品が持つファイルの数＋取り込み元」にする。印が同じ回は記録を読まない。変わった回は読み手が読んだ記録をそのまま渡して1回にする。
  見込み：6万件で1回 329ms・40MB の読み取りが、変わっていない回は 0 回、変わった回は 2 回から 1 回。取り込み中は数え直しが商品1件あたり約2回頼まれるので、未確定が多い保存先で取り込むときに効く。
- **行を全件組む**。札が要るのは単位の鍵（`UnitKey`）だけだが、画面と同じ行（名前・フォルダ・大きさの文字列）を全件ぶん作って捨てている。
  案：`ResolveViewModel.BuildRows` の「元zipの割り出し・登録済みのzipの中身を除く・展開物の根を決める」所を、行を作らずに鍵だけを返す関数に切り出し、画面の行もそれを使う（数え方を1か所に保つ）。
  見込み：数え直しのたびに作って捨てる行（6万件なら6万個）と、その名前・フォルダ・大きさの文字列が無くなる。時間は未測定——今回の直しの後で、残りがフォルダの中を見る所（フォルダごとに1回）と並べ替えのどちらにあるかを測ってから決める。
- どちらも画面の見え方は変わらない。未確定が数百〜数千件の普通の規模では数十ms の話。
