## A：履歴と足跡の書き込みを、画面のスレッドの外へ（直した・`88c1f63`）

検索の履歴（`search-history.json`）と「閲覧」の足跡（`recent.json`）は非同期の形で書いてあったが、錠が空いていると最初の待ちまで同期で進み、
続きも画面のスレッドへ戻るので、読む・ディスクへ書き出す（`Flush(flushToDisk: true)`）・置き換えるが画面のスレッドで走っていた。
押したときの処理の中で足跡の分が 8〜10ms、残りは処理が返った後の続きとして最初の1コマの前に乗っていた。

- 1本の列（`BackgroundWriteQueue`）につなぎ、プールのスレッドで頼まれた順に書く。道（`UiCommand.ChangeSearchHistory`・`RecentTracker`）と、錠の中で今の値に当てる所は変えていない
- `Task.Run` で投げるだけにしなかったのは、走り出す順が決まらないため。同じ商品を続けて開くと、後の足跡が先に当たり、古い時刻が後から書かれて勝ち得る
- 履歴を消す所（検索の札の ×・設定の「全部消す」）も同じ列を通す。別の道で書くと、開いた直後の「足す」がまだ列にいるとき、消した後にそれが書かれて1件戻る
- 閉じる前と保存先を運ぶ前に、列が空くのを待つ（`MainViewModel.FlushPendingWritesAsync`）
- 見た目は変えていない。戻ったときの履歴の札の並び（開いた条件が先頭へ来る）も前と同じ

**数字**（交互に2巡。上の表の「直す前」と「A」）：押したときの処理 11.6 → 2.5ms。最初の1コマまで、短い商品で 76 → 61〜63ms、長い商品で 351〜353 → 337〜344ms。
UI Automation の相手がいるときも同じ幅（128 → 113ms、445 → 429ms）。外から見た最長の止まりは変わらない（止まりの最長は最初の1コマの配置で、書き込みはその前の別の固まりだった）。

**確かめたこと**

- 順を守る・呼んだスレッドで走らない・1つの失敗で後ろを止めない・列が空くまで待ちが終わらない、は試験（`BackgroundWriteQueueTests`）
- 商品を押した直後に窓を閉じる（アプリが暇になる前に閉じる命令が届く）を5回。足跡も履歴も5回とも書けていた。
  **待ちを外した版でも5回とも書けていた**——この SSD では書き込みが約10ms で終わり、閉じる処理の方が長い。待ちは、ディスクへの書き出しが遅い機械のための保険
- HDD では測っていない。書き出しを待つ時間なので、遅いディスクほど A の効き目は大きい見込み

## B2：商品ページの画面（View）を1つ持ち回す（試作）

検索の `SearchViewHost` と同じ形の入れ物（`ItemViewHost`）で、主の窓の商品ページを持ち回す。

**数字**：短い商品で 62 → 38ms（UI Automation の相手がいると 113 → 68ms。外から見た 33ms 超の止まりがほぼ出なくなる）。
**長い商品では差が測れなかった**（336〜340 → 329ms）。説明の箱は商品ごとに作り直すので、持ち回しても残る。
1回目は変わらない（最初の1回は View を初めて作る）。B1 と重ねると、長い商品で 67〜69ms（B1 だけと同じ）、短い商品で 39〜40ms。
メモリは、作り直す・前の商品を持ったまま・離れて暇になったら外す、の3通りで差が測れなかった（検索へ戻って約1秒後の値がどれも揺れの中）。

**今でも、View は使い回されている所がある。**主の窓は画面を DataTemplate で出すので、同じ型の ViewModel へ替わるときは View を作り直さず、DataContext だけが替わる。
確かめた：フォルダビューで商品を続けて3件選ぶと、作られた `ItemView` は1つだけで、**流した位置（645px）が次の商品にそのまま残った**（今の動き。新しい商品が途中から出る）。
商品ページから別の商品ページへ直に移るとき（説明の中のリンク・取り直した後の開き直し）と、改変の画面で使ったものを選び直すときも同じ道。
B2 が足すのは、検索などを挟んだときも同じ道に乗せることだけ。

**画面に持つ状態**（持ち回すと、前の商品の物が残り得る所）

| 状態 | 持つ所 | 持ち回すと | 試作での扱い |
|---|---|---|---|
| 縦・横のスクロールの位置 | View（ページを流す部品） | **残る**（確かめた。前の商品で流した 5,585px のまま次の商品が出る） | 商品が替わるたびに先頭へ戻す |
| フォーカス | View | 残る（メモ欄に入れたままだと、打った文字が次の商品のメモに入る） | 商品が替わるたびに外す |

| 開いている吹き出し・右クリックのメニュー・「開く ▾」 | 別の窓 | 画面を移ると閉じる | — |

| 離れている間の View と前の商品 | 入れ物 | View（と、外さなければ前の商品の ViewModel と絵）を握る | 離れて暇になったら DataContext を外す切り替えを付けた（速さは同じ） |

**組み込んだ商品ページ・編集画面**

- フォルダビューと改変の画面は、それぞれ自分の DataTemplate で `ItemView` を作る（主の窓のとは別の1つ）。その画面を開いている間は、選び直しても同じ View を使い続ける（今の動き）。画面を開き直すと作り直す
- 違いは ViewModel の側（`IsEmbedded`：戻るを隠す・最小の幅・左の幅の控えの鍵）だけなので、1つの View を3か所で持ち回すことはできる（同時に出るのは1つ）。得は、その画面で最初に商品を選ぶ1回だけ
- 編集画面は `ItemView` を使わない。4つの部品（ギャラリー・対応アバター・ファイル・動画）を直に置き、商品を移っても同じ部品を使い続ける（今の動き）

**作りの変更**：入れ物1つ（`Views/ItemViewHost`。約100行）、`ItemView` に「次の商品を出す」口（状態を戻す所）、`MainWindow.xaml` の1行、`ItemGalleryPanel` の数行。

**危ない所**

1. View に状態を足すたびに、「商品が替わったら戻すか」を考える必要がある（今でもフォルダビューでは同じ。抜けると前の商品の状態が残る）
2. 離れる（Unloaded）・戻る（Loaded）が何度も来る。部品の側がそれを前提にしていること（`PaneGrid` はしている）
3. 前の商品の部品を壊す分が、次の商品の最初の1コマに乗る（長い商品から長い商品へ。今は前の View ごと捨てるので乗らない）
4. 効くのは2回目から。1回目の約260ms（短い商品）は残る

**おすすめ：B1 の後で、要るなら入れる。**単独では長い商品に効かず、短い商品の 24ms（1コマ半）は体感しにくい。
ただしこの PC のように UI Automation の相手がいると 45ms 効く。入れるなら、スクロールの位置を戻す所は今のフォルダビューにも効かせられる。

## 測り方の注意

- **UI Automation の相手がいるかで、開く時間が 50〜90ms 変わる。**道具が UI Automation を使わなくても、常駐の相手がいれば乗る。相手がいるかはアプリの中でしか分からない
  （窓の `AutomationPeer` が作られているか・`AutomationPeer.ListenerExists`）。相手のいない数字は、アプリの側で `WM_GETOBJECT` を断って測った
- 説明の長さで 60ms から 340ms まで変わる。長い商品と短い商品を分けて測る
- 1回目と2回目以降を分ける。1回目は同じ版でも 200ms 以上揺れる
- PowerShell は変数の名前の大文字小文字を区別しない（引数 `$Opens` と結果の `$opens` がぶつかって、結果が数に変換されて落ちた）
- 別の作業が同じ PC でビルドや試験を走らせていると、数字が揺れ、実入力が届かない回が出る。測る前に CPU の使用率を見る
