# 設計詳細：メモリの上限（#71）

> **要約（2026-09-14 に足した。中身は書かれた時点のまま）**
> - **目的**：大量の画像を読み込んでもメモリが目標に収まるか。収まらない原因は何か。
> - **方法**：2000件・画像16,393枚の作った保存先で5つの場面（起動・速いスクロール・編集で30件・0件の検索・落ち着いた後）を UI Automation だけで回した。作業セットとプライベートの最大を見た。`dotnet-dump`・`VirtualQueryEx` で内訳を取った。
> - **結果**：抱えすぎではなく、使い終わった物を返していなかった。直す前はスクロールで 628／734MB、直した後は 379／361MB。サムネイル1枚が管理外に1MiBを取っていた。
> - **結論**：手が止まる所で詰め直す（`MemoryTrim`）、カードは表示の大きさで復号、編集画面の候補は1回だけ作る。
>   その後 U12 で、目標を 300〜400MB・保持を 132MB に改め、保持を画素で持つ形に変えた（経緯は `docs/feedback/done-2026-09.md` の U12）。
> - **今の決め事**：`docs/spec/search.md`（結果のカード）・CLAUDE.md「速さとメモリの測り方」
> - **節**：測り方／結果／分かったことと打った手（1 読み込みのゴミ・2 サムネイルの管理外・3 ファイナライザ・4 編集画面の全件読み直し・5 小さなもの）／残っているもの／決め事

**目標：多い時でも300〜400MBに抑える**（ユーザ判断 2026-09-11 に200〜300MBで決め、U12 でサムネイルの保持を132MBに増やすのに合わせて300〜400MBに改めた。経緯と今の数字は `docs/feedback/done-2026-09.md` の U12 の行）。

大量の画像を読み込んでも耐えられるかを、実際に大きな保存先を作って測った。
直したのは「抱えすぎ」ではなく、ほとんどが**使い終わったものを返していない**ことだった。

## 測り方

| | |
|---|---|
| 保存先 | サンドボックスを型に作った **2000件・画像16,393枚**（本番の15件の約130倍）。本番には触れない |
| 場面 | ① 起動して15秒 ② 検索画面を端から端まで速くスクロール ③ 編集画面で「スキップ」30回 ④ 0件になる語で検索（表記の橋渡しの索引が組まれる） ⑤ 落ち着いた後10秒 |
| 操作 | UI Automation だけ（キーボード・マウスは使わない） |
| 数字 | 場面ごとの作業セット／プライベートの最大（MB） |
| 道具 | `dotnet-dump`（管理ヒープの内訳）、`VirtualQueryEx`（管理外の確保を大きさ別に数える）、画面なしで復号だけ回す試験プログラム |

## 結果

作業セット／プライベート（MB）の最大。

| 場面 | 直す前（Debug） | 直した後（Release） |
|---|---|---|
| ① 起動 | 380 / 329 | 310 / 253（落ち着くと 247 / 191） |
| ② スクロール | **628 / 734** | 379 / 361 |
| ③ 編集で30件 | 途中の版で 533 / 558 | 364 / 327 |
| ④ 0件の検索 | — | 259 / 199（①のすぐ後に単独で測った値） |
| ⑤ 落ち着いた後 | — | 330 / 286（①〜④を続けて回した後） |

15件（本番と同じ規模）のサンドボックスは、どの場面でも**最大 221 / 158**。

「直す前」の③〜⑤は、最初の測定では③の操作が途中で止まって取れていない。

**④の測り直し：**最初は検索欄のつもりで「木の最初の入力欄」に打っていたが、それは絞り込みパネルの
「BOOTHタグ」の欄で、表記の橋渡しの索引は組まれていなかった（そのときの値 331 / 291 は③の名残）。
いちばん幅の広い入力欄＝検索欄に打ち直して測ったのが上の値。

## 分かったことと、打った手

### 1. 読み込みのゴミが、穴の空いたまま握られていた

起動直後のダンプ：**生きている管理オブジェクトは64MBなのに、GCのヒープは210MB**。
第2世代の37%（75MB）が空きのまま。全件の読み込み・検索用の文字列作り・カードの生成が
一度に出すゴミを、裏で動くGC（詰め直しをしない）が掃くだけなので、穴ごと持ち続けていた。

- `MemoryTrim`：手が止まる所で一度だけ詰め直し、空きをOSへ返させる（`GCCollectionMode.Aggressive`）。
  頼むのは3か所：全件を読み込んだ後・サムネイルを捨てた後・画面を移ったとき。
  **前回から32MB以上増えていなければ何もしない**——間隔だけで絞ると、起動直後の画面の切り替え
  （まだ返すものが無い）で1回使ってしまい、肝心の「読み込み後」が後ろへずれた（実測で起動が 245→338MB に悪化した）。
- `System.GC.ConserveMemory = 7`：第2世代の空きが増えたらGC自身にも詰め直させる。

### 2. サムネイル1枚が、管理外に1MiBを取っていた

長辺384pxの画像（生ピクセル576KB）を WPF の画像にすると、管理外に **1MiB+4KiB** の確保が1つできる。
スクロール後に数えると115個・115MB並んでいた。キャッシュの上限（当時192MB）は生ピクセルで数えていたので、
実際にはその倍近くを握れる作りだった。

- **検索カードは表示の大きさで復号する**：長辺240DIP×画面の拡大率。画面なしの試験で、
  同じ100枚が **112MB → 42MB**、1MiBの確保は0個になった。形式を Pbgra32 に変えても変わらなかった（効くのは大きさだけ）。
- **商品ページ・編集画面の小さな一覧は96DIP**。大きく出す1枚だけ原寸で読む。
  以前は一覧も原寸で、編集画面で30件送ると1MiBの確保が107個並んでいた。
- **保持の上限は32MB**（カードなら約140枚、原寸でも約55枚）。
  以前の既定192MBは設定画面に出したことが無く、保存された192は全員「既定を写しただけ」なので、
  読み込み時に新しい既定へ置き換える。手で書き換えた値はそのまま。

### 3. 捨てた画像の実体は、ファイナライザが走るまで返らない

1枚が小さくなった分、WPFがGCを急かさなくなり、スクロール中に捨てた画像が溜まる。
スクロールしている間は手が止まらないので `MemoryTrim` も走らない。

- キャッシュから**上限の半分ぶん捨てるたびに、若い世代だけGCを回す**（捨てたばかりの画像はそこにいて、数ミリ秒で終わる）。

### 4. 編集画面が、1件進むごとに全件を読み直していた

店名の候補を作るために、1件表示するたびに2000件を全部読んでいた。スキップ30回で全件読み込み30回。

- 候補は**画面を開いて1回だけ**作り、保存した店名をそこへ足していく。

### 5. 小さなもの

- 復号の受け渡しに毎回 `new byte[]`（576KB・大きいオブジェクト用のヒープ行き）→ `ArrayPool` から借りて返す。
- ImageSharp が作業領域を溜めておく上限を16MBにする（既定は搭載メモリから決まり、数百MBまで握り得る）。

### 6. 表記をまたぐ辞書の索引が、閉じるまで約105MB残っていた（2026-09-24）

「別表記でも検索」で一度引くと、控え（`search-bridge.cache`・25.2MB・48.5万行）を `Dictionary<string, string[]>` 3つへ読み、
閉じるまで持っていた。画面なしの計測（Release・同じ控えを読む・交互に2巡）で：

| | 読み込み | 割り当て | 残る管理ヒープ |
|---|---|---|---|
| 前（3つの節を全部読む） | 210〜227ms | 188MB | **105.7MB** |
| 後・英日だけ引いた | 102〜119ms | 35MB | **17.2MB** |
| 後・3つとも引いた | 計 250〜263ms | 計 100MB | **44.6MB** |
| 参考：控えが無く XML から組む（最初の1回） | 前 3.3秒・後 3.4〜3.6秒 | 前 1.49GB・後 1.71GB | 前 73.6MB・後 44.6MB |

- 文字列が約163万個（異なる物は約66万個）できていた。同じ表記が何百もの鍵に繰り返し出るので、
  **異なる文字列を1本の文字列に1回ずつ詰め、鍵と並びは番号で指す**（`Search/PackedIndex`）。オブジェクトの頭と配列が消える
- **節は引かれたときに1つずつ読む**。切っている変換の節は読まない。控えの行はバイトのまま切り、頼んだ節の行だけを文字に直す
- 控えのファイルの形は変えていない（前の控えがそのまま読める）。前の読み方と全部の鍵で同じ並びを返すことを試験で見ている（`PackedIndexTests`）
- 3つとも引くと、控えを節ごとに読むぶん前より1〜2割遅い（250ms 前後。一度きり）。残る量を優先した

**上の表の④（259 / 199MB）と食い違う理由**：④は 2026-09-14 より前の測定で、そのときの索引は2つの節（英語・読み）だけだった
（読み→英語の節は 2026-09-16 に足した）。ただ、2つの節だけの控えを読んでも残るのは 73.3MB で、
④は①の落ち着いた値（247 / 191）から +12 / +8MB しか増えていない。**④では索引が載っていなかった見込みが高い**
（控えが無ければ組むのに3秒以上かかり、裏のスレッドで組むので、その前に測り終えた。または語がラテン文字でなく辞書を引かなかった）。
当時の手順は残っておらず確かめられない。辞書の重さは、プロセス全体の値ではなく、引く前後の管理ヒープの生きている量（`GC.GetTotalMemory(true)`）で見る。

## 残っているもの

- **2000件を端から端まで速くスクロールしたときだけ、最大 379 / 361**。他の場面は 364 以下、落ち着けば 280 前後。
- 生きている管理オブジェクト（約70MB）の大半は2000件ぶんの文字列（説明・見出しと、検索用に畳んだ写し）。
  さらに削るなら、検索画面が抱える商品から説明と見出しを落とし、検索用の写しだけを持つ
  （商品ページは開くときに読み直す）。**20〜30MB見込み・未着手。**
- GPU側の専用メモリが約100MB（WPFの描画。プライベートとは別に数えられる）。

## 決め事

- サムネイルの保持上限は起動時に決まる（読み込み器を作り直すと、見えている絵を全部復号し直すことになるため）。
- 縮めて持つのは「たくさん並ぶ所」だけ。大きく出す1枚は保存された大きさで読む。
