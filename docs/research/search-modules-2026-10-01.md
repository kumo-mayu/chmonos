# 検索の条件：同じ種類を複数・除く・未編集の項目（案 2026-10-01）

> **要点**：ユーザが 2026-10-01 に決めた4つ（同じ種類の条件を複数置く・各条件に「除く」・「除く」の切り替えの置き場・未編集を項目ごとに）と、
> 追加の2つ（同じ種類を隣に並べる操作・照らす重さと順番の計測）の作り方の案。**まだ実装していない。** （2026-10-01 に実装した。実装で変えた所は §12）
> 状態は `SearchModuleState` に `exclude` と `fields` を足すだけで、`searchModules` の並びはそのまま複数を持てる（古い形への救済は要らない）。
> 照らし方は「除く＝除かないときに OR で当てはまる物の反対。値の分からない物は除くときも外す」を条件の型ごとに1つずつ書く。
> 計測では、選択肢の件数（`RefreshFacetCounts`）が条件の数の2乗で伸び、2,000件・条件20個で 11.7ms、1万件で 64ms。
> 「外れた条件を2つ目まで数える」作りにすると条件の数によらず 1.5ms・8ms になる。照らす順は、2,000件では最悪の並びでも 2ms 程度の差。
> 同じ種類を隣に並べる操作は、パネルの見出しのメニューから押したときに1回だけ並べ替え、足す位置は既定で一番下・設定で同じ種類のすぐ下（ユーザ判断 2026-10-01・§5）。
>
> **決めること**は §10、**段取り**は §11。今のコードの事実（§1）と案（§2 以降）を分けて書く。
>
> **読んだ物**：`docs/spec/search.md`「絞り込み」・`ui-input.md`・`ui-rules.md`・`ui-writing.md`・`ui-terms.md`、`SearchModules.cs`・`SearchViewModel.Modules/Filtering/History/ShowOnly.cs`・

## 1. 今の作り（事実）

### 1-1. 条件の状態の持ち方

- 条件1つ＝`SearchModule`（App の ViewModel）。型は `ChoiceModule`（三項）・`ListModule`（候補から積む）・`RangeModule`（数の範囲）・`DateModule`・`AttributeModule`・`UserTagModule`・`RecentModule`。
  照らし方の中身は `SearchViewModel.CreateModule` の中の式（カテゴリ・タグ・対応アバターなど）で渡す。
- 共通の状態は `IsEnabled`（左のチェック）・`IsCollapsed`（畳む）・`DisabledReason`（R-18 を隠しているとき）。`IsActive = 有効 && 理由なし && HasCondition`。
- 保存の形は Core の `SearchModuleState`（1つの record に全種類の欄を並べ、種類ごとに使う欄だけ埋める）。`ui-state.json` の `searchModules` と検索の履歴の両方に同じ形で書く。
  JSON は camelCase（`JsonStore`）。読めない種類（`kind`）は黙って飛ばす。指紋（`Fingerprint`）は条件ごとの指紋を**並べ替えてから**つなぐので、順番に関わらない。
- AND／OR を持つのは `ListModule.MatchAll`（ショップは OR だけ）・`AttributeModule.MatchAll`（既定は AND）・`UserTagModule.MatchAll`（大分類どうし）と、その中の大分類の枠ごとの `UserTagCondition.MatchAll`（小分類どうし）。
- ユーザータグは今も「1つの条件の中に大分類の枠を何個も持てる」。枠どうしは AND／OR、枠の中の小分類も AND／OR。

### 1-2. 照らし方と件数

- `FilterMatches`：`_activeModules`（**画面の並び順**のまま）を上から当て、外れた所で打ち切る。文字列（`MatchesQuery`）は最後。非表示と R-18 の設定は先に外す（`PassesBase`）。
- `RefreshFacetCounts`：条件ごとに、全商品を「その条件を除いた他の全部」で照らし直し（`Matches(item, except: module)`）、その残りで選択肢の件数を数える。
  条件 M 個なら全商品×M 回、1回ごとに最大 M−1 個を照らす。**効いていない条件（「両方」など）にも同じことをする。**
- 文字列は1打鍵ごとに `ApplyFilters`（絞り込み＋件数）。スライダーは止まってから150ms後に1回。

### 1-3. 「1種類1つ」を前提にしている所

| 所 | 今の作り | 複数にしたとき |
|---|---|---|
| `SearchViewModel.AddModule` | 同じ種類があればそれを返す（足さない） | 複数を許す種類は足す |
| `RefreshModuleMenu` | 足してある種類はメニューでグレー。吹き出し「追加済みの条件は選べません。」 | 1つまでの種類だけグレー |
| `InitializeModules`（`searchModules` を戻す） | 状態ごとに `AddModule(kind, state)`。**同じ種類の2つ目の状態は黙って捨てる**（既にある物が返り、`Load` もしない） | 状態の数だけ作る |
| `ApplyHistory`・`RestoreFilters`（検索の履歴・画面の履歴の控え P4） | `AddModule(kind).Load(state)`。**2つ目の状態が1つ目を上書きする** | 同じ種類の n 番目の状態を n 番目の条件へ（§8-2） |
| 入口 `ShowOnly*`（タグの管理・属性・アバター・ショップ・フォルダ・統計のカテゴリ・壊れたzip） | `EnsureModule<T>(kind)`：その種類を1つ取り出して値を入れる | どれに入れるかの決まりが要る（§8-1） |
| `NoteShopNotesChanged`・`NoteFavoriteChanged`・`_allowsHidden`・`NeedsModifications` | 「その種類があるか」（`Any`） | そのままでよい（ショップ・お気に入り・非表示は1つまで、改変は複数でも「あるか」で足りる） |

| 畳んだ姿・結果の上の要約・畳んだパネルの吹き出し | `SummaryText` を並べる | 同じ見出しの行が2つ並ぶだけ（§4-4 の「除く：」は要る） |

| 確かめの道具 | `ui-ops.ps1` の `Add-ChmonosSearchCondition` は足したあと `SearchModule.$kind.Remove` が出るのを待つ。`tools.md`・`pitfalls.md` も同じ ID を書く | 2つ目を足したときは既に1つ目があるので、待ちが即座に抜ける |
| 描く台の場面（`tools/ViewShot/Scenes.Screens.cs`） | 検索の場面は既定の条件と `ShowOnlyBrokenZip` だけ | 複数・除く・未編集の場面を足す（§11） |
| spec・コメント | `search.md`「各条件は一度しか足せない」、`SearchModule` の「各モジュールは一度しか追加できない（検索画面が守る）」、メニューの XAML のコメント | 書き換える |

### 1-4. 条件の見出しの今の作り

`SearchView.xaml` の条件の枠：`DockPanel` に ⋮⋮（つまみ・止まらない）→ ×（右寄せ）→ ⌃（右寄せ）→ 有効のチェック（見出しの文字を中に持つ）の順に並ぶ。
**コードの並びから読むと、Tab は × → ⌃ → チェックの順に止まる**（画面の左から右と逆。起動して確かめてはいない）。右クリックのメニューは無い。並べ替えはつまみのドラッグだけで、キーボードからはできない。

## 2. 案1：同じ種類を複数置く

- **複数を許す種類**：カテゴリ・BOOTHタグ・対応アバター・改変・Unityプロジェクト・ファイルの場所・ユーザータグ。
  **1つまで**：ショップ（1商品に1つ）・三項（所持・壊れたzip・販売終了・R-18・有料無料・お気に入り・非表示・未編集・対応アバターの確認・ギフト）・範囲（価格・スキ数・属性）・日付（公開日・入手日）・最近。
  決まりは `SearchModuleCatalog` に1つ（`SearchModuleInfo.AllowsMany`）。メニューのグレーも、`AddModule` の「あれば返す」も、これを見る。
- 条件同士は今までどおり全部 AND。並び順は結果に関わらない（§9 の照らす順は画面の並びと別に持てる）。
- **ユーザータグとの関係**：ユーザータグは今も1つの条件の中に大分類の枠を何個も持てる。複数置けるようにすると、
  「(大分類A か 大分類B) かつ (大分類C か 大分類D)」が組める（今は1つの条件の AND／OR が全部の枠に掛かるので組めない）。
  枠の作りはそのまま残す（1つの条件で足りる人の手数を増やさない）。同じ大分類を2つの条件に入れてもよい（A かつ A は A と同じで、害は無い）。
- 選んだ値の候補から「積んだ物」を外すのは、今と同じく条件ごと（別の条件で選んだ値は候補に残る。除く条件に同じ値を入れる使い方があるため）。
- メニューの吹き出しは「絞り込みに使う条件を追加します。1つしか置けない条件は、追加済みなら選べません。」（40字。上限ちょうど）。グレーの項目そのものの吹き出しは今の `Hint` のまま。
- **足す位置**：既定は一番下（今と同じ）。設定「追加した条件を同じ種類の条件のすぐ下に置く」を入にすると、同じ種類の塊の最後の直後に入れる（ユーザ判断 2026-10-01・§5-2）。
  足した条件へ画面を送り、入力欄に止める。

## 3. 案2：各条件に「除く」

### 3-1. 照らし方の決まり

`SearchModule` に `IsExcluded` を持ち、照らす口を1つにする：

```
Passes(item) = IsExcluded ? MatchesExcluded(item) : Matches(item)
```

`MatchesExcluded` は型ごとに書く。決まりは「**除かないときに OR で当てはまる物の反対。ただし値の分からない物は、除くときも外す**」。

| 型 | 除くときに残す商品 | 補足 |
|---|---|---|
| 候補から積む（`ListModule`） | 積んだ値の**どれにも**当たらない商品 | AND／OR の設定は見ない（グレー）。値が1つも無ければ絞らない（今と同じ） |
| 対応アバター | チェック込みで当てはまらない商品（＝今の `Matches` を OR で当てた答えの反対） | 「☑対応している／☐指定が無い」で「アバターA」を除く → A に対応していない商品と、**指定が無い商品**が残る（指定が無い商品は「当てはまる物」に入っていないため）。「指定が無いのみ」を除く → 指定のある商品だけ。素体経由のチェックもそのまま効く |
| ショップ | 選んだショップのどれでもなく、（★を入れていれば）お気に入りのショップでもない商品 | もともと OR だけ |
| ユーザータグ | 選んだ大分類の枠の**どれにも**当たらない商品。枠の中は小分類（と「小分類なし」）のどれか | 大分類どうしの AND／OR も、枠の中の小分類の AND／OR も OR として扱い、両方グレー（推し・D3） |
| 範囲（価格・スキ数） | 数が分かっていて、**どの数も**範囲に入らない商品 | BOOTH の価格は種類ごとの数のどれか1つでも範囲に入れば「当てはまる」ので、除くと外れる。外れ値を外した結果、数が1つも残らない商品は「分からない」 |
| 属性 | 選んだ属性が**全部**評価済みで、**どれも**範囲に入らない商品 | 属性ごとに「値が分かっていて範囲の外」を求め、それを全部満たす物（推し・D2）。AND／OR はグレー |
| 日付（公開日・入手日） | 日付が分かっていて、範囲の外の商品 | 両端を切っていれば絞らない（今と同じ） |

- **「値の分からない商品だけを出す」条件は今は作らない**（ユーザ判断）。除いた範囲の条件には、値の分からない商品が出ないことを吹き出しで言う（§4-2）。
- 三項・最近には付けない（三項は「ある／ない」を選べる。最近はユーザが挙げた種類に入っていない。日付に近いので後で足すのは軽い・D10）。
- `HasCondition`（何か絞っているか）は除くときも今と同じ。値を何も選んでいない「除く」は何も絞らない。

### 3-2. 件数

- 選択肢の横の件数は今と同じ「**他の条件のもとで、その値に当てはまる件数**」（除いたら何件減るか、と同じ数）。数え方は変えない（`RefreshCounts` は `Matches` ではなく値ごとの式で数えている）。
- 除く条件そのものの件数：自分を除いた他の全部で数えるので、今の作りのまま正しい。

### 3-3. 要約の文

`SummaryText` を「中身」と「頭」に分け、頭は基底が付ける（`IsExcluded` なら「除く：」）。除くときは値の結び（` かつ `）を「・」に替える（OR として照らすので）。例（推し・D1 の B）：

| 条件 | 今の要約 | 除くときの要約 |
|---|---|---|
| カテゴリ（3D衣装・3D小物） | カテゴリ：3D衣装・3D小物 | 除く：カテゴリ 3D衣装・3D小物 |
| BOOTHタグ（AND） | BOOTHタグ：A かつ B | 除く：BOOTHタグ A・B |
| 対応アバター | 対応アバター：〇〇（対応の指定が無い商品も含める） | 除く：対応アバター 〇〇（対応の指定が無い商品も含める） |
| 価格 | 価格（購入額） 1,000円以上 5,000円以下 | 除く：価格（購入額） 1,000円以上 5,000円以下 |
| 公開日 | 公開日 2026-01-01から | 除く：公開日 2026-01-01から |
| ユーザータグ | ユーザータグ：衣装（トップス・小分類なし） | 除く：ユーザータグ 衣装（トップス・小分類なし） |

同じ文が畳んだ姿・結果の上の要約・畳んだパネルの吹き出し・検索の履歴のチップに出る（どれも `SummaryText`）。

## 4. 案3：除くの切り替えの置き場

### 4-1. 見出しの形

```
ふだん（乗せていない・止まっていない）
┌──────────────────────────────────────────┐
│ ⋮⋮ ☑ カテゴリ                         ⌃  × │
│    [カテゴリで絞り込む                    ]    │
│    (3D衣装 12 ×) (3D小物 8 ×)                 │
│    ☐ すべてに当てはまる商品だけ               │
└──────────────────────────────────────────┘

乗せた・キーボードで枠の中に止まった（「…」が出る）
│ ⋮⋮ ☑ カテゴリ                      …  ⌃  × │

除いている（札は常に出る。押すと除くのをやめる）
┌──────────────────────────────────────────┐
│ ⋮⋮ ☑ カテゴリ ［除く］                 ⌃  × │
│    [カテゴリで絞り込む                    ]    │
│    (3D衣装 12 ×) (3D小物 8 ×)                 │
│    ☐ すべてに当てはまる商品だけ   ←灰色・押せない │
└──────────────────────────────────────────┘

除いていて畳んだ
│ ⋮⋮ ☑ カテゴリ ［除く］                 ⌄  × │
│      除く：カテゴリ 3D衣装・3D小物              │
```

- 札「除く」は見出しの文字のすぐ右。色は字と枠を `DangerText`・`DangerBorder`、背景は `Surface`（新しい色を足さない。推し・D11）。
  吹き出し「当てはまる商品を除いています。押すと除くのをやめます。」（27字）。押せる部品は `PressableBorder` かボタン（UI Automation に出す）。
- 除くを入れた・外したら、すぐ絞り直す（`NotifyChanged`）。
- **AND／OR のチェックはグレーにして押せなくする（隠さない）**。値は覚えたまま（除くを外せば元の AND が効く）。
  吹き出し（押せないときも出す・`ToolTipService.ShowOnDisabled`）「除いているときは、選んだどれかに当てはまる商品を除きます。」（29字）。
  対象：候補から積む条件の「すべてに当てはまる商品だけ」、ユーザータグの大分類どうしと枠の中、属性。
- 範囲・日付で除くときは、範囲の下に1行「数の分からない商品は表示しません。」（日付は「日付の分からない」）を出すか（D12）。

### 4-2. 「…」のメニューと右クリック

```
 ┌──────────────────────────────┐
 │ ✓ 当てはまる商品を除く              │   ← 除くを持つ種類だけ
 ├──────────────────────────────┤
 │   折りたたむ（開いていれば）         │
 │   上へ移動                          │   ← D9
 │   下へ移動                          │
 ├──────────────────────────────┤
 │   この条件を外す                     │
 └──────────────────────────────┘
```

- 「…」は見出しの ⌃ の左。型は `RevealOnHoverOrFocusButton`（いちばん近い `Border`＝条件の枠に乗せた・枠の中にフォーカスがあるときに出る）。枠全体で出す（推し・D8）。
  名前「{条件名}の操作」、吹き出し「この条件の操作」。押すとメニューを「…」の下に開く。
- 右クリックのメニューは**同じ中身**（1つの `ContextMenu` を条件の枠に付け、「…」も同じ物を開く）。枠の上ならどこでも開く。
  入力欄・候補付きの欄・数の欄は自分のメニュー（切り取り・貼り付け）を持つので、その上ではそちらが出る（WPF はフォーカスのある部品から上へたどり、最初に見つかったメニューを開く）。
- **メニューキー（Shift+F10・アプリケーションキー）**：フォーカスが枠の中（チェック・札・「…」・⌃・×・チップ・チェックボックス）にあれば条件のメニューが開く。開く位置はフォーカスのある部品の下。
- 三項・最近の「…」には「除く」の行を出さない（推し・D10）。ほかの行は同じ。
- 「この条件を外す」で枠が消えたら、次の条件の「…」に止まり直す（最後なら前の条件。`ui-input.md` の「止まっていた行が消えたら」と同じ）。
  札を押して除くをやめたら、札が消えるので同じ枠の「…」に止まり直す。
- **Tab の順を直す**：チェック → 札 → 「…」→ ⌃ → ×（今は × が先・§1-4）。見出しを `DockPanel` のまま並べ替えるか、`Grid` の列にする。

### 4-3. 文言（`ui-terms.md` に足す語）

| 何を | 画面での言い方 | 使わない言い方 |
|---|---|---|
| 条件に当てはまる商品を結果から外す | **除く**（「当てはまる商品を除く」、札「除く」、要約の頭「除く：」） | 除外（「管理対象から除外」「除外を解除」は未確定とファイルの物）・NOT・否定 |
| 同じ種類の条件を並びの中で隣へ寄せる | **隣に並べる**（「同じ種類の条件を隣に並べる」） | まとめる・統合（2つを1つにすると読める） |
| 編集画面の欄に何も入れていない | **未入力** | 未設定・空 |

## 5. 同じ種類を隣に並べる（追加 2026-10-01）

ユーザの要望：上から見て、ある種類が初めて出た所の直下に、それより下にある同じ種類の条件を元の順のまま寄せる（安定な寄せ）。
例：[タグ1, アバター1, タグ2, カテゴリ, アバター2] → [タグ1, タグ2, アバター1, アバター2, カテゴリ]。

**ユーザ判断（2026-10-01）**：押したときに1回だけ並べ替える操作（常にまとまった形を保つのではない）。押す口はパネルの見出しのメニューと右クリック（条件の「…」と揃える）。
結果を変えないので絞り直さない。並びは覚える。元に戻す手段は付けない（並び順だけなので）。
条件を足す位置は既定で一番下、設定で「同じ種類のそば」にできる（§5-2）。

### 5-1. 並べ替えの操作

- **計算**：種類ごとに初めて出た順の一覧を作り、その順で種類ごとの条件を元の順のまま並べ直す（安定な寄せ）。純粋な関数にして試験する（`SearchModuleOrder.GroupByKind(種類の並び) → 新しい並びの番号`）。
  画面の並び（`Modules`）は `Move` を順に呼んで合わせる（作り直さない。条件の枠を作り直すと、入力の途中の値やフォーカスが消える）。
- **押す口**：パネルの見出し（「絞り込み」の行）に「…」を置き、メニューに「同じ種類の条件を隣に並べる」を出す。見出しの行の右クリックでも同じメニュー（1つの `ContextMenu`）。
  「…」は「絞り込み」の文字の右隣（「条件をクリア」から離す。見出しの行は押し間違えを避けて空けてある・U3）。出し方は条件の「…」と同じ `RevealOnHoverOrFocusButton`（見出しの行の `Border` に乗せた・中にフォーカスがあるとき）。
  名前「絞り込みの操作」・吹き出し「絞り込みの操作」。Shift+F10・アプリケーションキーは、フォーカスが見出しの行（「…」・「条件をクリア」）にあるとき開く。
- 分かれている種類が無いときは行をグレーにし、吹き出し（押せないときも出す）「同じ種類の条件はもう隣に並んでいます。」（19字）。
- 押したら絞り直さない（並べ替えと同じ。`FilterSummary` だけ知らせる＝結果の上の要約と畳んだパネルの吹き出しの順が変わる）。並びは今のドラッグと同じく `SaveModulesLater` で `searchModules` の順として覚える。
- 元に戻す手段は付けない。並びはドラッグと「上へ／下へ移動」（D9）で変えられる。
- キーボード：押したあとはパネルの「…」に止まったまま。読み上げの名前はメニューの文字のまま。ID はパネルの「…」が `SearchFilterMenu`、行が `SearchFilterMenu.GroupKinds`。
- メニューの行は今は1つ。後で「すべての条件を折りたたむ／開く」などを同じメニューに足せる（今回は足さない）。

### 5-2. 条件を足す位置と設定

- **既定は一番下**（今と同じ）。
- **設定「追加した条件を同じ種類の条件のすぐ下に置く」**（既定は切）。入のとき：
  - 同じ種類が無ければ一番下。
  - 同じ種類があれば、その種類の**一番上の塊の最後の直後**（塊＝同じ種類が隣り合って続く所。分かれて塊が複数あっても、一番上の塊に付ける。5-1 で並べたときにその種類が集まる位置と同じ）。
  - 例：[タグ1, アバター1, タグ2, カテゴリ] にタグを足す → [タグ1, **タグ3**, アバター1, タグ2, カテゴリ]。
- 同じ決まりを使う所：「＋ 条件を追加」・ほかの画面からの入口で新しく足すとき（§8-1）・履歴から戻すときに足りない分を足すとき（§8-2）。前回の状態を戻すとき（`InitializeModules`）は保存した並びのまま。
- 位置の計算も純粋な関数にして試験する（`SearchModuleOrder.InsertIndex(種類の並び, 足す種類, 設定)`）。
- 1つまでの種類（三項・範囲・日付・ショップ・最近）は、もともと同じ種類が無いときしか足せないので、設定によらず一番下。

**設定の置き場と文言**（`ui-wording` の決まりで書いた案）：

- 置き場：設定の画面の「一覧と検索」の欄。「非表示にしている件数を検索結果に表示」の下、「検索の履歴に残す件数」の上（検索の絞り込みの振る舞いが並ぶ所）。
- チェック：「**追加した条件を同じ種類の条件のすぐ下に置く**」（21字。動詞は「追加」・`ui-terms.md`）。
- 吹き出し：「オフのときは、いちばん下に追加します。」（19字。何が起きるかの1つだけ。並べる操作は検索の画面のメニューにあり、ここでは言わない）。
- 保存：`AppSettings` に `PlaceNewConditionNearSameKind`（bool・既定 false）。書き込みは今の設定と同じ `UiCommand.ChangeSettings`。検索は足すたびに今の値を読む（設定を変えたら次に足すときから効く。今ある並びは動かさない）。
- 読み上げはチェックの文字のまま（名前は付けなくてよい）。ID `Settings.PlaceNewConditionNearSameKind`。

## 6. 案4：未編集を項目ごとに

### 6-1. 今の決まり

- 「未編集」＝ユーザータグが0件で、取り込みの③（対応アバターの検出）を待っていない商品（`SearchViewModel.CreateModule`・ユーザ判断 Q6）。三項「未編集のみ／編集済みのみ／両方」。
  「編集済みのみ」はユーザータグが1件以上（③待ちを外していない。③待ちの商品はたいていタグが無いので、未編集にも編集済みにも入らない）。
- 同じ定義を使う所が検索の外にもある：ナビの「未:」の数（`MainViewModel`）・編集画面の順番（`EditViewModel.Queue`）・カードとリストの札「未編集」（`SearchViewModel.Filtering`・`ShopViewModel`）・統計の「ユーザータグが無い」・タグの管理の「未編集に戻りました」。
  **この案で変えるのは検索の条件だけ**。ほかは「ユーザータグが0件」のまま。

### 6-2. 編集画面の項目と「未入力」の判定

| 編集画面の項目（置き場） | 未入力の判定（案） | 並べるか |
|---|---|---|
| ユーザータグ（右） | `UserTags` が0件 | **並べる・既定で入**（今の未編集と同じ意味になる） |
| 属性（右） | `Attributes` が0件（全部「未評価」） | 並べる |
| 購入したバリエーション（右・払った額と種類はこの中） | `Purchases` が0件（自分用・貰った・贈ったのどれも記録が無い） | 並べる。編集画面の札「未選択」は「バリエーションがあって、どれにも印が無い」なので少し違う（バリエーションの無い商品でも「バリエーションを選ばない購入」を記録できるため、記録の有無で見る） |
| 払った額（購入の行の中） | — | **並べない（推し・D17）**。空欄は 0円として記録する（2026-09-29）ので、0円で入れた物と空欄を見分けられない。購入の記録が無い商品は上の項目で拾える |
| 購入の種類（自分用・貰った・贈った） | — | 並べない。既定が「自分用」で、選ばなかった物と見分けられない |
| バリエーション分け（右・ファイルごとの種類） | 札「未選択」と同じ（分けられる商品で、種類を選んでいないファイルがある） | **並べない（推し・D18）**。「指定しない」を選んだ物も記録の上では選んでいない物と同じなので、片付けても消えない。判定は今 `EditViewModel` の中にあり、Core へ出す手間もある |
| メモ（右） | 空か空白だけ | 並べる |
| 入手日（右） | `AcquiredAt` が無い（手で入れていない。画面はファイルの日付を出しているが、それは入力ではない） | 並べる |
| 更新を通知する・非表示（右） | — | 並べない（切り替えで、既定の値がある） |
| 商品名・ショップ・カテゴリ（左の「編集」・BOOTH から取れない商品の分） | 自分で入れた値も BOOTH の値も無い | 並べない（推し・D19）。BOOTH から取れる商品では常に「未入力」になり、意味を持つのは取れない商品だけ |
| 画像・お気に入り・対応アバター・手元のファイル（左・押した時点で保存） | — | 並べない。対応アバターの「指定が無い」は対応アバターの条件の「対応の指定が無い商品」で引ける |

並べるのは **ユーザータグ・属性・購入したバリエーション・入手日・メモ** の5つ（推し・D16）。

### 6-3. 組み合わせと画面

```
│ ⋮⋮ ☑ 未編集                          …  ⌃  × │
│    [未入力のみ                       ▾]        │   ← 三項：未入力のみ／入力済みのみ／両方
│    未入力の項目                                  │
│    ☑ ユーザータグ（412）                          │
│    ☐ 属性（1,350）                               │
│    ☑ 購入したバリエーション（230）                 │
│    ☐ 入手日（1,104）                             │
│    ☐ メモ（1,700）                               │
│    ☐ すべてが未入力の商品だけ                     │   ← 2つ以上入れたときだけ出す
```

- 図の件数は書き方の例（作り物）。
- **既定は「どれかが未入力」**（推し・D20）。片付けの一覧として使う場面（「まだ埋めていない所がある商品」）が多い。
  「すべてが未入力の商品だけ」は候補から積む条件の「すべてに当てはまる商品だけ」と同じ形のチェックにし、2つ以上入れたときだけ出す（1つなら結果が変わらない）。
- 三項は「未入力のみ／入力済みのみ／両方」に言い換える（鍵は今の `unedited`／`edited`／`both` のまま）。
  「入力済みのみ」は「未入力のみ」の反対：どれか→**すべて入力済み**、すべて→**どれかが入力済み**。
- **トグルの最後の1つは外せない**（対応アバターの2つのチェックと同じ・推し・D21）。全部切ると何も選ばない条件になり、意味が無い。
- 各項目の横に件数（他の条件のもとで、その項目が未入力の商品の数。選択肢の件数と同じ考え方）。
- **③待ちの商品は「未入力のみ」から外す**（今のまま・どの項目でも。推し・D22）。カードに「未編集」ではなく「取り込み中」と出る商品で、編集画面の順番にも出てこない。「入力済みのみ」は外さない（今のまま）。
- 名前は「未編集」のまま（推し・D23）。既定がユーザータグだけなので、足した直後の意味は札・ナビの「未編集」と同じ。吹き出しは「選んだ項目をまだ入力していない商品で絞ります。」（23字）。
- 要約の例：「未編集：ユーザータグが未入力」「未編集：ユーザータグ・属性のどれかが未入力」「未編集：ユーザータグ・メモがすべて未入力」「未編集：ユーザータグ・属性がすべて入力済み」。
- 型：`ChoiceModule` に混ぜず、新しい `UneditedModule`（三項＋項目のトグル＋すべて）。判定は Core の純粋な関数（`EditFieldsMissing.IsMissing(ItemRecord, EditField)`）にして試験する（App に置くと試験しにくい・今の判定は `CreateModule` の式の中）。

## 7. 状態の形（JSON）

`SearchModuleState` に2つ足す。ほかは今のまま。

```json
"searchModules": [
  { "kind": "Category", "enabled": true, "items": ["3Dモデル"] },
  { "kind": "Category", "enabled": true, "exclude": true, "items": ["3D衣装", "3D小物"], "matchAll": true },
  { "kind": "Price", "enabled": true, "exclude": true, "choice": "paid", "min": "1000", "max": "5000" },
  { "kind": "Unedited", "enabled": true, "choice": "unedited", "fields": ["userTags", "purchases"], "matchAll": false }
]
```

- `exclude`（bool・既定 false）：除くか。指紋に入れる（除くかどうかで結果が変わる）。
- `fields`（文字の並び・既定 `["userTags"]`）：未編集の項目。名前は `LocalField` の camelCase に揃える（`userTags`・`attributes`・`purchases`・`acquiredAt`・`memo`）。指紋に入れる（並べ替えてから）。
  すべてかどれかは今の `matchAll` を使う（未編集では「すべてが未入力」）。
- **同じ種類が複数あっても形は変わらない**（並びにもう1つ同じ `kind` の物が入るだけ）。番号や名前は持たない（並びの位置で決まる・§8-4）。
- **公開前なので古い形への救済は足さない**：前の版で書いた状態は `exclude` も `fields` も持たないので、既定の値（除かない・ユーザータグ）で読まれ、意味も今と同じになる。読み替えの道は作らない。
- 読めない値：`fields` の知らない名前は黙って飛ばす（`kind` と同じ扱い）。残りが0になったら既定（ユーザータグ）に戻す（手で直した JSON で「何も選ばない未編集」を作らない。対応アバターの「両方切った状態は作らない」と同じ）。
  1つまでの種類が2つ書かれていたら、2つ目を黙って飛ばす（今の作りが黙って捨てているのと同じ結果。報告は要らない画面の状態）。
  除くを持たない種類に `exclude: true` が書かれていたら、読まない（三項に除くは無い）。
- 検索の履歴（`search-history.json`）も同じ形。要約（`summary`）は「除く：」付きの文が入る。

## 8. 入口・履歴・キーボード・読み上げ

### 8-1. ほかの画面からの入口（`ShowOnly*`）

今は「条件の値を全部戻す → その種類を取り出して値を入れる」。案：**値を戻したあと、その種類のいちばん上の条件に入れる。無ければ §5-2 の位置に足す**（推し・D5）。
戻したあとは同じ種類の2つ目以降も空なので、絞るのは入れた1つだけになる。2つ目以降の空の条件は残す（人が足した物を勝手に消さない。クリアと同じ考え方）。
「条件をクリア」は除くも外す（足したときの姿に戻す・推し・D6）。外さないと、入口から入った値が「除く」で効いてしまう。

### 8-2. 検索の履歴・画面の履歴の控え（P4）

`ApplyHistory`：値を全部戻してから、状態を**種類ごとに順に**当てる。同じ種類の n 番目の状態は、パネルの同じ種類の n 番目の条件へ。足りなければ §5-2 の位置に足す。
今は2つ目の状態が1つ目を上書きする（§1-3）ので、ここは必ず直す。指紋は条件ごとの指紋を並べ替えてからつなぐので、複数・除くでもそのまま「同じ条件は積まない」が効く（`exclude` を指紋に入れれば）。

### 8-3. キーボード

- 見出しの止まる所：チェック → 札（除くのときだけ）→ 「…」→ ⌃ → ×（§4-2）。「…」は止まると出る。
- メニュー：Enter・Space で「…」を押して開く。Shift+F10・アプリケーションキーは枠の中のどこからでも（入力欄の中を除く）。
- 「上へ移動／下へ移動」をメニューに足すと、キーボードだけで並べ替えられる（今はドラッグだけ・推し・D9）。
- 条件の並び（パネル）を `ArrowGroup` にはしない。中に入力欄・スライダー・候補の欄が混ざり、`ui-input.md` の「入力欄・選ぶ欄・スライダーは並びに数えない」に当たって、矢印で移れる物がほとんど残らない。
  チップの並びは今どおり `ArrowGroup`。**別の担当が直している「検索などのカードの一覧を並びにする」直しとは、`SearchView.xaml` の別の所**（結果のカード）。同じファイルなので、実装はその直しが入ってから始める。

### 8-4. 読み上げの名前と ID

- 同じ種類が2つ以上あるときは、**2つ目から ID の種類の所に番号を付ける**：`SearchModule.Category.Input`（1つ目）、`SearchModule.Category-2.Input`（2つ目）（推し・D7）。
  1つ目は今の ID のままなので、確かめの道具と今の手順はそのまま動く。区切りの数（`.` で3つ）も変わらない。番号は並びの位置から毎回求める（動かすと振り直す）。条件に `IdKey` を持たせ、XAML の36か所を `{Binding Kind, …}` から `{Binding IdKey, …}` に替える。
- 名前も2つ目から番号を付ける：「カテゴリ（2つ目）の条件を外す」「カテゴリ（2つ目）で絞り込む」。見出しに見える文字は「カテゴリ」のまま（中身で見分けられる。番号を見せると、動かしたときに番号が替わって紛らわしい）。条件に `SpokenLabel` を持たせ、名前の31か所を替える。
- 新しい部品：「…」（名前「{SpokenLabel}の操作」・ID `SearchModule.{IdKey}.Menu`）、メニューの行（`.Menu.Exclude`（入・切を持つ行）・`.Menu.Collapse`・`.Menu.MoveUp`・`.Menu.MoveDown`・`.Menu.Remove`）、パネルの「…」（`SearchFilterMenu`・行 `SearchFilterMenu.GroupKinds`・§5-1）、
  札（名前「{SpokenLabel}を除くのをやめる」・ID `SearchModule.{IdKey}.Excluded`）、未編集の項目（`SearchModule.Unedited.Field.UserTags` など・名前は項目名）。
- `ui-ops.ps1` の `Add-ChmonosSearchCondition` は、足す前の同じ種類の数を数え、増えたのを待つように直す（2つ目を足すと、1つ目の × が既にあるので待ちが即座に抜ける）。`tools.md`・`pitfalls.md` に番号付きの ID を書く。

## 9. 照らす重さと順番（計測 2026-10-01）

ユーザの問い：「条件ごとに計算の重さが違うか、照らす順番が実際の速さに効くか。効くなら、それを考えた評価の順にしよう」。

### 9-1. 測り方

- `experiments/SearchFilterBench`。作り物の商品（2,000件・1万件・seed 固定。カテゴリの割合・アバター150体と素体10・BOOTHタグ500語・ショップ400・ユーザータグの大分類12・購入・ファイルの場所など）。友人のデータは使わない。
- 条件の部品はアプリの物：初期化しない `SearchViewModel` から非公開の `CreateModule` を呼び、`SearchModuleState` を `Load` して作る。絞り込みと件数の回し方（`Matches`・`RefreshFacetCounts`）は同じ形を写した。並べ替え・カードの作り直しは測っていない。
- 同じ処理を3回空回ししてから15回測り、中央値と最小〜最大を出す。**数は `DOTNET_TieredCompilation=0`（最初から最適化した翻訳）で測った物**。
  ふつうの起動（段の切り替え・PGO）だと、プロセスの初めの方は軽い翻訳のまま走って2,000件の方が1万件より重く出るなど、ぶれが大きかった。動き続けたアプリはおおむねこの数か、これより軽い（PGO の入った2,000件の件数で 2.08ms → 0.78ms のように、比は変わらない）。
  最初の1回（JIT 込み）は `cold` で別に、新しいプロセスで3回ずつ測った。
- spec の記録（実データ2,000件で絞り込み1回 11〜20ms＝照合 1.4〜6.6ms＋件数 4〜14ms）より作り物は軽い（対応アバターの数・説明の長さ・パスの深さが違う。並べ替えとカードも含まない）。**比べるのは比と伸び方**。

### 9-3. 照らす順を変えたとき（絞り込み1回 ms・条件を照らした数／件）

並び：「作り物の並び」＝対応アバター・所持・カテゴリ・価格・ユーザータグ・ファイルの場所・BOOTHタグ・公開日・属性・有料無料の順に先頭から。「軽く外れる物を先」＝1件あたりの重さ÷外れる割合が小さい順。「その逆」＝重くてよく当たる物が先。

| 件数 | 条件 | 作り物の並び | 軽く外れる物を先 | その逆 |
|---|---|---|---|---|
| 2,000 | 3 | 0.44（1.59個） | 0.41（1.49個） | 0.71（2.07個） |
| 2,000 | 6 | 0.55（1.75個） | 0.49（1.53個） | 2.21（2.46個） |
| 2,000 | 10 | 0.55（1.75個） | 0.23（1.12個） | 2.75（1.88個） |
| 1万 | 3 | 2.43 | 2.25 | 3.67 |
| 1万 | 6 | 3.02 | 2.59 | 11.43 |
| 1万 | 10 | 3.11 | 1.21 | 14.07 |

- **順は効く**：最良と最悪で4〜12倍。外れたら打ち切るので、先頭に軽くてよく外れる条件があるとほとんどの商品が1〜2個で終わる。
- ただし2,000件では最悪でも 2.75ms。人の並べた順がたまたま最悪に近い（ファイルの場所や公開日を先頭に置く）ときだけ差が出る。

### 9-4. 選択肢の件数（`RefreshFacetCounts`）と条件の数

案b：商品ごとに条件を上から照らし、**外れた条件を2つ目まで数える**（2つ外れた商品はどの条件の件数にも入らないので、そこで打ち切る）。
外れ0の商品は全条件の「他の全部」に、外れ1の商品はその条件の「他の全部」にだけ入る。照らすのは全商品×（2つ外れるまで）の1回だけで、その残りで値ごとの件数を数える。件数が今の作りと一致することを確かめた。

| 件数 | 条件の数 | 絞り込み | 件数（今） | 件数（案b） | 縮み |
|---|---:|---:|---:|---:|---:|
| 2,000 | 3 | 0.45 | 1.64 | 1.20 | 1.4倍 |
| 2,000 | 6 | 0.57 | 3.61 | 1.44 | 2.5倍 |
| 2,000 | 10 | 0.56 | 5.90 | 1.50 | 3.9倍 |
| 2,000 | 15 | 0.56 | 8.78 | 1.51 | 5.8倍 |
| 2,000 | 20 | 0.56 | 11.65 | 1.53 | 7.6倍 |
| 2,000 | 6＋文字列 | 0.56 | 3.64 | 0.44 | 8.3倍 |
| 1万 | 3 | 2.45 | 8.96 | 6.48 | 1.4倍 |
| 1万 | 6 | 3.00 | 19.75 | 7.63 | 2.6倍 |
| 1万 | 10 | 3.57 | 32.49 | 8.01 | 4.1倍 |
| 1万 | 20 | 3.07 | 64.04 | 7.97 | 8.0倍 |
| 1万 | 6＋文字列 | 3.01 | 19.50 | 2.52 | 7.7倍 |

（15・20 は「同じ種類を複数」「除く」で条件が増えた姿として、広めに当たる条件を足した。1万件・15 の案b は 8〜17ms とぶれた。）

- **1打鍵の重さの大半は件数**（絞り込みの3〜20倍）。今の作りは条件の数にほぼ比例して伸び（中で照らす数も増えるので、条件が多いほど1個あたりも重い）、案b はほとんど伸びない。
- 文字列を入れると、案b では文字列で外れる商品（76%）を条件より先に落とすので、さらに縮む（今は文字列を最後に照らす）。
- 案1・案2で条件が増える（同じ種類を2つ・除く用にもう1つ）ほど、今の作りの件数は効いてくる。

### 9-7. 人が感じる差

- **数百〜2,000件・条件10個まで**では、作り物で1打鍵 1〜7ms、spec の実データで 11〜20ms。照らす順を変えても縮むのは1〜2ms で、**人が感じる差は無い**（目安として、画面の1こまが約16ms）。
- 差が出るのは **1万件か、条件が10個を超えるとき**：1万件・条件20で件数だけ 64ms（今）→ 8ms（案b）。文字を打つたびに走るので、打つのが引っかかって感じられうる。
- 最初の1回の 180〜210ms は順では変わらない（起動の側で扱う）。
- おすすめ：**案1・案2を入れるときに b と c を一緒に入れる**（条件が増えたときの伸びを止め、1つずつの重さも下げる）。a は b・c の後に `perf-measure` で実データを測ってから。

- **§3-3・D1**：AND の要約は「A・B のすべて」（除くとき・除かないときとも。前の「A かつ B」から変えた）。
- **D23**：条件の名前は「編集状況」（三項は「未入力のみ／入力済みのみ／両方」）。種類の名前と ID は `Unedited` のまま。
- **D26**：設定の文言は「追加する条件を同じ種類の条件のすぐ下に置く」。
- **§9・D24**：案b・c を入れ、案a は入れていない。b・c の後に測り直した数は history の記録。

## 13. 条件を消す1回の重さ（計測 2026-10-02・担当SRC。追記）

ユーザ「検索モジュールの削除が少しもたついている気がする。削除で全て組み立て直しているのではないか？」（メモ2-①）。

### 13-1. 測り方

- **画面込み**：窓を出さずに描く台（`tools/ViewShot`）で主の窓を組み、作り物の商品を置いて検索を開き、条件を並べてから、
  「足したばかりのカテゴリ（何も絞っていない）」を消す1回を9回測った中央値。消す操作から `UpdateLayout` と `ContextIdle` の待ちまで（＝画面が描き終わるまで）。
  計測用の場面はコミットしていない（作業用フォルダで書いて消した）。
- **ViewModel だけ**：画面の試験の一式（`TestApp`）で同じ操作を Release で測り、`ApplyFilters` の中を private の関数ごとに分けた。

### 13-2. 直す前

| 商品 | 条件 | 消す1回（ViewModel だけ） | 消す1回（画面まで） |
|---|---|---|---|
| 200 | 3 | 0.3ms | 約190ms |
| 200 | 20 | 0.4ms | 約190ms |
| 2,000 | 3 | 0.4ms | 約200ms |
| 2,000 | 20 | 1.6ms | 約220ms（最大 590ms） |

- ViewModel の側は軽い（照らし直し 0.1〜1.9ms・件数の数え直し 0.0〜5ms・結果の組み直し 0.1ms 未満・メニューの作り直し 0.04ms 未満・番号の振り直し 0.01〜1.8ms）。
  **予想の「全部を組み立て直している」は当たっていなかった**（条件の並びからは消した1つを外すだけ。カードの段も差分だけ）。
- 画面まで約190ms のうち、**約90〜100ms は結果のリスト（`ItemListView`）の組み直し**だった。絞り直しのたびに `DisplayItems` を新しい並びとして渡していて、
  リストは中身が同じでも行を全部作り直す。しかも**カードで出している間（リストは隠れている）も渡していた**。
  何も変わらない絞り直し（効いていない条件を切って戻す）だけで、画面まで 95〜155ms かかっていた。
- 残りの約60〜90ms は、消した条件の枠を外して絞り込みの欄を並べ直す分（条件の数・商品の数でほぼ変わらない）。

### 13-3. 直したこと

- リストには `ListViewItems` を渡し、**カードで出している間は空**にした。
- 画面に出す並び（`DisplayItems`）は、**前と同じ並びなら前の入れ物のまま**渡す（参照で比べる。札は鍵ごとに使い回しているので比べられる）。
  消した条件が何も絞っていなかったときのように結果が変わらなければ、リストもカードの段も触らない。
- 照らし直しそのものは省いていない（2,000件・条件20で 1.5〜9ms。省く決まりを足すより、結果が同じなら画面に渡さない方が、どの道から来ても効く）。

### 13-4. 直した後

| 商品 | 条件 | 消す1回（画面まで） | 何も変わらない絞り直し（画面まで） |
|---|---|---|---|
| 200 | 3 | 約60ms（前 約190ms） | 0.4ms（前 約100〜130ms） |

- 測っていない事：アプリ本体を起動しての体感（担当が並行で動いていたので起動しなかった）。リストで出しているときに結果が**変わる**絞り直しは、今も行を組み直す
  （同じ作りのショップの中・フォルダの右は担当の外なので触っていない）。
