## 1. メモ60 未確定：登録と自動検索の進みを行ごとに分ける

### 今の作り

- **進みは画面に1つ**。`ResolveViewModel.Registering.cs` の `_registeringArea`・`_registeringDone/_registeringTotal`・`_registeringRequestsLeft` と、
  `ResolveViewModel.Candidates.cs` の `SearchPhase/SearchCurrent/SearchTotal`（`IsSearching`）は、どちらも画面の ViewModel に1組だけある。
  右の欄（`ResolveView.xaml` の `RegisteringStrip`・候補の欄の進み）はどの行を選んでいてもこの1組を出すので、別の行を選んでも同じ帯が出る。
- **登録中は画面全体の `IsBusy` が立つ**。`AssignCommand`・`ExcludeCommand`・`RegisterLocalCommand`・`PreviewCommand`・フォルダの登録・見つからないIDのまま登録が、
  どの行でも押せない。自動検索も `IsBusy` を立てるので、検索の間は登録も除外も押せない。左の一覧の選び直しはできる。
- **登録1件の中身**（`ItemService.AssignItemIdAsync` → `FetchNewItemAsync`）：手元に無い商品なら、商品JSON・商品ページ・**画像を全部**・ショップのアイコンを順に取る。
  問い合わせの数は「2 ＋ 画像の枚数 ＋ アイコン（無ければ1）」。その後、対応アバターの検出を裏で頼む（`Detection` の段。登録の進みには入らない）。
  確かめ（`PreviewItem`）は商品JSONを1回取るが、登録のときにもう一度取る（控えは無い）。
- **優先度**：`CommandHandler` の入口が `User`（0）を張る。登録の中の画像も同じ `User`。自動検索（`ProposeCandidates`）は `Foreground`（-1）。取り込みの①②は `Metadata`（2）。
- **門**（`PriorityGate`＋`BoothMachineGate`）：1本ずつ、間隔は設定（最小1.5秒）。空いたら優先度の高い順、**同じ優先度の中は着いた順**。
- **終わったら次へ**：1件の登録が済むと `AfterSettled()` が「今選んでいる行」を一覧から外して次の行を選ぶ。
- **画面は開くたびに作り直す**（フォルダビューの右にも別に作られる）。確定した商品のID（`ResolveSettledItemIds`）は主画面が、自動検索の結果（`RememberedSearches`）は静的に持つ。
  自動検索の「走っている」は主画面の長い作業の帯（`BeginLongJob`）にあり、ほかの長い作業と自動検索は押せなくなる（`ProposeHint` が理由を出す）。

### 登録を複数並べたときに、BOOTH への問い合わせがどうなるか（確かめた）

| 決め事 | 今の作りで並べたら | 理由 |
|---|---|---|
| 1本ずつ | **守られる** | 問い合わせは全部 `BoothClient` の門を通る。何本並べても門が1本ずつ通す |
| 1.5秒以上空ける | **守られる** | 間隔も門の中（PC で1つの門）で守る |
| 優先度どおり | **守られる** | 自動検索（-1）＞登録（0）＞取り込み（2）。登録の途中でも、自動検索の問い合わせが次に割り込む |
| **登録が1件ずつ順に終わる** | **守られない** | 2件の登録は同じ `User` の段に並ぶので、A の JSON → B の JSON → A のページ → B のページ…と**交互に**進み、どちらも遅く終わる |
| 同じ商品を2行で登録 | 無駄が出る | 2本とも「手元に無い」と見て、同じ商品を2回取る（書き込みは `CreateOrChangeLocalAsync` が錠の中で合わせるので壊れはしない） |

つまり、ユーザの言う「順番に並ぶだけ」は門だけでは出ない。**登録を1件ずつ流す順番待ちを、門の手前にもう1つ置く**必要がある。

あわせて見つけた所（直していない）：`AssignAsync` は登録が済んだ後に `AfterSettled()` で「その時に選んでいる行」を外す。
登録の間に別の行を選ぶと、**登録した行ではなく選び直した行が一覧から消え**、登録した行が残る（記録は正しく、開き直せば直る）。行ごとにするとき一緒に直す。

### ユーザの言葉と決定

> 登録のプログレスバーは個別の進行状態を表し他を妨げないが、自動検索は個別の進行状態を表しながら他を妨げる。
> 登録が完了した時に次の候補に自動で移動するのは、登録が完了した時点でその商品にとどまっていた時だけ。

### 案

**登録の順番待ち（`RegistrationQueue`）を1つ作り、主画面が持つ。**

- 押した登録は「1件の仕事」として列に積む。仕事は対象のハッシュ（束なら全部）・商品ID・名前・見込みの問い合わせ数を持つ。
- 列は**1件ずつ**、今までと同じ `UiCommand.AssignItemId` を呼んで流す（`UiCommand` 1本の決まりはそのまま。入口で `User` も張られる）。
- 問い合わせの要らない登録（手元にある商品へ足す・BOOTHに無い商品・見つからないIDのまま・フォルダ）は列に積まずにすぐ走らせる（数十ms で終わる。並ばせる理由が無い）。
- 主画面が持つので、画面を離れて戻っても・フォルダビューの右でも、同じ列を映す。行は**ハッシュ**で列と結ぶ（行は読み直しで作り直されるため）。
- **見込み**：確かめ（`PreviewItem`）で商品JSONを取っているので、`ItemPreview` に画像の枚数（とアイコンが要るか）を足せば、押した時点で「この商品は約 m 分」が出せる。
  「開始まで約 n 分」は、走っている仕事の残り（今ある `requestsLeft`）＋前に並んだ仕事の見込みの合計 × 間隔。
  自動検索が割り込むと延びるので「約」とする（今の「BOOTHへあと n 件・約 m 分」と同じ数え方）。
- **行の見た目**：左の一覧の行に札「登録待ち 2番目」「登録中」「登録できませんでした」。右の欄（その行を選んでいるとき）に
  「別の商品を登録中。開始まで約 n 分・この商品は約 m 分」、走っている行は今の帯（残りの数の棒）。
- **押せる・押せない**：画面全体の `IsBusy` をやめ、**列にいる行だけ**登録・除外を押せなくする。ほかの行は確かめも登録も除外もできる。
- **終わったとき**：その行を一覧から外す。**終わった時点でその行を選んでいたときだけ**次の行へ移る（`AfterSettled` を「外す行」を受け取る形に直す）。
  選んでいなければ、一覧の上に「『〇〇』を登録しました。」を出すだけ（今の束の登録と同じ置き場）。
- **自動検索**：走っている間の状態（対象・段階・n / m）を主画面へ移す（画面を離れて戻っても出るように）。
  候補の欄の進みは、**選んでいる行が検索中の対象のときだけ**出す。ほかの行の「自動検索」は押せず、吹き出しを「ほかの商品の検索を進めています。」にする。
  検索は `IsBusy` を立てない（登録・除外を妨げない）。長い作業の帯は今のまま1本で、検出・書き出しとは今までどおり重ねない。
  左の一覧の検索中の行にも札「検索中」。
- **閉じるとき**：列に残っている仕事があれば聞く（「登録を待っている商品が n 件あります。閉じると登録されません。」）。今の `IPendingWrites` と同じ形。

**案B（あわせて選べる）：1件の登録を短くする。**
登録のときは JSON・商品ページ・1枚目の画像（④）だけを取り、残りの画像を梯子の⑤（`Gallery` の段）に回す。
1件が「2＋画像の枚数＋1」から「3＋1」に縮み、順番待ちが目に見えて短くなる。
代わりに、残りの画像は取り込みの⑤と同じく後から来る（今の⑤は起動時の裏の作業。登録の直後に⑤を1件だけ頼む道を足す）。
画像は人が登録の直後に見たい物でもあるので、決め事として聞く。

### 触る所と大きさ

- Core：`ItemPreview` に画像の枚数（とアイコンが要るか）。案Bを選べば `FetchNewItemAsync` の画像の取り方と、⑤を1件頼む道。**小**

  自動検索の状態を主画面へ。`ResolveView.xaml` の行の札・右の帯・候補の欄の進み。閉じるときの確認。**大**（500〜800行）

### 決めてほしい点

1. **列を置く場所**：A 主画面が持つ（画面を離れても進み、戻れば映る）／B 未確定の画面が持つ（離れたら列は止める）。

## 2. メモ44 改変の複製

### 今の作り

- 改変は `modifications/mod-{hash8}.json` に1件ずつ（`ModificationRecord`）。ID は「アバター＋名前＋作った時刻」から1度だけ作る。同じ名前を許す（作るときに知らせる）。
- 欄：`avatarItemId`・`name`・`createdAt`/`updatedAt`・`unityProject`（0か1。プロジェクトから見ると多対1を許す）・`memo`・`blueprintId`・`images`（`images/_mods/{改変ID}/`、ファイル名は中身のハッシュ）・`members`（導入の順。外した行 `detached` も残る）。
- 命令は `UiCommand.CreateModification`（空で作る）ほか1項目ずつ。**複製は無い。**
- 置き場の候補：改変の画面（`ModificationHubView`）の左の一覧の行には**右クリックのメニューが無い**。改変の詳細（`ModificationView`）の上の帯に「この改変を削除」（改変の画面に組み込んだときだけ）。

### ユーザの言葉

> 改変は複製できた方が良い。

### 案

**命令 `UiCommand.DuplicateModification(元の ID, 新しい名前)` を1つ足し、Core（`ModificationService.DuplicateAsync`）で新しい改変を作って返す。**
名前は「〇〇のコピー」。同じアバターに同じ名前があれば「〇〇のコピー 2」…（同じ名前は許されているが、複製の直後に同じ名前が2つ並ぶと見分けが付かない）。

写す物・写さない物の案：

| 欄 | 案 | 理由 |
|---|---|---|
| アバター | 写す | 改変はアバター1体＋名前で1つ |
| 使ったもの（`members`） | **写す**（順・使ったファイル・unitypackage・種類） | 複製したい理由の本体（同じ組み合わせから少し変える） |
| 外した行 | 写さない | 外したのは元の改変での判断。新しい方に持ち越すと「何を外したのか」が意味を失う |
| メモ | 写す | 組み合わせの覚え書きは同じく効く。要らなければ消せる |
| Unity プロジェクト | 決めてほしい（下） | 同じプロジェクトで着せ分けるなら写したい。別のプロジェクトに組み直すなら要らない |
| blueprint ID | **写さない** | 1つの改変＝1つのアップロード。写すと2つの改変から同じアバターへ着替えることになり、記録が嘘になる |
| 写真 | **写さない** | 写真は組み合わせた結果の姿。新しい改変はこれから変わるので、元の姿が残ると取り違える（0枚なら「写真はまだありません」が出る） |
| 作った日・更新日 | 今の時刻 | 新しい記録 |

置き場：改変の画面の左の一覧の**改変の行の右クリック**に「複製」（メニューを新しく作る。今は無い）と、改変の詳細の上の帯（「この改変を削除」の左）に「複製」。
押したら新しい改変を右に開き、名前の欄を変える状態にしてフォーカスを置く（名前を変えるのが次の一手なので）。

別のアバターへ写す（「同じ衣装の組を別のアバターに」）は、案として次に回す（複製の後でアバターを変える道が今は無い。アバターを変えると ID の決め方とも絡む）。

### 触る所と大きさ

- Core：`UiCommand`・`CommandHandler` に1件、`ModificationService.DuplicateAsync`（名前の決め方は `internal static` にして試験）。写真を写すなら `ImagePipeline` に改変の画像の写しを1つ（書き込みの門を通す）。**小**
- App：改変の画面の行の右クリック（`ModificationHubView.xaml`・`ModificationHubViewModel`）、改変の詳細のボタン。作った後に開いて名前の欄へ。**小〜中**
- 文書：`docs/spec/modifications.md`・`features.md`。

### 決めてほしい点

1. **Unity プロジェクトとの紐付け**：A 写す（同じプロジェクトで着せ分ける使い方）／B 写さない（組み直すときに選び直す）。
2. **写真**：写さない（おすすめ）でよいか。
3. **外した行**：写さない（おすすめ）でよいか。
4. 置き場は右クリックと詳細のボタンの両方でよいか。

### おすすめ

1-A（写す。プロジェクトは多対1を許していて、違えば「替える」で聞いてから替えられる。写さないと、同じプロジェクトで分けたい人が毎回選び直す）。2・3 は写さない。4 は両方。


### ユーザの決定（2026-10-05）

- 1：**A**（Unity プロジェクトとの紐付けを写す）
- 2・3：おすすめどおり（写真と外した行は写さない）
- 4：置き場は右クリックと詳細のボタンの**両方**

## 3. メモ46 共通素体の側からアバターを足す・外す

### 今の作り

- アバターの所属は登録簿の各行の `BaseName`（1体に1つ）。書くのは `UiCommand.SetAvatarBase(アバターID, 名前 or null)` → `AvatarService.SetBaseAsync`（登録簿を錠の中で書き換え、無い素体なら手で足した素体として作る）。
- **所属の数え方は「手で決めた所属 ＋ 名前から推した仲間」**（`AvatarCompatibilityIndex.Build`）。`BaseName` が空のアバターは、名前・別名の「#MARUBODY」「（〇〇素体）」「+Head」から毎回推す（保存しない）。
- 素体の詳細の「この素体を使っているアバター」（`SelectedBaseMembers`）は推した仲間も含めて並ぶ。足す欄は無い。
- アバターの詳細の素体の欄は `BaseName` だけを映し、**推した素体は出さない**。「素体から外す」は `BaseName` を空にするだけなので、**推した仲間は外せない**（空にしても、また推されて同じ素体に入る）。
  今もアバターの側で「欄は空なのに、素体の一覧には入っている」アバターがある（名前から推された物）。

### ユーザの言葉

> 共通素体側からもアバターを追加できるか？

### 案

- 素体の詳細の「この素体を使っているアバター」の一覧の上に、**アバターを足す欄**（候補付き `SuggestBox`。登録簿のアバターのうち、この素体に入っていない物。絵付き。
  ほかの素体に入っている物は添え書き「今は『〇〇』」）。選ぶと `SetAvatarBase(そのアバター, この素体)`。
  1体に素体は1つなので、ほかの素体に入っていた物は**移る**。アバターの側で一覧から選ぶと聞かずに入るのと揃え、聞かずに移して欄の下に「『A』を『〇〇』から移しました。」。
- 一覧の行の右クリックに「この素体から外す」。
  - 手で入れた所属なら `SetAvatarBase(そのアバター, null)`。
  - **推した仲間**は今のデータでは外せない。2つの道がある：
    - **案A**：推した仲間の行に札「名前から」を出し、「外す」は出さない（吹き出しで「名前の『#〇〇』から入っています。」）。データは増やさない。
    - **案B**：登録簿の行に「素体なし」を手で決めた印（例 `noBase: true`。立っているときだけ書く）を足し、推しを止める。外すとこの印を立て、素体を選び直すと印を下ろす。
      アバターの側の「素体から外す」も、推した素体に対してこの印を立てるようにすれば、両方の側の食い違いも消える。
- アバターの詳細の素体の欄に、推した素体を薄く出す（「名前から：〇〇」）。今の食い違い（欄は空なのに素体の一覧に入っている）を見えるようにする。案A・Bのどちらでも要る。

### 触る所と大きさ

- Core：案Aなら無し（`SetAvatarBase` をそのまま使う）。アバターの詳細に推した素体を出すため、`AvatarSummary` に推した素体名を1つ足す（`BaseNameOf` は今どこからも使われていない）。
  案Bなら登録簿の行に印1つ・`AvatarCompatibilityIndex.Build` で印を見る・`SetBaseAsync` で印を下ろす。**小**
- App：`AvatarsView.xaml` の素体の詳細に欄と右クリック、`AvatarsViewModel` に候補と2つの命令、アバターの詳細の素体の欄の薄い字。**小〜中**

### 決めてほしい点

## 4. メモ47 ナビを矢印で移る

### 今の作り

- ナビ（`MainWindow.xaml` の `NavRail`）は手で並べた `Button` の縦の並び：上から 戻る・進む（横に2つ）・畳む、見出し「ライブラリ」、検索・改変・ショップ・フォルダ・統計、
  見出し「作業」、取り込み・未確定・編集、見出し「管理」、通知・アバター・タグ・属性。ここまでが送る入れ物（`NavScroller`）の中。
  その下に送らない場所で、BOOTH の形式の知らせ（出ているときだけ）と「設定」。上下に続きがある印（`NavMoreAbove/Below`）は重ねるだけで止まらない。
- どの項目も Tab で1つずつ止まる（14〜16回）。
- ほかの並びは `ArrowGroup`（`Controls/ArrowGroup.cs`）：`ItemsControl` に付けると、Tab では1回だけ止まり、中は矢印で移る。
  仮想化していない一覧では、上下も**画面の上の位置**で近い物へ移る（`ArrowStep`）。前にいた所を覚え、次に Tab で入るとそこへ止まる。

### ユーザの言葉

> ナビもtab移動がかさむので矢印での移動にしたい。

### 案

**案A：送る入れ物の中を `ItemsControl` に包み、`ArrowGroup` を付ける。**
`ItemsControl` は子に部品をそのまま並べると、部品が自分の器になる。`ArrowGroup` は器の中の止まり先を集めるので、手で並べたボタンがそのまま並びになる（見出しの文字は止まらないので飛ばされる）。
上下は位置で近い物へ移るので、戻る・進む（横並び）は ←→、畳む・項目は ↑↓ で移る。Enter・Space はボタンがそのまま受けて開く。
フォーカスが送る入れ物の外の項目へ移ると、WPF の `BringIntoView` で送られ、続きの印も今の作り（`OnNavScrollChanged`）で付け直される。畳んだナビも同じボタンなのでそのまま効く。

**案B：ナビ専用のキーの処理を `MainWindow.xaml.cs` に書く。**
並びの決め方を自由にできる（「設定」まで↓で届かせる、など）が、矢印の移り方がほかの並びと別の作りになる。

どちらでも決めておく所：

- **「設定」とBOOTHの形式の知らせ**は送る入れ物の外にある。案Aでは別の並びになり、Tab で止まる所は「ナビの並び」「（知らせ）」「設定」の2〜3つ。
  ↓で「設定」まで届かせたいなら、`ArrowGroup` に「並びの端で、続きの並びへ移る」を足す（小さい足し算）か、ナビ全体を1つの `ItemsControl` にして下端に固定する作りに組み直す。
- **Tab で入ったときに止まる所**：`ArrowGroup` は前にいた所を覚えるが、ナビは「今開いている画面の項目」に止まる方が分かりやすい。`ArrowGroup` に「入る所を決める」口（例 `IsPreferredStop` の添付プロパティ）を足す。
- Alt+←→（戻る・進む）は修飾キー付きなので `ArrowGroup` は受けない（今の作りのまま）。

### 触る所と大きさ

- App：`MainWindow.xaml` のナビの並びを `ItemsControl` で包む、`ArrowGroup` に「入る所を決める」口（と、要るなら「続きの並びへ」）。**小**（100〜200行）
- 確かめ：キーで移るのは描画が要らない所なので UIA で押して止まる所を見る。並びの見た目が変わっていないことは `tools/ViewShot` で前後を比べる。
- 文書：`docs/spec/ui-rules.md` のナビの節。

### 決めてほしい点

1. 案A（ほかの並びと同じ作り）か案B（ナビ専用）か。
2. **「設定」**：A 別に Tab で止まる（ナビの並び＋設定の2つ）／B ↓で設定まで届く（1つの並び）。
3. Tab で入ったとき：A 今開いている画面の項目／B 前にいた所（ほかの並びと同じ）。
4. 戻る・進む・畳むも並びに入れるか（入れなければ、それぞれ Tab で止まる）。

### おすすめ

1-A・2-B（↓で設定まで行けないと「最後の1つだけ Tab」で覚えることが増える）・3-A・4 は入れる（ナビの上の3つも同じ縦の列にあるので、矢印で届く方が自然）。


### ユーザの決定（2026-10-05）

- 1：**A**（`ArrowGroup` を付けて、ほかの並びと同じ作りに）
- 2：**B**（↓で設定まで届く1つの並び）。ただしユーザは A（設定が別に Tab で止まる）も直感的だと言っている
- 3：**A**（Tab で入ったときは今開いている画面の項目に止まる）
- 4：戻る・進む・畳むも**並びに入れる**。ただし **Tab でも動けた方が自然**（矢印だけでしか届かない形にしない）

- 3と4の食い違いの確認に対して：**案X**（外から Tab で入ると今の画面の項目に止まり、ナビの中は矢印でも Tab・Shift+Tab でも1つずつ動く。設定から Tab で画面の中身へ出る）。違和感があればユーザが言うので、**手で見る確認項目に必ず出す**

## 5. メモ45 購入記録ごとの日付

### 今の作り

- 日付は商品に1つ：入手日 `LocalBlock.AcquiredAt`（`DateOnly?`。持ち主は編集画面）。購入記録 `Purchase` は種類・名前の写し・価格・種別・メモを持ち、日付は持たない。
- 入手日を使う所は2通りに分かれている：
  - **空ならファイルの日付で代える**（`AcquiredDateResolver.Resolve`。代えたことを `IsFallback` で持つ）：統計の月ごと・年ごとの支出と「日付の無い支出」（`StatsService`）、月ごとのカテゴリ構成（`StatsExtras.MonthlyCategories`）、

### 決定（2026-10-05）

> 購入記録ごとの日付を、商品の日付（入手日）とは別に持つ。空（null）でなければ、要る場面（統計の月ごとの支出・入手日の検索や並べ替え など）で商品の日付より優先して使う。
> 空のときは今までどおり商品の日付。空を推定で埋めない。

### 案

**持つ欄**：`Purchase.PurchasedAt`（`DateOnly?`。JSON は `purchasedAt`、空なら書かない）。名前は「入手日」と分けるため「買った日」。贈った・貰った行も同じ欄（贈った日・貰った日）。

**1つの決まりにまとめる**：Core に `PurchaseDates`（仮）を作り、場面はここだけを呼ぶ。

- 購入1件の日付 ＝ `PurchasedAt` があればそれ、無ければ**商品の日付**。
- 商品の日付 ＝ 今の2通りのまま（ファイルの日付で代える場面と、代えない場面）。ここは変えない。

  入手日は「最初に手に入れた日」の意味で使ってきた（ファイルの日付も古い方を採る）ので、それに揃える。

**場面ごとの表**（何を優先するか）：

| 場面 | 今 | 案 |
|---|---|---|

## 6. メモ51 通知：商品を指して開いたら、その商品の通知を強調する

### 今の作り

- 通知の画面（`InboxViewModel`）は、束（種類ごと）の見出しと行を**平らな1本の一覧**（`Lines`）に並べて仮想化している（`ScrollUnit=Pixel`）。束の並びは「重要がある束 → 新しい知らせのある束」、束の中は新しい順。
- カード・ショップの「更新の通知を開く」は `MainViewModel.ShowInboxFor(商品ID)` で開く。今も `FocusRequestedItem` が「商品ページの変更」の束を開き、その商品の行（未読を先）まで**送るだけ**はしている。
  送り方は `BringIndexIntoViewPublic` なので、行は画面の端（下の端）に来ることが多い。送った後は商品IDを忘れる（読み直しで同じ所へ戻されないように）。強調は無い。
- 「商品ページの変更」は商品ごとに未読が1件（同じ ID の未読は差し替える）。既読の古い分は残るので、同じ商品に既読の行が複数並ぶことがある。
  ほかの束（消えたバリエーション・復活したバリエーション・非公開商品の復活・zipを入手した・展開先のファイルを取り込んだ・タグの参照切れ…）にも同じ商品の行があり得る。

### 決定（2026-10-05）

> 自動で流して強調するのは「商品ページの変更」の束のその商品の行。ほかの束にもその商品の通知があれば、その束の見出しに分かる印を出し、束を開いたときはその商品の行がいちばん上に来るようにする。

### 案

- **指した商品を画面の間ずっと持つ**（`_targetItemId`）。送るのは開いたときの1回だけ（今の `_focusItemId` は「送る」用として残す）。
- **束の中の並び**：指した商品の行を、**どの束でも束の先頭**に寄せる（未読を先、次に新しい順）。決定の「開いたときにいちばん上」は、開く前から先頭にしておけば満たせる。
  「商品ページの変更」の束でも先頭に寄せると、送る先が「束の見出しのすぐ下」になり、見出しと行が一緒に画面の上に来る。
- **送り方**：その束の**見出しの行を画面のいちばん上**に合わせる（`BringIndexIntoViewPublic` の後に、行の位置を測って `ScrollToVerticalOffset` で上へ寄せる。`ScrollUnit=Pixel` なので位置で合わせる）。束が畳まれていれば開く（今と同じ）。
- **強調**：`NotificationRow.IsTarget` を足し、行の地の色を強調の色（色の表に鍵を1つ足す。明るい・暗い両方）と左の縦線で描く。
  アニメーションはしない。消えるのは画面を離れたとき（決め事に無かったので下で聞く）。
- **ほかの束の見出しの印**：`NotificationGroup.TargetCount`（その束にある指した商品の行の数）を足し、見出しの札の並びに「この商品 n」（強調と同じ色）。畳んでいても見える。
- **「未読のみ」のとき**：指した商品の行が既読なら出ない。見出しの印は出ている行だけで数える（出ない行を数えると、開いても何も無い）。
- `Rebuild`・`RebuildLines` は今の差分で入れ替える作りのまま、並べる順だけを変える。指した商品が無いとき（ナビから開いたとき）は何も変わらない。

### 触る所と大きさ

- App：`InboxViewModel`（指した商品・束の中の並び・行と束の印）、`InboxView.xaml`（行の強調・見出しの札）、`InboxView.xaml.cs`（上へ寄せる送り方）、色の表に1つ。**小〜中**（150〜250行）
- 試験：束の中の並び・印の数・未読のみとの組み合わせ・ナビから開いたときに変わらないこと（App の試験）。上へ寄せる送り方と色は `tools/ViewShot` で描いて見る。
- 文書：`docs/spec/notifications.md`。

### 決めてほしい点

1. **強調が消える時**：A 画面にいる間ずっと／B 数秒で消える／C どこかを押すまで。
2. 指した商品の行を束の先頭に寄せるのを、「商品ページの変更」の束にも当てるか（当てると送り方が単純になり、同じ商品の既読の古い行もまとまって見える）。
3. 見出しの印の文言（「この商品 n」など。`ui-wording` で整える）。

### おすすめ

1-A（時間で消えると、一瞬目を離した人がまた探すことになる。画面を離れれば消えるので残り続けることは無い）・2 は当てる・3 は「この商品 n」を起点に `ui-wording`。


### ユーザの決定（2026-10-05）

- 1：**A**（強調は画面にいる間ずっと）
- 2：**当てる**（「商品ページの変更」の束でも、その商品の行を先頭に寄せる）
- 3：見出しの印の文言は ui-wording で整える（「この商品 n」が起点）
