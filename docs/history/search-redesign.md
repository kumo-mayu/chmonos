    -  AND : 全てを満すもの
    - OR : いずれかを満すもの

- 上下指定 : ユーザが範囲を指定する方式。指定されていない方は制限せずに開いたものと考える
    - 数値 : ユーザが数値の範囲を指定するもの
        - 単品 : 一つのスライダーのみが存在する
        - AND : 全てを満すもの
        - OR : いずれかを満すもの
    - カレンダー : ユーザが日付などで範囲を指定するもの。日まで指定でき、指定日をまるまる含む。結果的には数値となるが、ユーザが日付データなどを気にする必要はない。基本はテキスト欄の見た目をしているが、右端にカレンダアイコンがあり、そこをクリックすると出てくる

        - カレンダ入力 : 視覚的なカレンダを使って日付を指定できる。

- 三項 : プルダウンを使って条件を指定する方式。追加時のデフォルトは項の先頭にdefと表記している。実際にはdef部分を表示しなくてよい。あなたへの指示でのみの表記だ
    - トグル拡張 : 本来ならトグルで表現できるものでもユーザが条件に含めたまま無効化できるように何も絞らない条件を加えているものがある。

### 2-2. 今のデータでは作れない・そのままでは意味が決まらない条件

- **価格（BOOTH）**：BOOTH の価格は商品全体では**表示用の文字列（`PriceText`「¥ 2,500」）しか持っていない**。数値は種類ごと（`BoothVariation.Price`）にある。種類が複数あるとき「単品」の範囲をどの値で見るか（最安・最高・どれか1つでも入れば）が決まらない。**今の「価格」の条件は自分が払った額**（spec）なので、名前が同じで意味が変わる。
- **有料無料**：種類ごとの価格が 0 かで作れる（「両方の種類があれば両方に出す」も作れる）。BOOTH に無い商品は種類が0件なので、どちらに出すかが決まらない。購入記録の価格 0（無料配布を貰った）とも別。
- **販売終了**：印が3つある——販売終了（`IsEndOfSale`）・売り切れ（`IsSoldOut`）・非公開・削除と確定（`IsDelisted`・404が続いた）。どれ（の組み合わせ）を指すかが決まらない。
- **ギフト**：購入記録の種類（自分用・貰った・贈った）で作れる。**購入記録が1件も無い商品が多い**（編集で入れるまで無い）ので、それを「購入」に入れるかが決まらない。「購入（無料のみではない）」の意味（無料で入手した物も「購入」に入れる、の意味か）を確かめたい。
- **未編集**：今は「ユーザタグが0件（検出待ちを除く）」。編集画面で保存したかどうかではない。この定義でよいか。
- **UnityProject**：「改変経由でそのプロジェクトに紐付いた商品」なのか、「プロジェクトの中に実在する商品」（`UnityProjectMatcher`・開くたびに zip の中身と照らすので重い）なのか。
- **大文字と小文字・全角と半角を区別する**：今は探す側も探される側も、商品ごとに1度だけ **NFKC＋小文字に畳んだ文字列**を作って持っている（入力1文字ごとに全商品の説明文を畳まないため・`SearchText`）。区別するには畳まない写しも持つ必要があり、メモリが増える（本文を含めると増える。量は測っていない）。また NFKC は全角・半角のほかに ①→1・㈱→(株) のような互換文字も畳み、**全角で打った括弧・引用符・ハイフン・空白を構文として読むのも NFKC に頼っている**。「全角と半角を区別する」を入れても、構文の記号は畳む必要がある。
- **日英変換（カタカナ→英語）**：**今は無い経路**（今の経路はローマ字→読み・読み→カタカナ・読み→辞書・英語→辞書の4つ・`BridgeRoute`）。同梱の JMdict で引ける見込みだが、測っていない。
- **造語変換**：今は KANJIDIC2 の**音読みと訓読みの両方**から、**商品名の側**に読みを組んで照らす（「撫で音」→ なでおと）。案は「訓読みから推定」。訓読みだけにすると `nadeoto` は届く（撫で＝訓・音＝訓）が、音読みの造語は落ちる。
- **ファイル名**：今の「パス」は手元のファイルの保存場所の全体（ファイル名を含む）。案の「ファイル名」が、手元のファイル名なのか、zip の中のファイル名（`Contents`）なのかが決まらない。

### 2-3. 既存の仕様との食い違い

| 案 | 今の決め事（spec・経緯） |
|---|---|
| 別表記は既定オフで、0件のときは中央に「別表記でも検索する」ボタン | **0件なら自動で広げる**（「悪くなりようがない」・`docs/spec/search.md`「文字列」） |
| 文字列の対象に BOOTHタグ・カテゴリが無い | 既定の対象に BOOTHタグ・自分で入れたカテゴリが入っている |
| サブドメインは既定オフ | 既定の対象に入っている |
| 平仮名と片仮名を区別（既定オン） | 検索画面は区別する（同じ）。ただしフォルダビュー・改変の画面の探す欄・画面内の検索（Ctrl+F）は区別しない |
| 条件を追加した物（有効・無効を含む） | **積んだ条件は種類だけ覚える。値は覚えない**（`ui-state.json`・「なぜか少ない」で始まるのを防ぐ） |

### 2-4. 今の文字列検索・表記変換・辞書の仕組みと評価（確かめたこと）

- 構文：スペース＝AND・`-語`・`"…"`・`OR`・`( )`（案と同じ）。NFKC で畳んでから読むので、全角で打った記号も効く。
- 対象：既定＝商品名（自分の名前と BOOTH の名前）・ショップ名（両方）・サブドメイン・自分で入れたカテゴリ・メモ・BOOTHタグ。「本文も探す」＝説明文と h2 の見出し・本文。「ファイルのパスも探す」＝手元のファイルの保存場所。商品名の読み＝広げるときだけ。
- 表記をまたぐ：同梱の JMdict（CC BY-SA 4.0・無改変で同梱し索引は初回に手元で組む・組み上げ2.1秒・キャッシュ17MB）と KANJIDIC2（造語）。式の木を `Or(Term, 別表記…)` に組み替え、何で当たったかを出す。1文字のかなは候補にしない。英語は6語・読みは4語まで。
- 評価（`docs/history/ui-revision.md` §2・2026-09-10・手元15件に実際に打ちそうな10語）：引けた語 2/10 → 9/10、誤爆1件（`nadeoto` が「音」で心音ギミックも拾う）。`shinon` は「しのん」「しんおん」の両方に読んで心音に届くようにした。類義語辞書は入れない（足した分の4件に3件が無関係）。
- 通信は使わない（前に試した Google Transliterate・Jisho は同梱の辞書に置き換えた）。
