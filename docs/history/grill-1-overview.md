## Item ↔ LocalFile

* Item : LocalFile は 1:N。`filepath` / `ファイル容量` / `contents` / `hash` はItem直下ではなく、Item配下の`LocalFile[]`配列の要素に持たせる。
* `is_downloaded` はItemレベルの計算値（`LocalFile.length > 0`）として再定義する。
* LocalFileは任意で`variations`のID（variation_id）に紐付けられる。紐付いていればエクスプローラへの直接ジャンプ等に使える。必須にはしない（ユーザ自身どのzipがどのvariationか判別できないケースがあるため）。
* 同一Itemに対して同一hashが既に登録済みなら、再取込み時は自動スキップする。パスが違うだけの同一実体は複数パスとして記録するが、容量計算では二重カウントしない。ユーザがUI上で重複に気付ける表示をする。
* LocalFile.variation_idが指すvariationがBOOTH側の更新で消滅した場合は、decideには混ぜず、後述の「要確認」受信箱に通知する。

## decideの責務

* decide対象かどうかは保存されたステータスフラグではなく、「appTagのトップレベルが未設定」を必須条件とした計算値にする。属性・メモ・対応アバター・購入variationは永久に任意。
* `ordered_variations`が指す選択肢がBOOTH側の更新で消滅した場合、自動的にdecide対象へ再浮上させる。
* ユーザが自分から「decideし直したい」と選んだitemもdecide対象にできる。その場合、appTag/属性/メモ/ordered_variationsは空にリセットせず、既存値を初期値として編集可能な状態で開く。

## appTag / 属性 / category / BOOTH tagsの役割分担

* `category`（BOOTH由来）と`tags`（BOOTH由来）は常にread-only。ローカルで改変しない。フェッチのたびの差分マージを複雑にしないため。不満があればappTag/属性で独自の分類を追加する。
* appTagはユーザ管理用のマスタ（toplevelとsublevelsが対応したKVリスト、tag画面で追加削除を含めて編集可能）。1itemに対してトップレベルは複数選択可能。検索ではそのitemに選択されている全トップレベルがヒット対象になる。
* サブレベルはトップレベルごとに個別に選択する（複数トップレベル横断のフラットなプールにはしない）。あるトップレベルを後から解除した場合、その配下で選んでいたサブレベルは自動的に外す。
* 一覧表示ではトップレベルは全て表示する。サブレベルは設定でオプション表示。
* 属性はappTagとは別の、階層のないフリーフォームな複数値タグ集合として構造化する（メモのような単なる自由記述文にはしない）。「かわいい」のような曖昧な印象でもフィルタ可能な離散値として持たせる。

## 検索モデル

* 離散値（category / appTag / 属性 / 対応アバター等）はファセットフィルタとして絞り込みに使い、自由記述系（name / メモ / description / h2）は単一テキストボックスで横断検索する、というハイブリッド方式にする。
* フィルタ（絞り込み）と表示順（ソート）は完全に分離する。ソートはExplorerの列ソート（名前・サイズ等のヘッダクリックで昇順/降順）と同じ発想で、単一値フィールド（name, 入手日, 購入価格, ファイル容量, published_at, wish_list_count等）のみを対象にする。属性 / appTag / tags / 対応アバターのような複数値フィールドはソート対象にはせず、フィルタとしてのみ機能させる。

## missing fileの復旧

* 起動時に全LocalFileのpathを軽くstat確認して`is_downloaded`を更新する。hash照合などの内容検証は、個別にItemを開いた時、そのItem詳細画面に表示される全LocalFileについて毎回行う（1Item内のLocalFile数は通常少数なので軽量）。
* missing発生時の再スキャン範囲は、過去に取り込み元として選択したフォルダの履歴に限定する（ドライブ全体は対象外）。範囲外を探したい場合はユーザが明示的にフォルダを指定し直す。

## BOOTH商品が非公開・削除された場合

* JSON取得の単発404では「非公開/削除」と確定させない。次回更新予定のタイミングで複数回（2〜3回程度）連続して同じ404が観測されて初めて確定する。一時的なネットワーク不調との誤判定を避けるため。
* 確定後も、通常の更新間隔よりずっと長い間隔（例：月1回程度）で復活チェックだけは継続する。完全に打ち切ると、本当に復活した際に気付く手段がなくなるため。

## 同一BoothIDに複数ZIP・複数versionが存在する場合

* 上記「Item ↔ LocalFile」の1:N構造でそのまま表現する。専用の別構造は不要。

## 「要確認」通知の一本化

以下の3種類の「ブロッキングではないが把握しておきたい」事象は、個別にUIを作らず、共通の1つの受信箱にまとめる。受信箱内では種別ごとにグルーピング表示する。

1. 対応アバターのあいまい判定（`作業方針メモ.md`の「対応アバターの解決」で決定済みの、精度向上のためのユーザへの質問）
2. LocalFileの孤立したvariation紐付け（BOOTH更新でvariationが消滅した場合）
3. 重複ハッシュの発見
