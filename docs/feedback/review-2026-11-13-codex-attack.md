## 1回目（G）の Codex の報告

以下、Codex の報告そのまま。

**3件の問題を試験で確認しました。追加24件は、2回とも20件成功・4件失敗でした。** 同じ原因の失敗2件をまとめています。

製品コード・既存試験は変更していません。アプリ本体のビルド・起動、外部通信、利用者データへのアクセス、コミット・プッシュは行っていません。

### [中] ソフト ID の重複で再読み込みが失敗し、別トークンへイベントが渡る
- 場所：`Chmonos.Api/ApiClients.cs:167`、`Chmonos.Api/PluginEvents.cs:512`
- 手順：ソフト A が購読し、`itemOpened` を1件積む。一時保存先の `api-clients.json` に、異なるトークンハッシュを持つ同じ `id: "a"` の行を2件書き、読み直す。その後、もう一方のトークンで `/v1/plugin/events` を取得する。
- 起きること：重複キーの `ArgumentException` が発生する。一方、認証索引は既に差し替わっており、もう一方のトークンに A のイベントが返る。
- 根拠：`Reload` は `_index` を公開してから変更通知を呼ぶ。通知先の `OnClientsChanged` が `ToDictionary` で失敗する。失敗した試験：
  - `控えの重複ソフトIDは_例外を出さず隔離する`：`ArgumentException … Key: a`
  - `重複IDの読み直しが失敗しても_別トークンへ既存の列を渡さない`：空を期待した応答に、A の `itemOpened` が1件入った。
- 確かさ：**試験で確かめた**。保存ファイルの破損・手編集が前提。通常の許可手続きで重複 ID を作れることは確認していない。
- 直し方の方向：重複 ID の行を認証索引の公開前に隔離する。認証索引・メニュー・イベント列の対応が検証できてから、新しい状態を公開する。

### [中] 保存した未知のメニュー条件が無条件に変わる
- 場所：`Chmonos.Api/ApiClients.cs:164`、`Chmonos.Api/PluginMenus.cs:231`、`Chmonos.Core/Models/ApiClients.cs:132`
- 手順：一時保存先のメニューに `"when":{"futureRestriction":true}` を書き、読み直して `/v1/plugin/menu` を取得する。
- 起きること：不正な宣言として隠されず、`"when":null` の項目が返る。保存ファイルを読む経路では、HTTP の宣言時に拒否される未知の条件が失われる。
- 根拠：型付きの保存モデルに読む段階で未知の欄が捨てられる。`FromRecords` の再検証時には、その条件が残っていない。`控えの未知の条件は_無条件の許可へ変わらない` が失敗し、応答に `preview`・`when:null` が残った。
- 確かさ：**試験で確かめた**。
- 直し方の方向：保存した宣言の未知の条件を、型への変換前に検証する。未知の条件を含む宣言は出さず、条件を捨てて許可を広げない。

### [中] 許可を外しても、その種類の未受信イベントを取得できる
- 場所：`Chmonos.Api/PluginEvents.cs:525`、`Chmonos.Api/PluginEvents.cs:241`
- 手順：`itemOpened` と `selectionChanged` を購読し、各1件を積む。`watch.itemOpened` の許可を外して読み直し、同じトークンで `/v1/plugin/events?after=0&wait=0` を取得する。
- 起きること：購読から `itemOpened` は外れるが、列に残った `itemOpened` と商品 ID が返る。
- 根拠：許可変更時は `Kinds` だけを削除し、既存のイベント列は変更しない。応答も現在の許可で絞らない。`許可を外した種類は_未受信の出来事も返さない` が失敗し、応答に両方の種類が残った。
- 確かさ：**試験で確かめた**。取り消し後に新しく発生したイベントの漏れではなく、取り消し前の未受信分。
- 直し方の方向：許可を外した種類の未受信分を削除するか、返す直前に現在の許可で除外する。許可が残る種類とメニューのイベントは維持する。

## 2回目（H・A）の Codex の報告

以下、Codex の報告そのまま。

**新規の指摘は2件です。追加した25ケースは、19件成功・6件失敗でした。** 失敗は次の2原因にまとまります。

1. **［中］壊れた manifest を正常な空一覧として扱い、VPM の削除履歴や空の改変控えを保存する。**
2. **［中］時計が戻ると、VPM 履歴の現在が古い版になり、同じ履歴・写しが増え続ける。**

D2・D3 の修正、通知の追記保護、バックアップの往復と失敗時の片付けは、今回の条件では通りました。製品コードと既存試験は変更せず、失敗する試験も残しています。

### [中] 壊れた manifest が「VPM を全部外した」という記録になる

- 場所：`Chmonos.Core/Services/VpmPackages.cs:94`・同`:136`、`Chmonos.Core/Services/ModificationService.cs:755`
- 手順：一時保存先に `com.example.tool` の版 `1` を控える。作り物のプロジェクトの `Packages/vpm-manifest.json` を、途中で切れた `{"locked":{"com.example.tool":` または `[]` に変更し、再走査・保存する。別試験では、その状態で改変に構成物を追加する。
- 起きること：再走査は「全部外した」という履歴を追加する。改変への記録では、前の走査結果に版 `1` があるのに、それを使わず空の VPM 写しを保存する。
- 根拠：`ReadCore` は文字列を読めたかで完全性を判定する一方、`ParseManifest` は構文エラー・不正なルートを空一覧にする。そのため `TryRead` が空一覧を返し、履歴維持や改変の控えへの代替が働かない。対応する3ケースが失敗し、削除印が真、または期待したパッケージ一覧が空になった。
- 確かさ：**試験で確かめた**。再走査結果と改変の保存ファイルを読み直して確認。
- 直し方の方向：manifest の解析結果に成功・失敗を持たせ、壊れている場合は `TryRead` を `null` にする。正常に読めた空一覧と区別し、既存履歴の維持・前の控えへの代替へ進ませる。

### [中] 時計が戻ると、現在の版と記録順が食い違い、同じ履歴が増える

- 場所：`Chmonos.Core/Services/VpmHistory.cs:112`・同`:28`、`Chmonos.Core/Models/Modification.cs:219`、`Chmonos.Core/Services/ModificationService.cs:732`
- 手順：差し替え時計で12時に版 `1` を保存し、時計を11時へ戻して版 `2` を保存する。その後、版 `2` をさらに8回控える。改変の VPM 写しについても同じ日時順で記録する。
- 起きること：再読した `vpm` は版 `2` なのに、履歴の `Current` は版 `1` になる。状態は2種類しかないのに、履歴も改変の写しも10件になる。
- 根拠：日時順に並べ直した末尾を「最後に観測した状態」として使っている。時計が戻ると古い観測が末尾となり、同じ版でも変更と判定される。3試験が失敗し、現在の版は期待 `"2"` に対して実際 `"1"`、件数は期待 `2` に対して実際 `10`。
- 確かさ：**試験で確かめた**。プロジェクト履歴は保存後の再読、改変は写しを追加する実処理で確認。
- 直し方の方向：観測した順と壁時計の日時を区別する。日時で並べ替えた末尾を、現在値や重複判定に使わない。過去時点を引く処理と表示順も合わせて確認する。
