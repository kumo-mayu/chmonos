# サブエージェントで並行して直す

点検→担当ごとに分けて直す→統合、で踏みやすい所を先に避けるための手順。
件数が少ない・1つのファイルに固まっているなら、分けずに自分で直す（分けると統合と確かめの手間の方が大きい）。

## 洗い出しを分けるとき

- 観点で分ける（例：Core の正しさ／画面側の動き／文言と決め事／文書と実装／撮って見る／今日入れた変更の副作用／試験の穴）
- 既知の一覧（`docs/feedback/` の `open.md`・`behavior-*`・`ui-consistency-*`・`review-*`）を渡し、載っている物は除かせる
- 報告の形を決めて渡す：重大度・file:line・何が起きるか（状況→結果）・直し方の方向、推測は「要確認」、件数の上限
- 読むだけの点検は worktree を使わない。撮って見る点検は1人だけ（画面は1つ）
- 戻った重い指摘は、ユーザへ出す前に自分でコードか画像を見て確かめ、確かめた物に印を付けて報告する
- 洗い出しの報告で止め、直すかを聞く（CLAUDE.md の「進め方」）

## 直すのを分けるとき

- **触るファイルで分ける**（Core の保存・通信／商品を書き換える処理／画面の動き／画面の見た目とキーボード、など）。
  同じファイルに2人が入るなら「そのファイルのどの関数だけ」と境目を書き、相手の担当を互いに伝える
- `isolation: "worktree"` で起動する。**worktree は古い地点から始まることがある**（master でなく、前にプッシュした地点だった）。
  指示の最初に「`git log --oneline -3` で master の最新にいるか確かめ、古ければ `git merge --ff-only master`」を書く
- 画面の確かめは、**写しが違えば並行でできる**（`ui-check` の道具が、起動したアプリを写しごとに控える。2026-09-30 までは控えが1つで、2人が起動すると互いのアプリを閉じ合った）。
  担当ごとに写しを割り当て、指示に「道具を読み込んだら `Use-ChmonosStore <写し>`」と書く。決まりは `ui-check` スキルの「並行で確かめるとき」
  （BOOTH へ問い合わせる確かめ・実入力・画面から直に撮る確かめ・速さの計測は、1人ずつ）
- 作業用フォルダ（scratchpad）は自分とサブエージェントの全員で共有される。コミットの下書きも、測る道具・スクリプトも、担当ごとの名前か担当ごとのフォルダに置かせる
  （`msg-agentA-*.txt`・`agentA\`）。サブエージェントが1人でも同じで、`perf-kit.ps1` を同じ名前の自分の道具で上書きされた
  （今は `.claude/skills/perf-measure/scripts/` に置いてある。使い回す部品は作業用フォルダではなく、スキルの `scripts/` に足させる）
- 指示の中のコミットの署名は `Co-Authored-By:` の行だけにする。`Claude-Session:` の行を指示に入れると、起動が安全判定で止められた。
  セッションの署名は、統合するときの merge コミットに付ける
- ユーザの判断が要る項目は「飛ばして、選択肢と根拠を報告に書く」と指示する。判断が出たら SendMessage で担当へ伝える
- 重さでモデルを選ぶ：並行・保存・データ保全の直しは Opus、文言・文書の照合・撮って見る確かめは Sonnet
  - **試行中（2026-10-02・ユーザ「あまり使用しすぎない形で試しましょう」）**：完成形を言えて、試験か絵で結果を確かめられる仕事
    （仕様の決まった小さな機能・記録の照らし合わせ）も1件ずつ Sonnet（`model: "sonnet"`）で出す。同じ仕事を両方で回して比べることはしない。
    比べる相手は Opus の実績（入手日の札 SEC2：約15.7万トークン・101回、照らし合わせ CHK：約14.4万トークン・63回）。
    比べるのは、かかった量と、統合の前に自分で直した数。判断の要る設計・データ保全は Opus のまま
  - Sonnet へ出す指示には次の3つを足す（記事で挙がっていた癖への対策。2026-10-02）：
    「頼まれた変更だけを行い、終えたら止めて報告する」「最後まで続ける。止まるのは情報が足りないときと取り返しのつかない操作の前だけ」
    「足した試験は、直しを一時的に戻すと落ちることを確かめる（期待値を記憶から書き間違えることがある）」

## 統合

担当が終わるたびに、1本ずつ：

1. `git log --format=%s` と `git show --stat` で、各コミットの件名と変えたファイルが合っているか見る（下書きの取り違えを拾う）
2. `git merge --no-ff <ブランチ>`（メッセージに何の直しかと署名の2行）。衝突は両方の意図を残して解く。`docs/features.md` は同じ行を2人が直しやすい
3. `dotnet build`（警告0）と `dotnet test`
4. 統合できたら `git worktree remove` と `git branch -d`（-d は統合済みでないと断るので安全）
5. 担当が「範囲外として残した物」は拾って、自分で直すか次の担当へ回す

全部そろったら、統合した本体のビルドで画面を撮って確かめる（Sonnet に任せてよい）。
2人の変更が重なった所を中心に見させ、最後に写しで起動したまま渡し、`Test-ProductionUntouched` の結果を報告に書く。

## 記録

見つけた物・判断をもらった物・確かめていないことを `docs/feedback/review-YYYY-MM-DD.md` に書く（何が変だったかだけ。直し方はコミットに書く）。
`open.md` の「記録のみ」に1行、判断待ちは「判断待ち」に置く。友人のデータの写しで見た名前は書かない。
